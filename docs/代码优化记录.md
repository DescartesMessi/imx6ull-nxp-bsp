## ① 启动链路优化（已完成，含实测）

### 优化动作

1. U-Boot `bootdelay` 由 3 秒改为 1 秒。
   - 运行态：U-Boot 命令行 `setenv bootdelay 1; saveenv`（环境变量存 eMMC）

     `#define CONFIG_BOOTDELAY 1`（必须放在 `mx6_common.h` 之前，否则被其兜底值覆盖）

   - 原：`imx6ull-alientej-jjl.dtb`（少一个 `k`）
   - 新：`imx6ull-alientek-jjl.dtb`

## ③ 板级驱动优化（已完成，含硬件回归修复）

### 第一步：GT9147 迁移到 gpiod 描述符 API

改动：头文件换成 `linux/gpio/consumer.h`；结构体改用 `struct gpio_desc *`；
probe 改用 `devm_gpiod_get(&client->dev, "reset"/"interrupt", GPIOD_OUT_LOW)`；
方向与电平操作改用 `gpiod_direction_*` / `gpiod_set_value_cansleep`；
中断号获取改用 `gpiod_to_irq`；错误处理改用 `IS_ERR` / `PTR_ERR`。

| 指标 | 改前 | 改后 |
|---|---|---|
| 传统 GPIO API 调用点 | 12 | 0 |
| gpiod 描述符 API 调用 | 0 | 9 |
| 编译告警 | — | 0 |

计数口径（可复现）：

```bash

```

### 第二步：迁移后的实机回归 —— 编译期完全无法发现的极性错误（重点）

这一段完整记录一次“编译通过、符号正确、上板失败”的排查过程。
它的价值在于说明：**接口迁移类改动无法只靠编译验证，必须上板跑通一次真实业务。**

#### 1. 迁移完成后，静态检查全部通过

改完 `gt9147.c` 后，主机侧的验证结果看不出任何问题：

- 交叉编译单文件：`make O=build/kernel drivers/smarthome/gt9147.o` → 退出码 0，零告警
- 链接符号核对：`arm-linux-gnueabihf-nm build/kernel/drivers/smarthome/gt9147.o`

  ```
  U __devm_gpiod_get
  U gpiod_direction_input
  U gpiod_direction_output
  U gpiod_set_value_cansleep
  U gpiod_to_irq
  ```

- 传统 API 残留计数：12 → 0（`grep` 口径见上）
- 全目录复扫：8 个驱动全部使用 `linux/gpio/consumer.h`

也就是说，编译器、链接器、符号表和静态检查都判定这是一次干净的迁移。

#### 2. 上板后触摸屏直接 probe 失败

把新内核烧进 eMMC 后启动，触摸屏这一路报错：

```
gt9147 1-0014: failed to read product ID: -5
gt9147: probe of 1-0014 failed with error -5
```

对照同一份启动日志，其余 7 个驱动全部正常：

```
smarthome-back-key back-key: back key initialized
dht11 smarthome_dht11: DHT11 ready, device=/dev/dht11
icm20608 spi2.0: ICM20608 detected, WHO_AM_I=0xae
ap3216c 0-001e: AP3216C initialized successfully (/dev/ap3216c)
smarthome_beep: probed successfully (/dev/beep_device)
smarthome_sr04 sr04: device: /dev/sr04, irq: 152
sr501 smarthome_sr501: SR501 ready, irq=168
```

异常边界因此非常清晰：这次只动了 GT9147 的 GPIO 接口，也只有 GT9147 挂掉。

#### 3. 为什么编译期发现不了这个错误

错误码 `-5` 是 `-EIO`，来自 I2C 读产品 ID 寄存器（0x8140）失败。
而“复位电平反相”既不是语法错误、也不是类型错误、更不是符号缺失：

- `gpiod_direction_output(desc, 0)` 与 `gpiod_direction_output(desc, 1)`
  两个参数都合法，编译器没有任何理由报错；
- 真正决定物理电平高低的是设备树里的 `GPIO_ACTIVE_LOW` 标志，
  这个标志在**运行时**才由 gpiolib 参与换算；
- 于是“驱动写入的逻辑 0/1”与“引脚实际输出的物理高/低”之间的映射关系，
  在编译期完全没有被检查的机会。

换句话说，这个 bug 处在**驱动代码语义与设备树语义的交叉点**上，
静态工具看不到，只有把系统跑起来、让硬件真正响应，才会暴露。

#### 4. 根因：gpiod 用逻辑电平，旧 gpio_* 用物理电平

设备树中的极性标志：

```dts
reset-gpios     = <&gpio5 9 GPIO_ACTIVE_LOW>;   /* 复位低有效 */
interrupt-gpios = <&gpio1 9 GPIO_ACTIVE_HIGH>;  /* 中断高有效 */
```

- 旧接口 `gpio_set_value()` 直接操作**物理电平**，迁移前代码写 0 就是物理低；
- 新接口 `gpiod_set_value()` 操作**逻辑电平**，会再叠加 `GPIO_ACTIVE_LOW`：
  - 逻辑 1 → 物理低（复位有效）
  - 逻辑 0 → 物理高（释放复位）

迁移时只替换了函数名、把逻辑值照抄旧代码，于是复位时序整体反相：
上电后芯片一直被按在复位态，I2C 自然读不到产品 ID。

值得注意的一点：只有复位脚出问题、中断脚没出问题，正是因为两个引脚的极性不同。
`interrupt-gpios` 是 `GPIO_ACTIVE_HIGH`，逻辑电平与物理电平同向，
所以照抄旧代码不会产生任何影响——这也说明**不能用“另一个脚没问题”来推断迁移安全**。

#### 5. 修复

在 `gt9147_reset()` 中按逻辑电平重写复位时序，并补注释说明极性来源：

```c
/*
 * 设备树中 reset-gpios 带 GPIO_ACTIVE_LOW，gpiod 的逻辑电平与物理电平相反：
 *   逻辑 1 -> 物理低（复位有效）
 *   逻辑 0 -> 物理高（释放复位）
 * 所以“复位有效”要写 1，而不是旧 gpio_* 接口里的 0。
 */
ret = gpiod_direction_output(ts->reset_gpio, 1);   /* 断言复位 */
...
gpiod_set_value_cansleep(ts->reset_gpio, 0);       /* 释放复位 */
```

#### 6. 验证

重新编译并烧写后，同一路驱动恢复正常：

| 指标 | 迁移后（错误） | 修复后 |
|---|---|---|
| 产品 ID 读取 | failed: -5 | `product ID: 1158, firmware version: 0100` |
| 触摸参数 | 未打印 | `resolution: 800x480, points: 5, irq type: 3` |
| Input 注册 | 无 | `input: gt9147-touchscreen ... /dev/input/event2` |
| 中断 | 无 | `GT9147 touchscreen registered on IRQ 39` |

#### 7. 结论

- `gpio_*` → `gpiod_*` 是**语义变更**，不是纯重命名：必须成对检查
  设备树 polarity 标志与驱动电平语义。
- 编译通过、符号正确、零告警，都不能证明行为等价。
  这类改动的验收标准是“上板跑通一次真实业务”，
  本例中的验收动作就是：读到产品 ID、解析出分辨率与触点数、注册 input 设备。
- 这次能快速定位，也正是因为手里有板子、有可对比的启动日志：
  8 个驱动只有 1 个挂，异常边界立刻收敛到本次唯一改动的 GPIO 代码上。

## ⑥ 有线网口与 PHY 优化（已完成，含实测）

有线网口是本板最重要的板载外设：根文件系统通过 NFS 挂载，整机可用性依赖它。
因此这块单独做了一次从硬件寄存器到驱动绑定的完整排查。

### 1. 现状诊断（硬件 + 驱动 + 内核配置）

板上有两个 FEC 控制器，均配置为 RMII：

| 接口 | 控制器 | 设备树节点 | 状态 |
|---|---|---|---|
| eth0 | ENET1 | `20b4000.ethernet` | 正常，承载 NFS 根文件系统 |
| eth1 | ENET2 | `2188000.ethernet` | 无 PHY，不可用 |

eth0 侧实测信息（均来自板端运行时读取）：

| 项目 | 实测值 | 读取方式 |
|---|---|---|
| PHY 芯片 ID | `0x001cc816` | `cat /sys/bus/mdio_bus/devices/*/phy_id` |
| PHY 厂商 | Realtek（RTL8201F 系列，10/100M） | 由 PHY ID 的 OUI 段判定 |

### 2. 发现的问题

| 编号 | 问题 | 证据 |
|---|---|---|
| P1 | **内核没有编译 realtek PHY 驱动**，PHY 只能退化为通用驱动 | 原 defconfig 中 `# CONFIG_REALTEK_PHY is not set`；启动日志为 `PHY driver [Generic PHY]` |

### 3. 已实施的优化

针对 P1、P2 做了两处改动：

1. `arch/arm/configs/imx6ull_alientek_jjl_defconfig`：新增 `CONFIG_REALTEK_PHY=y`
2. `drivers/net/phy/realtek.c`：在 `realtek_drvs[]` 与 `realtek_tbl[]` 中
   增加 RTL8201F 条目（`phy_id = 0x001cc816`，`phy_id_mask = 0x001fffff`，
   复用 `genphy_config_aneg` / `genphy_read_status`）

### 6. 第二个网口 eth1 的修复（已完成）

#### 6.1 硬件事实（由板级资料确认）

- i.MX6U 内部有两个网络 MAC，各需外接一个 PHY，本板两个 RJ45（HR91105A）组成 10M/100M 双网口。
- **ENET1 与 ENET2 共用 ENET_MDIO / ENET_MDC**，这两根线接在 GPIO1_IO06 / GPIO1_IO07。
- 两个 PHY 各有独立复位：ENET1_RESET → SNVS_TAMPER7（GPIO5_IO07），
  ENET2_RESET → SNVS_TAMPER8（GPIO5_IO08）。设备树中的
  `pinctrl_enet1_reset` / `pinctrl_enet2_reset` 与 `phy-reset-gpios` 与之一致，无需修改。

> 关于 PHY 型号：板级资料确认 **V2.4 及以后版本的底板采用 SR8201F**（RMII 接口、支持 Auto-MDIX），
> 更早版本的资料写的是 LAN8720A。实测两块 PHY 的 MDIO 寄存器读回 ID 均为 `0x001cc816`
> （Realtek OUI，RTL8201F 家族），内核 `fec_main.c` 的复位延时注释也写着 “SR8201F”，
> 与 V2.4+ 的说明完全一致。因此本项目按 SR8201F / RTL8201F 兼容处理是正确的。

> 关于 ENET 编号（容易踩坑）：本 SoC 上 **ENET1 = 0x02188000、ENET2 = 0x020b4000**。
> 依据是 U-Boot 的 `arch/arm/include/asm/arch-mx6/imx-regs.h`：
> `ENET2_BASE_ADDR = AIPS1_OFF_BASE_ADDR + 0x34000 = 0x020B4000`。
> 因此 dtsi 中 `fec1: ethernet@02188000`（ENET1）与 `fec2: ethernet@020b4000`（ENET2）
> 的对应关系是**正确**的，并不是写反。

#### 6.2 根因：三层叠加

| 层 | 问题 |
|---|---|
| 编号体系不对应 | 硬件编号是 ENET1（`0x02188000`）/ ENET2（`0x020b4000`），而 Linux 的 `eth0`/`eth1` 是**按探测顺序**命名——ENET2 先探测成为 `eth0`，ENET1 成为 `eth1`。两套编号不对应，是后面所有混淆的根源 |
| 驱动行为 | `fec_enet_mii_init()` 中 `fep->dev_id = dev_id++` 按探测顺序分配；只有 `dev_id == 0` 的那一路会注册 MDIO 总线，另一路直接复用（`FEC_QUIRK_ENET_MAC && dev_id > 0` 分支）。结果 **ENET2 拥有并驱动共享 MDIO 总线**——这与 `enet2grp` 把 GPIO1_IO06/07 配成 ENET2_MDIO/MDC 完全吻合，原 pinctrl 是对的 |
| PHY 节点位置 | `of_mdiobus_register()` 只遍历**总线拥有者自己**的 `mdio` 子节点。原设备树把两个 PHY 分别挂在 `&fec1` 和 `&fec2` 下，而拥有总线的是 ENET2（`&fec2`），于是挂在 `&fec1` 下的那个 PHY 从未被注册，对应网口自然找不到 PHY |

这三层叠加，导致现象看起来很像“第二块 PHY 不存在”：只有一条 `libphy: fec_enet_mii_bus: probed`，
`ip link set eth1 up` 返回 `SIOCSIFFLAGS: No such device`。

#### 6.3 修复

把两个 PHY 都声明到总线拥有者（`&fec2`，即 `ethernet@020b4000`）的 `mdio` 子节点下：

```dts
&fec1 {   /* ethernet@02188000：复用 MDIO 总线，不声明 mdio 子节点 */
	phy-handle = <&ethphy0>;
	...
};

&fec2 {   /* ethernet@020b4000：先探测，拥有 MDIO 总线 */
	phy-handle = <&ethphy1>;
	...
	mdio {
		ethphy1: ethernet-phy@1 { compatible = "ethernet-phy-ieee802.3-c22"; reg = <1>; };
		ethphy0: ethernet-phy@0 { compatible = "ethernet-phy-ieee802.3-c22"; reg = <0>; };
	};
};
```

第二个 PHY 的实际地址是通过“先不写 `reg`、让内核自动扫描”方式测出来的：

```
mdio_bus 20b4000.ethernet: scan phy ethernet-phy at address 0
...
fec 2188000.ethernet eth1: Freescale FEC PHY driver [RTL8201F 10/100 Ethernet]
    (mii_bus:phy_addr=20b4000.ethernet:00, irq=-1)
```

测出地址为 **0** 后即写回 `reg = <0>`，去掉扫描噪声。

#### 6.4 实测结果

| 指标 | 修复前 | 修复后 |
|---|---|---|
| MDIO 总线上的设备 | 仅 `20b4000.ethernet:01` | `:00` 与 `:01` 两个 |
| `ip link set eth1 up` | `SIOCSIFFLAGS: No such device` | 成功，绑定 `phy_addr=20b4000.ethernet:00` |
| eth0 / NFS 启动 | 正常 | 正常（未受影响） |
| 启动噪声 | 无 | 固化地址后无 `scan phy`、无 `invalid PHY address` |
| 整机启动时间 | 10.36s | 10.10s（同一量级） |

#### 6.5 过程中的一次事故与恢复（教训）

第一次修复时我把 `mdio` 子节点放到了 `&fec1`（按“ENET1/ENET2”的字面理解），
并删掉了 `&fec2` 的 `mdio`。结果总线拥有者（`&fec2`）没有 `mdio` 子节点，
驱动退化为 `mdiobus_register()` 全地址扫描，扫到的 PHY 没有绑定设备树节点，
`of_phy_connect()` 匹配失败 —— **连 eth0 的 PHY 也拿不到，NFS 根文件系统挂载失败，内核 panic 挂起**。

恢复过程：

1. 复位后 1 秒 bootdelay 窗口内，用 `serial_console.py --spam` 连续发送按键抢占 U-Boot；
2. 注意：长时间连续发送会**占满 U-Boot 命令行缓冲区**，需先发一个回车清行，再下发命令；
3. 用 eMMC 上保留的同名备用镜像引导：
   `fatload mmc 1:1 80800000 zImage; fatload mmc 1:1 83000000 imx6ull-alientej-jjl.dtb; bootz 80800000 - 83000000`
   （该文件是早前部署时留下的拼写错误副本，内容为可用版本，意外成了救命备份）
4. 进入 Linux 后把修复版 DTB 写入 eMMC 启动分区，重启恢复正常。

教训：**改动承载根文件系统的网口相关配置时，必须在 eMMC 启动分区保留一份可独立引导的备用 DTB**，
并且要从驱动源码确认“哪一路 FEC 拥有共享总线”，而不是按节点名字面推断。

| 事项 | 说明 | 建议 |
|---|---|---|
| eth1 链路 | eth1 已能启用并绑定 PHY，但 `carrier=0`（第二网口未插网线），链路能力尚未实网验证 | 插上网线后测 `carrier`、`speed` 与吞吐 |
| eth1 启用对 eth0 的扰动 | `ip link set eth1 up` 时 eth0 出现约 1 秒 `Link is Down` 后恢复，NFS 未中断 | 需要进一步确认是两个 PHY 地址/映射问题，还是共享 MDIO 上的时序干扰 |

| MDIO 引脚归属 | `enet2grp` 把 GPIO1_IO06/07 配为 ENET2_MDIO/MDC，`enet1grp` 不含 MDIO。这与硬件一致：共享 MDIO 由 ENET2 驱动，而 ENET2 正是 MDIO 总线拥有者 | **原配置正确，无需修改**（此前误判为“引脚被占用”，已更正） |
| PHY 型号资料差异 | 早期资料写 LAN8720A，**V2.4 及以后底板为 SR8201F**（RMII、支持 Auto-MDIX），与实测 ID `0x001cc816` 及驱动注释一致 | 按 V2.4+ 说明为准，PHY 按 SR8201F / RTL8201F 兼容处理 |
| 硬件编号与网口序号 | 硬件按 ENET1（`0x02188000`）/ENET2（`0x020b4000`）编号，Linux 按探测顺序命名（ENET2→eth0、ENET1→eth1） | 涉及网口配置时先确认用的是哪套编号，避免张冠李戴 |

### 8. 网口 MAC 改用设备树指定（已完成）

#### 8.1 原来的问题

两个网口 MAC 相同，且分配是错乱的。排查后发现是 U-Boot 的 fixup 在起作用：

1. `imx6ull.dtsi` 里定义了别名 `ethernet0 = &fec1; ethernet1 = &fec2;`，
   即按**硬件编号**：`ethernet0` = ENET1（`0x02188000`）、`ethernet1` = ENET2（`0x020b4000`）。
   这个别名本身没错，问题在于它与 Linux 的网口序号不对应——
   Linux 的 `eth0` 是 ENET2、`eth1` 是 ENET1。于是别名 `ethernet0`
   实际指向了 Linux 眼中的 **eth1**。
2. U-Boot 的 `fdt_fixup_ethernet()`（`common/fdt_support.c`）会遍历 `/aliases` 中
   以 `ethernet` 开头的项，按序号取环境变量 `ethaddr` / `ethNaddr`，
   写回对应节点的 `mac-address` 与 `local-mac-address`。
3. 结果是 MAC 被写串：`ethernet@02188000`（Linux eth1）拿到 `ethaddr=b8:ae:1d:00:00:00`，
   而 `ethernet@020b4000`（Linux eth0）拿到的是 `eth1addr`（全零，无效）——
   内核因此回退到第 4 优先级来源（U-Boot 写好的 FEC 地址寄存器），
   又得到同一个 `b8:ae:1d:00:00:00`，最终两口撞号。

顺带确认了内核侧的取值优先级（`fec_get_mac()`）：
模块参数 → **设备树 `local-mac-address`** → 平台数据 → FEC 寄存器 → 随机值；
且只有“模块参数”来源会叠加 `dev_id` 偏置，**设备树里的 MAC 原样使用**。

#### 8.2 改法

在两处 FEC 节点写死 MAC，并**删掉 `ethernet0`/`ethernet1` 别名**，
让 U-Boot 的 fixup 无项可改、不再覆盖：

```dts
&fec1 {                       /* ethernet@02188000，Linux eth1 */
	local-mac-address = [b8 ae 1d 00 00 01];
	...
};

&fec2 {                       /* ethernet@020b4000，Linux eth0 */
	local-mac-address = [b8 ae 1d 00 00 00];
	...
};

&{/aliases} {
	/delete-property/ ethernet0;
	/delete-property/ ethernet1;
};
```

MAC 取值说明：eth0 沿用原值 `b8:ae:1d:00:00:00`（避免改动承载 NFS 的网口配置），
eth1 取相邻的 `b8:ae:1d:00:00:01`。若产品有正式的 OUI 分配，直接改这两个字面量即可。

#### 8.3 实测结果

| 项目 | 改前 | 改后 |
|---|---|---|
| eth0 MAC | `b8:ae:1d:00:00:00` | `b8:ae:1d:00:00:00`（不变） |
| eth1 MAC | `b8:ae:1d:00:00:00`（与 eth0 撞号） | `b8:ae:1d:00:00:01` |
| 设备树 `local-mac-address` | 被 U-Boot 改写/置零 | 与运行时一致，U-Boot 不再改写 |
| dhcp/NFS 启动 | 正常 | 正常（`IP-Config hwaddr=b8:ae:1d:00:00:00`） |

验证命令（板端）：

```sh
for i in eth0 eth1; do echo -n "$i "; cat /sys/class/net/$i/address; done
od -An -tx1 /proc/device-tree/soc/aips-bus@02000000/ethernet@020b4000/local-mac-address
od -An -tx1 /proc/device-tree/soc/aips-bus@02100000/ethernet@02188000/local-mac-address
```

## ⑦ 根文件系统由 NFS 改为 eMMC 本地（已完成，含实测）

这是整轮优化里收益最大的一项，也是 ① 里遗留的“内核阶段约 3 秒等链路”问题的根治办法。

### 1. 动机

原来根文件系统走 NFS，带来两个后果：

1. 内核必须等以太网链路建立、拿到 IP 之后才能挂载根文件系统，
   这段时间（含 PHY 自协商）约 3 秒，无法通过优化网口本身消除；
2. 板子**没有网络就起不来**，工程上不健壮。

把根文件系统放到板载 eMMC，这两个问题一起解决。

### 2. 现状确认

排查发现 eMMC 第二个分区本来就是一个可用的 ext3 根文件系统：

| 项目 | 实测 |
|---|---|
| 分区 | `mmcblk1p1` 250MB（FAT 启动分区）、`mmcblk1p2` 3.35GB |
| 文件系统 | p2 为 ext3（超级块 magic `53 ef`，日志 `EXT3-fs ... using internal journal`） |
| 容量 | 6.5G，已用 410M，可用 5.7G |
| 内核支持 | `CONFIG_EXT2_FS/EXT3_FS/EXT4_FS=y`（内置，可直接作根文件系统） |
| init | `linuxrc -> bin/busybox`、`/sbin/init -> ../bin/busybox`、`/etc/inittab` 完整 |

### 3. 改动

**U-Boot 环境变量**（`setenv` + `saveenv`）：

```
bootargs=console=tty0 console=ttymxc0,115200n8 root=/dev/mmcblk1p2 rootwait rw ipv6.disable=1
```

与原来相比去掉了 `root=/dev/nfs`、`nfsroot=...`、`ip=...`。
去掉 `ip=` 是关键：内核不再在启动阶段做 IP-Config、也就不再等待链路建立。

**板端 `/etc/init.d/rcS`** 追加后台网络配置（保证去掉 `ip=` 后仍能联网、且不阻塞启动）：

```sh
# 本地根文件系统不再依赖网络，这里后台配置 eth0，避免阻塞启动
```

## ⑧ 板级驱动协议层修复（已完成，含实测）

### 1. 背景：功能正常不等于协议正确

对 8 个板级驱动做了一次体检。生命周期（probe/remove 的资源释放顺序）、并发保护
（mutex/spinlock 的分工）、`copy_to_user` 返回值检查、错误路径清理这些方面基本没问题。
真正的缺陷在**传感器协议层**：驱动没有强制传感器数据手册规定的采样间隔。

这类问题的特点是**静默失效**——不报错、不崩溃，只是数据不对，只看代码很难发现。

### 2. 发现的问题

| 编号 | 问题 | 后果 |
|---|---|---|
| D1 | DHT11 未限制采样间隔（数据手册要求 **≥1s**） | 读太快时传感器会重复返回旧值或返回全 0，属于“假数据” |
| D2 | 全 0 帧能通过校验和（5 字节全 0 时 `0 == 0` 成立） | 无响应/时序失败时上报 `0.0°C / 0.0%RH` 且 `valid=1` |
| S1 | HC-SR04 未限制测量间隔 | 上一次的余波被当成这一次的回波，测出偏小的距离值 |

### 3. 修复

**D1 + S1：驱动内主动补足间隔（睡眠而非报错）**

```c
/* dht11.c：真正采样前先睡到满足 1s 间隔 */
if (dev->last_read &&
    time_before(jiffies, dev->last_read + msecs_to_jiffies(DHT11_MIN_INTERVAL_MS))) {
        unsigned long delay = dev->last_read + msecs_to_jiffies(DHT11_MIN_INTERVAL_MS) - jiffies;
        if (msleep_interruptible(jiffies_to_msecs(delay)))
                return -ERESTARTSYS;
}
...
dev->last_read = jiffies;
```

SR04 的间隔**没有采用固定的 60ms**，而是做成自适应的。

数据手册的 60ms 是按“最大量程 + 保护余量”给的保守值，直接当固定值用会造成
两类浪费或风险：取 60ms 在近距场景下白等，取更小的固定值（如 35ms）
又会在**超时路径**上不安全——驱动已经放弃等待，但模块可能还在等更远的回波，
此时触发会把迟到回波误算成下一次的距离（静默错值）。

真正的物理约束是「下一次触发不能落在上一次的回波窗口内」，而驱动恰好知道
窗口何时关闭，于是按测量结果分别推算下一次允许触发的时刻：

```c
    wait_ret = wait_for_completion_interruptible_timeout(
        &sr04->measurement_done, msecs_to_jiffies(SR04_TIMEOUT_MS));

    if (wait_ret == 0)   /* 等待超时：模块可能仍在等更远回波，保守兜底 */
        sr04->next_trigger = jiffies + msecs_to_jiffies(SR04_TIMEOUT_GUARD_MS); /* 60ms */
    else                 /* 收到回波：窗口已在下降沿关闭，只需换能器余振时间 */
        sr04->next_trigger = jiffies + msecs_to_jiffies(SR04_ECHO_GUARD_MS);    /* 10ms */
```

这样间隔会**随实际距离自动伸缩**：近处快、远处慢，不需要拍一个固定值。

选择“睡眠补足”而不是“返回 -EAGAIN”，是为了**不破坏用户态接口**：
应用照常 read/ioctl，只是被驱动自动节流到协议允许的速率。

**D2：拒绝全 0 帧**

```c
if (!(data[0] | data[1] | data[2] | data[3] | data[4]))
        return -EIO;
```

DHT11 湿度量程为 20~90%RH，0%RH 物理上不可能出现，据此判定无效更可靠。

**顺带修正**：`dht11_read_frame()` 里原注释写“不在这里关闭全局中断”，
但代码实际调用了 `local_irq_save()`，注释与代码矛盾。已改写为准确说明：
为什么要关（位周期 26~70us、采样点容差约 ±13us）、为什么用 `local_irq_save`
而不是 `local_irq_disable`（只关本核、保存恢复状态）、代价约 2.8~4ms。

### 4. 实测结果

测量工具：新增 `scripts/drv_rate.c`（ARM 静态编译），在固定时间内尽可能快地
反复 read 设备，统计成功采样次数、失败次数与平均单次耗时。
它能识别 sr04 这类用 `*ppos` 做一次性读保护的驱动，遇到 EOF 自动重开而不虚增计数。

| 指标 | 优化前 | 优化后 |
|---|---|---|
| DHT11 采样速率 | 108 次 / 6.0s ≈ **18 次/秒** | 9 次 / 8.4s，**937ms/次 ≈ 1.1 次/秒** |
| DHT11 返回数据 | **全 0 帧（0.0°C / 0.0%RH）仍 `valid=1`** | **真实数据 26.4°C / 64.0%RH**（`checksum=0x5e`） |
| DHT11 超时失败 | 93 次 / 6.0s | 3 次 / 8.4s |
| SR04 采样速率（固定 60ms 版） | 约 188 次测量尝试 / 6.0s ≈ **31 次/秒** | **75.3ms/次 ≈ 13.3 次/秒** |
| SR04 采样速率（自适应版） | 同上 | **30.4ms/次 ≈ 32.9 次/秒** |
| SR04 超时失败 | 103 次 / 6.0s | 固定版 9 次 / 8.1s；自适应版 **1 次 / 8.0s** |
| SR04 读数一致性 | — | 2.38m 目标连续 5 次：2381 / 2385 / 2381 / 2382 / 2376 mm（±5mm） |

两项修复都直接消掉了大量超时失败：

- DHT11 的超时次数从 93 降到 3 —— 说明原来大部分超时就是“读太快”造成的；
- SR04 的超时次数从 103 降到 1（自适应版）—— 说明原来大部分超时是
  **上一次余波干扰**，而不是“前方没有障碍物”。
- 自适应版把速率从固定 60ms 的 13.3 次/秒提到 **32.9 次/秒**（约 2.5 倍），
  同时把超时失败压到 1 次；读数的 ±5mm 重复性说明没有发生回波错配。
  注意速率会随目标距离变化（本次目标约 2.38m，单次回波 13.9ms），
  这正是自适应设计想要的效果。

### 6. 过程中自己引入并修掉的一个 bug（值得记录）

把 SR04 的固定间隔改成自适应时，第一次读就**卡死**，`Ctrl-C` 才能中断。

诊断手段（两个文件就够了）：

```
wchan=msleep_interruptible          # 卡在自己新加的睡眠里
152:  2  gpio-mxc  ...  smarthome_sr04   # 中断计数不再增长
```

根因：改写时漏掉了原代码里的零值保护。原来的写法是
`if (sr04->last_measure && time_before(...))`，那个 `&&` 不是多余的。

内核的 `jiffies` 初值不是 0，而是 `INITIAL_JIFFIES = -300*HZ`
（故意做成负数以便尽早暴露未初始化使用的 bug）。于是**开机后 5 分钟内
`jiffies` 折算成有符号长整型是负数**，此时：

- `time_before(jiffies, 0)` → `(long)(jiffies - 0) < 0` → **成立**
- `delay = 0 - jiffies` → 按无符号回绕成约 28300 jiffies
- `msleep_interruptible(jiffies_to_msecs(28300))` → **睡约 283 秒**

修复：不要拿 0 当“尚未设置”的哨兵值，而是在 probe 里显式初始化：

```c
sr04->next_trigger = jiffies;   /* 用真实 jiffies 初值，避免与 INITIAL_JIFFIES 比较出错 */
```

（DHT11 那处保留了 `dev->last_read &&` 的零值判断，所以没踩到这个坑。）

### 7. 经验

- 传感器驱动的正确性有三个层次：**能读到数据**、**数据是新的**、**数据是对的**。
  这次修的是后两层，而它们都不会在“驱动能 probe 成功”这件事上暴露出来。
- 判断驱动是否遵守协议，最直接的办法是**测速率**：把实测次数和协议上限一对比，
  一眼就能看出有没有约束。
- 涉及 `jiffies` 的比较，**永远不要用 0 或魔法值当哨兵**：`INITIAL_JIFFIES`
  让开机初期的时间轴处于“负值区间”，用 0 比较会得到反直觉的结果。
- 数据手册给的是**保守建议值**，直接当固定值用往往既慢又不对；
  更好的做法是找出它背后的物理约束，再让代码按实际场景去满足那个约束。

## ⑨ 启动期 probe 延时精简（已完成，含实测）

### 1. 动机

驱动 probe 是**串行阻塞**在启动路径上的：每个 `msleep()` 都会把整机启动往后推。
⑧ 修完协议层后顺带量了一下 probe 耗时，发现网口和海思两个传感器在启动时白等了近 1 秒。

### 2. 找到的三处延时

| 位置 | 原值 | 依据 | 处理 |
|---|---|---|---|
| 网口 PHY 硬件复位（`phy-reset-duration`，两个 FEC 各一份） | `200` (ms) | SR8201F 只要求 RESET# ≥10ms；且驱动在释放后还会固定延时 200ms，所以每口实际 400ms | 改为 `20`，留一倍余量 |
| AP3216C probe 等“首帧有效数据” | `msleep(120)` | ALS+PS+IR 一次转换约 100ms，固定等 120ms 既不能保证足够、又纯属浪费；数据有效性本就由寄存器有效位（`ir_valid`/`ps_valid`）判定 | 删除，交由调用方按有效位重读 |
| ICM20608 probe 读 WHO_AM_I 前等上电稳定 | `msleep(100)` | 该驱动在开机约 8 秒后才 probe，器件早已上电；真正的复位等待在 `reset_and_configure()` 里（软复位后 100ms）；WHO_AM_I 在睡眠模式下同样可读 | 删除 |

网口的这一处影响最大：从启动日志看，每个 FEC 的 `supply phy ...` 到 `registered PHC`
之间固定有 **约 0.43s**，正好等于 `200ms(拉低) + 200ms(释放后固定延时)` 加上少量开销。

### 3. 实测结果

| 指标 | 优化前 | 优化后 |
|---|---|---|
| 单个 FEC 的 probe 耗时 | 约 0.43s | **0.25s** |
| AP3216C probe 耗时 | 约 0.17s | **0.034s** |
| **整机启动（U-Boot banner → 控制台就绪）** | **5.610s** | **5.046s（-0.564s，-10.1%）** |

累计对比最初基线：**12.342s → 5.046s，共 -7.296s（-59.1%）**。

### 4. 功能验证（改动后逐项确认）

| 项目 | 结果 |
|---|---|
| DHT11 | `26.1°C / 61.0%RH`，`valid=1` |
| AP3216C | 第三次读数起稳定（`ALS=512`）；前两次偏低正是删掉“等首帧”后的预期行为，`valid=1` 始终有效 |
| ICM20608 | `WHO_AM_I=0xae`；`ACCEL[g]=-0.092,-0.022,0.994`（Z 轴约 1g，正是重力方向），陀螺仪近零 |
| SR04 | `distance_mm=2448`，`valid=1` |
| 网口 | `eth0` 取得 `192.168.31.50`，ping 主机 0% 丢包（说明缩短后的 PHY 复位时序仍然有效） |

### 5. 经验

- 启动路径上的 `probe` 是串行的，**里面的固定延时直接等于启动时间**。
  写驱动时习惯性加 `msleep(100)` 之类的“保险”，代价是每次开机都要付。
- 判断一个延时是否必要，看三点：**数据手册给的是最小值还是保守值**、
  **代码运行到这个位置时器件是否早已就绪**、**有没有别的机制（如有效位）替代它**。

## ⑩ CAN 总线使能与验证（已完成，含实测）

### 1. 发现的问题

设备树里 `&flexcan1` / `&flexcan2` 都写着 `status = "okay"`，还配了引脚和收发器供电
（`xceiver-supply = <&reg_can_3v3>`），看起来 CAN 是就绪的。但实测：

```
$ ls /sys/class/net/
eth0  eth1  lo  sit0          ← 没有任何 canX
$ grep CONFIG_CAN build/kernel/.config
# CONFIG_CAN is not set        ← 内核根本没编译 CAN 子系统
```

**设备树声明了 CAN，内核却没有 CAN 支持**——这是一处“配置看起来齐全、功能实际不存在”的缺口。

另外检查了用户态：总线工具 `candump` / `cansend` / `cangen`（can-utils）是有的，
但 busybox 的 `ip` 不支持 CAN 链路类型（`ip link set can0 type can ...` 直接报参数错误），
所以即使内核支持也**无法配置波特率**，接口会停在 `bit-timing not yet defined` 而起不来。

### 2. 修复

1. **内核配置**（`imx6ull_alientek_jjl_defconfig`）新增：

```
CONFIG_CAN=y
CONFIG_CAN_RAW=y
CONFIG_CAN_DEV=y
CONFIG_CAN_FLEXCAN=y
```

2. **交叉编译 iproute2 并部署**：`sources/3rdparty` 里本就带了 iproute2-4.4.0。
   编译时踩到一个旧版本与新 libc 的冲突（`include/namespace.h` 里的 `setns()` 兜底
   声明与 libc 冲突），用源码自带的开关解决：

```bash
make CC=arm-linux-gnueabihf-gcc SUBDIRS="lib ip" CCOPTS="-O2 -DHAVE_SETNS"
```

产出的 `ip`（302KB，含 `iplink_can.o`）部署为 `/sbin/ip`，替换掉功能不足的 busybox 版本。

3. **关闭 CAN2**：FLEXCAN2 的候选引脚在本板全部被占用——
   `UART2_RTS_B/CTS_B` 给了 ICM20608 的 ECSPI3、`ENET1_RX_EN/TX_DATA0` 给了以太网、
   `LCD_DATA10/11` 给了 LCD、`SD1_DATA2/3` 给了 SD 卡——没有可用引脚。
   因此把 `&flexcan2` 改为 `disabled`，避免出现一个存在却无法工作的 `can1`。

### 3. 硬件连接（由板级资料确认）

| 项目 | 说明 |
|---|---|
| CAN1_TX / CAN1_RX | 接到 I.MX6ULL 的 **UART3_CTS / UART3_RTS** |
| 收发器 | **TJA1050**，对外提供 CAN_H / CAN_L |
| 端接 | 板载 **120Ω** 匹配电阻（R10） |

设备树中的引脚组与之一一对应，无需修改：

```dts

        fsl,pins = <
                MX6UL_PAD_UART3_RTS_B__FLEXCAN1_RX	0x1b020
                MX6UL_PAD_UART3_CTS_B__FLEXCAN1_TX	0x1b020
        >;
};
```

#### 4.1 分层验证与一处未覆盖项

回环模式是 FLEXCAN **控制器内部**自收自发，信号不经过引脚，也就**不经过 TJA1050**。
因此这里把验证拆成三层，明确哪一层测到了、哪一层没测到：

| 验证层次 | 方法 | 结果 |
|---|---|---|
| 控制器 + SocketCAN 协议栈 | 回环模式收发 2 帧 | ✅ 0 错误 |
| 控制器发送 + 缺失 ACK 检测 | 正常模式连发 16 帧 | ✅ `berr-counter tx 128`（= 16×8，正是 ACK 错误特征） |
| 帧完整性与自接收 | 正常模式发送 1 帧前后对比计数 | ✅ RX 由 2 包/16 字节变为 3 包/24 字节，恰好 +1 帧 |
| **TJA1050 与 CAN_H/CAN_L 实总线** | 需要**第二个 CAN 节点** | ⚠️ **未做** |

第三层是判断物理层是否真正工作的关键：CAN 控制器在发送过程中会逐位回读总线
（bit monitoring），若 TJA1050 没有正确驱动总线，控制器会在第一个显性位就报**位错误**
并中止该帧，根本走不到 CRC/ACK 阶段，也不会把帧存入接收邮箱。实测帧能完整跑完、
仅缺一个 ACK，说明帧的位时序与回读是正确的。

但**没有第二个节点就永远收不到 ACK**，因此“实总线通信”这一层没有验证，
需要再接一块 CAN 节点或使用示波器观察 CAN_H/CAN_L 差分波形。
这一点不写成已完成项。

### 5. 顺带澄清：本板没有可用的第二路串口

检查串口时发现 `&uart2`（对应 `/dev/ttymxc1`）虽然被使能、设备节点也存在，
但它的四个引脚在本板全部被占：

```
MX6UL_PAD_UART2_TX_DATA__GPIO1_IO20     ← ICM20608 片选
MX6UL_PAD_UART2_RX_DATA__ECSPI3_SCLK    ← ICM20608 SPI 时钟
MX6UL_PAD_UART2_RTS_B__ECSPI3_MISO      ← ICM20608 SPI 数据输入
MX6UL_PAD_UART2_CTS_B__ECSPI3_MOSI      ← ICM20608 SPI 数据输出
```

原设备树把 UART2 的 TX/RX 注释掉、只留 RTS/CTS，正是这个原因。
所以**本板可用的串口只有 UART1（调试控制台 ttymxc0）**，`ttymxc1` 有节点但不能收发数据。
如果后续要接 RS232/RS485，需要先确认板上的收发器接在哪一路 UART，
并解决与 SPI 的引脚冲突——这一条留作待办，未在文档中作为已完成项。

## ⑪ UART3 串口适配（RS232 / RS485 / GPS）

### 1. 发现的问题

板级资料说明 **RS232（SP3232，经 JP1 跳线 1-3/2-4 接入）、RS485（SP3485，
RE/DE 由 RS485_RX 自动方向控制，无需方向 IO）与 GPS 接口都接到 UART3**。

但设备树里的实际情况是：

| 检查项 | 结果 |
|---|---|
| `&uart3` 节点 | **根本不存在**，UART3 从未被使能 |
| UART3 的数据引脚 | 被 `pinctrl_uart2` 借去当 UART2 的 RTS/CTS |
| 另一个串口 | `/dev/ttymxc1` 是 UART2，而 UART2 的数据引脚早已被 ICM20608 的 ECSPI3 占用 |

也就是说：**这块板真正对外提供的串口（RS232/RS485/GPS）一直是不可用的**，
而一个引脚冲突的 UART2 反倒是使能状态。

### 2. 修复

1. 新增引脚组 `pinctrl_uart3`：`UART3_TX_DATA → UART3_DCE_TX`、`UART3_RX_DATA → UART3_DCE_RX`；
2. 新增并使能 `&uart3`，绑定上述引脚组；
3. 把 `&uart2` 改为 `disabled`，并注明原因（其数据引脚被 SPI 占用，
   且原配置错误地把 UART3 的引脚借给它），把引脚还给 UART3。

> 注意：UART3 的 CTS/RTS 两个引脚在本板另作 FlexCAN1 的 RX/TX，
> 所以 `pinctrl_uart3` 只申请数据引脚 TX/RX，两者不冲突。

### 3. 实测结果

```
$ ls /dev/ttymxc*
/dev/ttymxc0  /dev/ttymxc2        ← UART2(ttymxc1) 消失，UART3(ttymxc2) 出现

dmesg: 21ec000.serial: ttymxc2 at MMIO 0x21ec000 (irq = 231, base_baud = 5000000) is a IMX
/proc/device-tree/.../serial@021ec000/status → okay
/proc/device-tree/.../serial@21e8000/status → disabled
```

控制器回环自测（新增工具 `scripts/uart_loopback.c`，用 `TIOCM_LOOP` 打开
控制器内部 TX→RX 回环）：

```
/dev/ttymxc2: 回环成功 (发送 13 字节, 收到 13 字节: "UART-LOOPBACK")   ← 9600
/dev/ttymxc2: 回环成功 (发送 13 字节, 收到 13 字节: "UART-LOOPBACK")   ← 115200
```

**未验证部分**：内部回环绕过了 SP3232 / SP3485，因此
RS232/RS485 的物理层通信未验证，需要 JP1 跳线 + 回环插头、RS485 对端节点
或 GPS 模块才能完成。这一条不写成已完成项。

### 4. 事故记录：在控制台串口上跑回环测试导致控制台失控

第一次使用回环工具时，我顺手在 `/dev/ttymxc0`（即调试控制台）上也跑了一遍。
工具当时**只在正常路径清除 `TIOCM_LOOP`，异常路径没有清除**，
于是控制台 UART 被留在内部回环状态：

```
控制台输出 → UART 内部回环 → 变成自己的输入 → shell 执行乱码 → 又产生输出 → ……
```

形成自持刷屏循环，串口接收缓冲区被占满，外部发进去的 `reboot` 直接被丢弃，
无法用软件手段恢复，最终需要**物理复位**清除 UART 的 LOOP 位。

**已修复**：`uart_loopback.c` 现在在所有退出路径（含失败分支）都会调用
`clear_loopback()` 清除该位，并在用法说明里明确警告不要在控制台串口上运行。

**修复验证**（复位后在新版工具上复测）：

```
/tmp/uart_loopback /dev/ttymxc2 9600
/dev/ttymxc2: 回环成功 (发送 13 字节, 收到 13 字节: "UART-LOOPBACK")

# 随后向同一端口写入数据，确认回环已被清除（不该收到自己的数据）
echoed_bytes=0        ← 无回显，说明 TIOCM_LOOP 已正确复位
```

同时确认复位后 UART3 的配置依然生效（`/dev/ttymxc0` 与 `/dev/ttymxc2`，
UART2 已消失），说明改动已固化在 eMMC 上的设备树里。

**教训**：

- 涉及"改变设备自身工作模式"的测试（回环、自检、寄存器自改），
  **必须在所有退出路径上恢复现场**，包括异常路径；只覆盖成功路径等于埋雷。
- 执行这类测试前先问一句"如果这一步失败，我怎么退回来"；
  在控制台串口这种"唯一带外通道"上尤其要谨慎——一旦它被自己搞坏，就没有退路了。

## ⑬ USB 鼠标 / 键盘支持（代码完成，待上板验证）

### 1. 先厘清：内核这一层本来就是通的

核查后发现 USB HID 相关配置**早已齐全**，不存在"插上不认"的内核问题：

| 配置 | 状态 |
|---|---|
| `CONFIG_USB_HID` / `CONFIG_HID_GENERIC` / `CONFIG_HIDRAW` | y |
| `CONFIG_INPUT_EVDEV` / `CONFIG_INPUT_MOUSEDEV` | y |
| `CONFIG_INPUT_KEYBOARD` / `CONFIG_INPUT_MOUSE` | y |
| 启动日志 | `usbcore: registered new interface driver usbhid`、`usbhid: USB HID core driver` |

所以插上鼠标键盘，内核会正常枚举并生成 `/dev/input/eventX`。

### 2. 真正的缺口在应用层

`Vehicle-system` 的 `app/main.cpp` 里，`configureQtEnvironment()` **只把 GT9147 触摸屏
告诉了 Qt**，没有加载 `evdevmouse` / `evdevkeyboard` 通用插件。结果：
内核认识鼠标键盘，但 Qt 界面完全不响应——插了也"没效果"。

### 3. 修复

把原来的"只找触摸屏"扩展为按 **evdev 能力位**识别三类设备：

- 触摸屏：设备名为 `gt9147-touchscreen`；
- 鼠标：支持 `REL_X/REL_Y` 或带 `BTN_MOUSE`；
- 键盘：支持 `EV_KEY` 且含字母键。

触摸屏只有 `BTN_TOUCH`、没有字母键和 `BTN_MOUSE`，因此不会被误判。
识别到后写入 `QT_QPA_GENERIC_PLUGINS`：

```cpp
// 找到具体设备就指定路径；一个都没有则退化为让 Qt 自行探测
if (!input.mouse.isEmpty())
    genericPlugins.append(QByteArray("evdevmouse:") + input.mouse);
if (!input.keyboard.isEmpty())
    genericPlugins.append(QByteArray("evdevkeyboard:") + input.keyboard);

qputenv("QT_QPA_GENERIC_PLUGINS", genericPlugins.join(','));
```

退化分支（`evdevmouse,evdevkeyboard` 不带路径）依赖 Qt 插件自身的设备探测，
**支持运行中热插拔**——先启动应用再插鼠标也能识别。

### 4. 顺带修掉的两个问题

**（1）mousedev 坐标基准与屏幕不匹配**

内核默认 `CONFIG_INPUT_MOUSEDEV_SCREEN_X/Y = 1024/768`，而本板 LCD 是 800×480，
会让 `/dev/input/mouseX` 这条传统接口的指针缩放不对。已在 defconfig 中显式设为 800/480。

**（2）应用构建脚本因 locale 而中断（既有 bug）**

`Vehicle-system/scripts/build_app.sh` 里用 `readelf -h | grep -E "Class|Machine"` 做架构校验。
但交叉工具链的 `readelf` 会**跟随系统 locale 输出中文**（"类别/系统架构"），
英文关键字匹配不到 → `grep` 返回 1 → 在 `set -o pipefail` 下直接中断整个构建，
而且失败点在部署之前，**表现为"编译成功但没有部署"**，很容易误判。

修复：脚本开头强制 `export LC_ALL=C`、`export LANG=C`。

> 这是"脚本依赖本地化输出"的典型坑：凡是解析工具输出做判断的地方，
> 都应该固定 `LC_ALL=C`，否则换一台中文环境的机器就复现。

## ⑭ 车载终端应用优化（代码完成，待上板量化）

优化对象：`Vehicle-system`（Qt 5.12.9 应用，约 6000 行 C++）。
本板 CPU 仅 396MHz，因此优先处理**单位时间内被重复计算的像素量**。

### 1. 发现的问题

| 编号 | 问题 | 影响 |
|---|---|---|
| V1 | 摄像头采集线程**对每一帧都做 YUYV→RGB 转换**，而 UVC 摄像头通常以 30fps 交付、界面刷新定时器只有 100ms（10fps） | 约 **2/3 的转换结果无人消费**，纯属浪费 CPU |
| V2 | 渲染路径写成 `QPixmap::fromImage(image).scaled(控件尺寸)` | 先把整幅 640×480 的 RGB888 转成屏幕格式的 QPixmap，**再**缩放；预览控件比原图小、缩略图更小（150×112），等于对用不到的像素白做一次格式转换 |

### 2. 修复

**V1：采集侧按界面消费速度节流**

```cpp
// 只转换真正会被显示的那部分帧；未转换的帧直接重新入队，无额外开销
const qint64 nowMs = frameThrottle.elapsed();
if (nowMs - lastConvertMs >= kMinConvertIntervalMs) {   // 80ms
    lastConvertMs = nowMs;
    ... 转换 + emit frameReady ...
}
```

取 80ms 而非 100ms，是为了略快于界面刷新，保证每次刷新都能拿到较新的帧。

**V2：先缩放、后转格式**（3 处：摄像头预览、倒车预览、倒车缩略图）

```cpp
// 原：QPixmap::fromImage(image).scaled(target, ...)
// 改：QPixmap::fromImage(image.scaled(target, ...))
```

### 3. 顺带排查掉一个潜在冲突

⑧ 给 DHT11 驱动加了 **≥1s 采样间隔**保护，而应用是轮询读取的，
担心会出现"读一次卡 1 秒、拖慢整个轮询循环"。核查后确认**不冲突**：

```
快传感器（AP3216C / ICM20608 / SR04 / SR501）：每 500ms 读一次
DHT11：                                         每 2500ms 读一次
```

DHT11 的读取间隔远高于驱动的 1s 下限，驱动的补足睡眠不会真的触发。

### 4. 待量化（需要调试串口）

应用已重新编译并部署到 NFS rootfs（`usr/local/bin/VehicleSystem`，7.6MB，ARM）。

**已测得的绝对值**（用 `/proc/<pid>/stat` 的 utime+stime 按秒采样，
HZ=100，故 jiffies/秒 ≈ 单核百分比）：

| 场景 | CPU（jiffies/秒） |
|---|---|
| 应用启动阶段 | 24~34 |
| 首页空闲 | 0~7 |
| **打开摄像头预览** | **68~71（约 69%）** |

69% 的单核占用对 640×480@10fps 预览来说偏高，印证了色彩空间转换确实是主要开销。

**对照实验未完成**：为了量化节流到底省了多少，我另外编译了一个
`kMinConvertIntervalMs = 0`（关闭节流）的对照版本并部署测量，
但那一轮没能在采样窗口内打开摄像头页面，因此"优化前"的数字尚未取到。
补测方法：把对照版本放到 `/tmp/nt/VehicleSystem`（保持同名，`pidof` 才能匹配），
启动后打开摄像头页面，按同样方式采样即可对比。

**对照实验结果（重要，与预期相反）**：

| 版本 | 摄像头预览时 CPU（jiffies/秒） |
|---|---|
| 节流版（`kMinConvertIntervalMs = 80`） | 68~71 |
| **关闭节流（`= 0`）** | **70~71** |

两者**没有可测量的差异**，说明 V1 的前提判断错了：
CPU 并不主要消耗在 YUYV→RGB 转换上。最可能的解释是
**该 UVC 摄像头实际交付帧率本就接近界面需要的 10fps**，
节流并没有真正减少转换次数（原本就没有"多转的帧"）。

因此 69% 的 CPU 开销出在别处，按优先级推测：

1. GUI 侧每帧的 `image.scaled()` + `QPixmap::fromImage()` +
   `setPixmap()` 引发的控件重绘，以及 linuxfb 往 /dev/fb0 的位块传输
   （约 600×380×10fps ≈ 230 万像素/秒）；
2. 摄像头驱动侧（UVC 内核解码、DMA 拷贝）本身的占用。

下一步要先用"只采集不显示"与"正常显示"两组对比，把开销定位到
采集侧还是显示侧，再决定优化点（例如降低预览刷新率、缩小预览尺寸，
或让摄像头直接输出更小的分辨率）。**在没有定位清楚之前不再改代码。**

上板后要测的核心指标：**开启摄像头预览时进程的 CPU 占用**，
用 `/proc/<pid>/stat` 的 utime+stime 在固定时间窗内取差（单位 jiffies），
对比优化前后的数值，即可量化 V1 节省的转换开销。

同时确认界面功能未受影响：触摸、鼠标、拍照、倒车预览。

## ⑮ 系统时间、时区与 RTC 修复（已完成，含上板验证）

### 1. 现象

车载终端界面和串口提示里，开发板的时间一直是 1970 年：

```
/ # hwclock
Fri Jan  2 12:51:04 1970  0.000000 seconds
```

而且**板上没有任何现成命令能把时间改过来**——这一点在动手之前必须查清楚，
否则很容易把问题误判成"改一行配置的事"。

### 2. 根因（三层，缺一层都不成立）

| # | 层次 | 具体原因 |
|---|------|----------|
| 1 | 硬件 | 板上没有 RTC 后备电池，SNVS RTC（`20cc000.snvs:snvs-rtc-lp`）从没被写过，初值接近 0 |
| 2 | 内核 | 内核开了 `CONFIG_RTC_HCTOSYS=y`、`CONFIG_RTC_HCTOSYS_DEVICE="rtc0"`，启动时会把 RTC 的值直接当作系统时间——RTC 是 0，系统时间自然就是 1970 |
| 3 | 用户态工具链 | busybox **没有编译 `date` applet**（`date: applet not found`）；板上的 `hwclock` 只支持 `-r/-s/-w/--systz/--localtime/-u/-f`，**不支持 `--set`**。也就是说：既不能改时间，也不能打印时间 |
| 4 | 时区 | rootfs 里**既没有 `/etc/localtime` 也没有 `TZ`**，即使时间对了也会按 UTC 显示，和北京时间差 8 小时 |

### 3. 修复

**① 自研 `settime` 工具**（`scripts/settime.c`，静态编译，2.6MB）：

```
settime --epoch <秒>          用 Unix 时间戳设置并写 RTC（推荐，无时区歧义）
settime --show               打印 epoch / UTC / 本地 / RTC 时间
settime <年> <月> <日> <时> <分> <秒>   按本地时区解释后设置
```

实现要点：

- 设置走 `settimeofday()`，同时用 `ioctl(fd, RTC_SET_TIME)` 写 `/dev/rtc0`，
  **写进 RTC 的必须是 UTC**（内核按 UTC 解释 RTC 寄存器），本地时间由时区数据换算；
- 增加 `--epoch` 入参而不是只接受"年月日时分秒"，是为了让调用方（开发主机）
  直接下发 `date +%s`，**从源头上消除时区/夏令时导致 8 小时偏差的可能**；
- `--show` 是为了补上"板上没有 date 命令"这个洞，否则改完时间无法自查。

**② 补齐时区数据**（NFS 开发 rootfs 与 eMMC 运行 rootfs 都要装）：

```
/etc/localtime   ← tzdata Asia/Shanghai（TZif 格式，573 字节，glibc 默认读取）
/etc/TZ          ← "CST-8"（busybox / 非 glibc 程序用）
/etc/profile     ← 追加 export TZ=CST-8
```

**③ 装进运行环境**：`/usr/bin/settime`。

这里踩了本项目的固定坑：**运行 rootfs 是 eMMC `mmcblk1p2`，NFS 上的改动不会自动同步**，
只改 `deploy/nfs/rootfs` 板上是看不到效果的（第一次验证时 `TZ=未设置`、
`settime: not found` 就是这个原因）。

### 4. 上板验证（实测）

**① 设置时间**，由开发主机下发 `date +%s`：

```
/mnt/nfs/tmp/settime --epoch 1790857950
系统时间已设置: 2026-10-01 12:32:30 UTC (= 本地 2026-10-01 12:32:30)
RTC 已同步  : 2026-10-01 12:32:30 UTC
```

本机 `date -d @1790857950` 为 `2026-10-01 20:32:30 +0800`，
即 UTC 12:32:30 —— 分发与设置**零误差**。

**② 重启后由内核从 RTC 恢复**，启动日志里能直接看到：

```
snvs_rtc 20cc000.snvs:snvs-rtc-lp: setting system clock to
    2026-10-01 12:34:46 UTC (1790858086)
```

这一行就是"不再退回 1970"的直接证据：时间已经落在 RTC 里，内核启动时接管。

**③ 重启后自查**（`uptime` 只有 19 秒，说明是刚启动的新系统）：

```
/ # settime --show
epoch      : 1790858102
UTC        : 2026-10-01 12:35:02
本地       : 2026-10-01 20:35:02  (TZ=CST-8)
RTC(UTC)   : 2026-10-01 12:35:03
/ # hwclock
Thu Oct  1 12:35:03 2026  0.000000 seconds
```

本地时间与北京时间一致，RTC 与系统时间一致（差 1 秒属正常读取间隔）。

**④ 验证时区对普通程序生效**（busybox `ls` 走 glibc `localtime`）：

```
/ # touch /tmp/tzcheck3; ls -l /tmp/tzcheck3
-rw-r--r--    1 root     root             0 Oct  1 20:35 /tmp/tzcheck3
```

修改前同一操作显示的是 `Oct 1 12:32`，说明差 8 小时的问题确实出在时区数据缺失，
而不是时间设置本身。

**⑤ 界面层的直接证据**（`dd if=/dev/fb0` 导出屏幕，800×480×32bpp）：

修复后首页时钟显示 `20:38:46 / 2026年 10月 01日`，与主机时间一致，
见 `docs/images/时间修复后首页时钟.png`。

修复前有更"扎眼"的证据：应用拍照时用 `QDateTime::currentDateTime()` 拼文件名
（`CameraPage.cpp`），NFS rootfs 的 `photo/` 目录里存着一批
`photo_19700101_000322_085.bmp`、`photo_19700101_013448_182.bmp`——
**时间不对会直接污染应用产出的数据资产**，这也说明这条优化不是"界面好看"
而已，而是业务正确性问题。

**⑥ 可复现**：把上面整套动作固化成一个命令
`scripts/set_board_time.sh`（主机算 `date +%s`，串口下发 `settime --epoch`），
实测一次执行即完成设置 + 自查：

```
主机时间 : 2026-10-01 20:36:50 +0800
下发 epoch: 1790858210  (设备 /dev/ttyUSB0)
系统时间已设置: 2026-10-01 12:36:50 UTC (= 本地 2026-10-01 20:36:50)
RTC 已同步  : 2026-10-01 12:36:50 UTC
本地       : 2026-10-01 20:36:50  (TZ=CST-8)
```

### 5. 量化

| 指标 | 修复前 | 修复后 |
|------|--------|--------|
| 系统时间 | 1970-01-02（RTC 初值） | 2026-10-01 20:35 CST（实测） |
| 设置时间的手段 | 无（`date` applet 缺失、`hwclock` 无 `--set`） | 1 条命令 `settime --epoch $(date +%s)` |
| 命令下发到生效耗时 | — | 约 0.13 s（串口回显 3.049s → 结果 3.183s），含 1 次 RTC 写入 |
| 开发者本地时间差 | — | 0 s（下发 epoch 与板端打印 epoch 完全相同） |
| 重启后是否保持 | 退回 1970 | 保持（内核启动日志 + `settime --show` 双重验证） |
| 本地时间与北京时间 | 差 8 小时 | 一致 |

### 6. 口径与局限（写简历时不要含糊）

- 本板**没有 NTP、也没有 4G 授时**，时间来源是开发主机通过串口下发，
  因此"准"的定义是"与开发主机一致"，不是"与标准时间源一致"。
- SNVS RTC 只靠 `VDD_SNVS_IN` 供电，**板上无纽扣电池**：不断电时重启可保持，
  **完全断电后仍会丢时间**，需要重新校时。这是硬件限制，不是软件缺陷。
- 应用（Qt）在启动时由 glibc 缓存时区，**改完 `/etc/localtime` 必须重启应用**才生效，
  本次是重启板卡后重新拉起 `VehicleSystem` 验证的。
- 后续若要彻底免维护，应在 rcS 里加一句"开机从 NTP 校时"（eth0 有网时可用）
  或保留串口下发作为离线兜底。

### 1. 需求

  "退出"/"取消"（Qt 默认按钮文案是英文 Yes/No，和整个中文界面不一致），

### 4. 上板验证（截图）

见 `docs/images/首页退出按钮.png`：退出按钮位于摄像头按钮右侧，红字红边、
圆角与其它控件一致，800×480 下原布局没有被挤变形（其它 6 个入口尺寸不变）。

### 5. 必须记住的踩坑：framebuffer 抓图的 R/B 通道

第一次看截图时"退出"按钮是**蓝色**的，一度以为样式没生效。实际原因是抓图解码：

- 本板 linuxfb 为 800×480 / 32bpp / stride 3200，像素字节序是 **B,G,R,X**；
- 用 Pillow 的 `Image.frombytes('RGBA', …)` 直接读，会把红蓝两个通道对调，
  于是 `#c62828`（红）显示成 `#2828C6`（蓝）；
- 判据很简单：温度标签源码里是 `#e87532`（橙），截图里若量到
  `(50,117,232)` 就说明通道被对调了（`(50,117,232)` 正好是 `(232,117,50)` 的交换）。

为此补了 `scripts/fb_raw2png.py`，统一按本板字节序做一次 R/B 交换再存 PNG，
以后所有界面截图都用它转换，避免再被"假配色"误导。

**按钮显示**已经上板验证；**点击 → 确认框 → 退出**这条链路需要手指在触摸屏上
真实点一次。本板内核 `CONFIG_INPUT_UINPUT` 未开启，无法注入合成输入事件自动
验证，因此这一步交给实际操作确认（若确认框里点"退出"后程序正常回到控制台，

## ⑱ 视频播放卡顿：真凶是触摸屏中断风暴（已完成，含修复前后实测）

### 1. 现象

车载应用播放视频时明显卡顿：mplayer 打印
`**** Your system is too SLOW to play this! ****`，状态行里音画偏差（A-V）越拉越大。

### 2. 排查过程（逐层排除，而不是猜）

| 步骤 | 做法 | 结果 |
|------|------|------|
| 看片源 | `ffprobe` 逐个文件 | 应用默认播放的 `/video/test.avi`：H.264 **Main L3.1 800×600@25fps 2.1Mbps** + MP3 128k |
| 测纯解码 | `mplayer -benchmark -nosound -vo null` | 800×600 解 5 秒要 **8.33s CPU（1.66 倍实时）** → 单核根本解不动；520×330 只要 1.82s（36%） |
| 测输出 | 同一片源换 `-vo null / -vo fbdev2 / 加不加 -zoom` | 差异只有 0.5~1.2s，不是主因 |
| 测音频 | `-ao null / -srate 48000 / 不指定` | `-srate 48000` 会让 ALSA 跑到 88200Hz 多一次重采样，影响约 1.8s，但不是根因 |
| **看"谁在吃 CPU"** | `top -b -n 1` | **`[irq/38-gt9147]` 占 22.5%~28.5% CPU**，系统态 CPU 高达 **69%** |
| **量中断频率** | `/proc/interrupts` 前后取差 | 空闲时 **10 秒 14785 次 ≈ 1480 次/秒**，且类型是 **Level** |
| **量引脚电平** | `devmem 0x0209C008` 读 GPIO1_PSR | bit9（GPIO1_IO09 = 触摸 INT）**常态为 1（高）** |
| 看驱动 | `gt9147.c` | `irq_type = config_data[6] & 0x03` 从芯片配置寄存器读出 **3**，驱动表映射成 `IRQF_TRIGGER_HIGH` |

### 3. 根因

触摸芯片的 INT 引脚是**低有效**（空闲为高、有触摸数据时拉低），但驱动按芯片配置寄存器里的
"3 = 高电平触发"申请了 `IRQF_TRIGGER_HIGH`。于是**电平触发条件在空闲时恒成立**：

- 中断以 ~1480 次/秒持续触发（`/proc/interrupts` 类型显示 Level）
- 中断线程每次都去读一次状态寄存器（I2C，约 0.2ms），发现"无数据"就 `return IRQ_HANDLED`——
  **既没清中断标志也没释放中断线**，下一次电平立即再次触发，形成自激
- 光这一条中断线程就吃掉 **22%~28% CPU**，系统态 30%，视频软解自然被饿死

### 4. 修复（`drivers/smarthome/gt9147.c`）

1. 中断触发方式**固定为下降沿**，不再采信芯片配置寄存器里的电平值：
   `irq_flags = IRQF_TRIGGER_FALLING | IRQF_ONESHOT;`
2. 顺带修掉一个隐患：中断线程里"状态寄存器 bit7=0（假中断）"的分支原来直接 return，
   现在改成 `goto clear_status`，**任何分支都会写 0 清状态**。
3. 删除因此不再使用的 `gt9147_irq_flags[]` 映射表。

### 5. 修复前后实测（同一块板、同一片源 520×330 Baseline 670kbps）

| 指标 | 修复前 | 修复后 |
|------|--------|--------|
| 空闲 10s 中断数（IRQ 38） | 14785 次 | **0 次** |
| 中断类型 | Level | **Edge** |
| `irq/38-gt9147` CPU | 22.5%~28.5% | **消失（top 里已无该线程）** |
| 空闲系统 CPU | 30%（sys）/ 70% idle | **9%（sys）/ 91% idle** |
| loadavg（空闲） | 1.43 | **0.00** |
| 播放 A-V 偏差 | **1.82s** | **0.000s** |
| 丢帧数 | 59 | **0 / 1** |
| mplayer too SLOW | 出现 | **不再出现** |
| 播放时系统 CPU | 88.5% | 63% |

**触摸功能回归验证**（改了中断触发方式必须复验）：

| 动作 | IRQ 38 计数 | 结论 |
|------|------------|------|
| 修复后空闲 | 6（开机累计） | 不再自激 |
| 在触摸屏上滑动 | **6 → 3343** | 触摸正常产生中断，功能未受影响 |
| 滑动后空闲 10 秒 | **+0 次** | 边沿触发不会自激 |
| 输入设备 | `gt9147-touchscreen`（/dev/input/event2） | 注册正常 |

### 6. 顺带查清的两件事

- 应用默认播放的 `/video/test.avi` **根本没在播**：mplayer 打印
  `Requested audio codec family [mpg123] (afm=mpg123) not available.`
  —— 本板 mplayer 编译时没带 MP3 解码器，而该文件音频是 MP3。
  即使补上解码器，800×600 H.264 也需要 166% 单核，仍然放不动。
- 已用 ffmpeg 生成一个"板子友好"的片源做对照：
  `520×330 / Constrained Baseline L3.0 / 670kbps / AAC 96k / 25fps`（`/video/demo_520x330.mp4`），
  在修复后的内核上 **A-V = 0.000s、零丢帧**。

### 7. 这条经验值得记进简历

**"播放卡顿"最终不是播放器的问题，而是触摸屏驱动的一个中断触发方式配错**：
用 `/proc/interrupts` 的中断计数 + `devmem` 读引脚电平 + `top` 看 `irq/*` 线程，
三步就把 22%~28% 的隐性 CPU 开销定位并回收了。

## ⑲ 车载应用"点播放没反应/报没有文件"：mplayer 路径写死（已修复）

### 1. 现象

在视频页点播放，界面右侧状态栏显示：

```
MPlayer错误：execve: No such file or directory
```

（截图见排查记录；界面同时显示"请选择视频"，容易被误读成"文件不存在"。）

### 2. 根因

应用里把播放器路径**写死**成 `/usr/bin/mplayer`，但两个 rootfs 的布局不一样：

| rootfs | mplayer 位置 | 结果 |
|--------|--------------|------|
| NFS 开发 rootfs（`deploy/nfs/rootfs`） | `/usr/bin/mplayer` | 能用 |
| **eMMC 运行 rootfs（板子实际跑的）** | **`/bin/mplayer`** | **`/usr/bin/mplayer` 不存在 → execve 失败** |

`QProcess::errorOccurred` 收到 `execve: No such file or directory` 后，
`MPlayerVideoPlayer` 把它包装成"MPlayer错误：…"显示在状态栏——**报的不是视频文件不存在，而是播放器程序没找到**。

这正是本项目反复强调的那条坑：**NFS 上的改动/布局不会自动同步到 eMMC**，
凡是"写死路径"的地方都必须在真实运行环境上验证。

### 3. 修复

`MPlayerVideoPlayer` / `MPlayerAudioPlayer` 都改成运行时探测（音视频两个播放器一起改，症状相同）：

```cpp
static QString resolveMPlayerPath()
{
    const QStringList candidates = {
        QStringLiteral("/usr/bin/mplayer"),
        QStringLiteral("/bin/mplayer"),
        QStringLiteral("/usr/local/bin/mplayer"),
    };
    for (const QString &path : candidates) {
        const QFileInfo info(path);
        if (info.exists() && info.isExecutable())
            return path;
    }
    const QString fromPath = QStandardPaths::findExecutable("mplayer");
    return fromPath.isEmpty() ? QStringLiteral("/usr/bin/mplayer") : fromPath;
}
```

### 4. 验证

用自动巡检进入音乐页/视频页，触发播放器构造，日志里打出实际选中的路径：

```
[VS  9410ms] 音乐播放器 mplayer 路径: /bin/mplayer
[VS 15410ms] 视频播放器 mplayer 路径: /bin/mplayer
```

两个播放器都正确落到 eMMC 上真实存在的 `/bin/mplayer`。

### 5. 顺带结论

`/video/test.avi` 即使路径修好了也放不出来：本板 mplayer 编译时**没有 MP3 解码器**
（日志：`Requested audio codec family [mpg123] (afm=mpg123) not available`）。
演示请用 `520×330 / Baseline / AAC` 的片源（例如 `/video/demo_520x330.mp4`），
转码参数见 ⑱ 节。

网络接口与内核特性（实测）：

| 项目 | 实测值 |
|---|---|
| 接口 | eth0、eth1、lo、sit0 |
| eth0 链路 | 100Mbps / Full / carrier=1 |
| eth0 PHY ID | `0x001cc816` |
| eth0 PHY 驱动 | RTL8201F 10/100 Ethernet |

### 约束与注意事项

- 本板内核从 **eMMC FAT 分区** 加载（`fatload mmc 1:1 ...`），不是从 TFTP；
  U-Boot 环境变量保存在 eMMC。
- 当前 U-Boot 启动参数（⑦ 之后）：
  `console=tty0 console=ttymxc0,115200n8 root=/dev/mmcblk1p2 rootwait rw ipv6.disable=1`；
  根文件系统为 eMMC `mmcblk1p2`（ext3），网络由根文件系统里的 rcS 在后台配置。
- U-Boot `bootdelay=1` 后，串口打断 autoboot 的窗口只有约 1 秒，
  需用定时重复发送的方式抢占（`serial_console.py --spam`）。
- 板端 getty 处于 “Please press Enter to activate this console” 时，
  直接发送的命令会被 getty 吞掉，需先发一个回车激活控制台。
