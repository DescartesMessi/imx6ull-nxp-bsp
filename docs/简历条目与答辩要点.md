## 条目一：i.MX6ULL 开发板 BSP 开发与设备驱动开发（2026/05 -- 2026/10）

> 基于 i.MX6ULL 开发板搭建嵌入式 Linux 基础软件平台，围绕
> U-Boot → Linux Kernel/Device Tree → BusyBox/eMMC Rootfs 完成完整启动链路与
> 交叉编译体系建设，并完善板载设备驱动。
>
> **技术栈**：C、Linux Kernel、U-Boot、Device Tree、I2C、SPI、GPIO、CAN、BusyBox

• **启动链路与根文件系统**：完成 U-Boot → 内核/DTB → 根文件系统（BusyBox + eMMC ext3）的完整启动链路搭建与调试，整机启动时间（U-Boot banner → 控制台就绪）**12.34s → 5.05s，缩短 59.1%**。

• **设备树**：维护 **973 行**板级设备树、**39 个 pinctrl 引脚组**，
完成 LCD、触摸、双网口、CAN、UART、USB、传感器等节点的引脚复用与外设资源描述，
启动告警 **3 条 → 0 条**。

• **有线网络**：双网口（内部双 MAC + 外部 PHY + 内置变压器 RJ45）全部可用，
PHY 绑定 RTL8201F，**TCP 吞吐 91.7 Mbps（线速的 91.8%）**，
两网口 MAC 地址不再冲突。

• **显示与输入**：完成 **800×480 LCD**（framebuffer `/dev/fb0`、32bpp、
单帧 1.5MB、面板时序 800×480p-60）与 **GT9147 五点电容触摸**
（I2C 100kHz + 下降沿中断驱动上报、Linux input 子系统、坐标 800×480 映射）适配，
触摸空闲时中断频率 0 次/秒、滑动时按中断实时上报。

• **板级驱动**：完成 **8 个板载驱动**（触摸、温湿度、六轴、光照/距离、
超声测距、人体检测、蜂鸣器、背光按键）的开发与调试，统一通过
open/read/write/ioctl 与 Linux input 子系统向用户态提供接口。实测能力：
六轴 ICM20608 经 **SPI 8MHz** 一次读取三轴加速度+角速度+温度共 7 通道，
**9280 次/秒（0.1ms/次）**；超声测距 SR04 **49.7ms/次（最高 20 次/秒）**；
温湿度 DHT11 受单总线协议约束 **1 次/秒**，单次读取 29.3ms；
人体检测 SR501 采用**双边沿中断 + 等待队列事件驱动**，无需轮询即可上报状态；
AP3216C 经 **I2C 100kHz** 读取光照/距离/红外三通道。

• **性能问题定位**：定位并修复触摸驱动中断风暴，
**中断频率 1480 次/秒 → 0、中断线程 CPU 22~28% → 0、空闲系统 CPU 30% → 9%**；
连带把视频播放指标从 **音画偏差 1.82s → 0.000s、丢帧 59 → 0**。

• **总线与外设**：**can0 500kbps 回环收发 0 错误**（RS232/RS485/GPS 共用的 UART3
补齐后 **/dev/ttymxc2 回环 9600/115200 全部通过**）；
USB 转串口/网卡/4G、USB HUB 与 gadget 全部就绪，**启动报错清零**，
鼠标键盘热插拔即可识别。

• **系统时间与工具链**：完成系统时间/RTC/时区配置（**1970 → 当前时间，
重启后由 RTC 保持，界面与文件时间零偏差**）；建立 ARM 交叉编译体系
（**11 个构建脚本严格模式 7/11 → 11/11**），完成 Qt 5.12.9、ALSA-lib、
libjpeg-turbo、mjpg-streamer、mplayer 等第三方库的交叉编译与 sysroot 部署。

• **调试与量化工具**：自研串口抓取、驱动采样率、传感器阻塞时长、摄像头能力枚举、
framebuffer 截屏、指标巡检等 6 个工具，形成可复现的量化流程。

## 条目二：基于 i.MX6ULL 的智能车载系统（2026/07 -- 2026/10）

> 基于 i.MX6ULL BSP 构建的 Qt 智能车载应用系统。采用"页面层 + 服务层 +
> Linux 设备接口"的分层架构，实现从底层硬件驱动、实时数据采集到车载人机交互
> 和远程视频服务的完整嵌入式应用。
>
> **技术栈**：C++、Qt 5.12.9、V4L2、MPlayer、MJPG-streamer、HTTP、LinuxFB

• **界面框架**：基于 Qt 5.12.9 构建 800×480 LinuxFB 触摸界面，
**7 个功能页**（首页、音乐、视频、板载设备、摄像头、倒车影像、哨兵监控；
页面层 3224 行 + 服务层 2381 行、**116 处信号槽、51 个自定义信号**），
页面切换 **3~16ms**；**应用启动 8.16s → 4.98s（-39%）、体积 7.98MB → 0.55MB（-93%）、
首页常驻内存 70MB → 28MB（-60%）**。

• **首页与板载设备页**：首页集成系统时间、温湿度显示与 7 个功能入口；
板载设备页实时展示 **DHT11 温湿度、AP3216C 光照/距离、ICM20608 六轴、
SR04 测距、SR501 人体检测、蜂鸣器控制**；
实测 **首页空闲 CPU 0.5~4%，板载设备页 CPU 11~17%、内存 +8.7MB**。

• **音乐与视频播放页**：基于 MPlayer 实现音乐（FLAC/WAV）与视频播放，
含播放列表、播放/暂停、进度与音量控制；实测 **音乐播放 CPU 约 3%（单核）**，
视频在 520×330/Baseline 规格下 **音画偏差 0.000s、零丢帧**
（对照：1080p/800×600 H.264 需 166% 单核，实测卡顿，已给出片源规格约束）。

• **摄像头页**：完成 **9 个 ioctl** 的标准 V4L2 采集流程，支持 YUYV→RGB 与 MJPEG 解码，
实时预览 + 一键拍照（640×480 BMP，**0.88MB/张**，文件名带时间戳）；
实测驱动交付 **21.5~21.8fps**、转换 **~11fps**、上屏 **8.6~9.7fps**、
预览 CPU **54~62%**，并通过能力枚举查明请求分辨率不被硬件支持（实际 1280×720/640×480）。

• **倒车影像页**：SR04 超声测距 + 摄像头实时画面 + 蜂鸣器报警联动，
带距离显示与倒车抓拍（JPG，质量 85）；实测**带摄像头时该页 CPU 56%**（无摄像头 4.5%）。

• **哨兵监控（远程视频）**：SR501 人体检测触发 MJPG-streamer 推流，
局域网客户端可直接拉流查看：**触发到推流启动 32~101ms**、
**推流 25.0fps / 22.5Mbps**、**推流进程仅占 5% 单核**，无人 10s 自动停流；
并修掉残留进程占用端口导致推流启动失败的问题。

• **输入支持与分层架构**：触摸（event2）、USB 鼠标（event4）、键盘（event5）
按 evdev 能力位自动识别，热插拔即用；**6 个服务模块**封装
**8 个设备接口**（video1 / ap3216c / dht11 / icm20608 / sr04 / sr501 /
beep_device / fb0），页面层不承担设备管理，并提供界面化退出入口。

## 高频追问与回答

**Q1：启动时间怎么量的？为什么不是 5 秒就是极限？**
用自研串口抓取工具给每行日志打时间戳，口径是"U-Boot banner → 控制台就绪"，不含 bootdelay。
三段收益：bootdelay 3→1 与 bootcmd 修正（-1.99s）、根文件系统 NFS→eMMC（-4.49s）、
probe 时序精简（-0.56s）。再往下压要动内核裁剪和启动脚本并行化，属于新课题，
我不会说"已经到极限"。

**Q2：为什么换 eMMC 根文件系统能省 4.5 秒？**
NFS 根文件系统要在启动时挂载并首次访问大量文件，网络往返把每个 open 都放大了；
换成本地 ext3 后，又把 eth0 配置移到 rcS 里后台执行，不再阻塞用户态启动。

**Q3：应用启动 8.16s，其中 2.5s 是什么？为什么不去掉？**
是 Qt 5.12.9 在本板上**首次创建"带图标的按钮"**的一次性开销。我用 4 组对照实验排除其他可能：
移走 20MB 中文字体只快 135ms（且会丢中文）；首按钮用矢量标准图标 2503ms、用资源 PNG 2530ms、
用文件图标 2530ms（与图片来源、图标主题查找无关）；先创建带样式表的 QLabel 再创建按钮，
QLabel 只 211ms（不是 QSS 首次初始化）；QPushButton 2470ms、QToolButton 2503ms（与控件类型无关）。
第一个按钮 2.5s、之后每个 7~25ms，所以启动下限 ≈ QApplication 1.44s + 首次按钮 2.5s ≈ 3.9s。

**Q4：70MB→28MB 内存怎么降下来的？**
首页 6 个入口图标原来是 1254×1254 的 PNG（每张 1.1~1.4MB），Qt 会把渲染用的位图留在图标缓存里：
6 × 1254² × 4B ≈ 37MB，正好对应实测 41MB 的差值；改成 172×172 后缓存位图约 0.7MB。
同一次改动还让体积小 93%、启动快 39%。

**Q5：摄像头丢帧 20~28%，算合格吗？**
不算，这是我列出的待改进项。根因已查明：代码按 320×240 请求，但这颗摄像头只支持
1280×720/640×480，驱动把请求调整成 640×480，每帧像素量是预期的 4 倍。
可选方向：改用 MJPEG、按枚举结果选最小可用尺寸、或引入硬件缩放（PxP）。
我没有把它写成"流畅"，因为实测数据不支持。

**Q6：你那个"按帧率节流"的优化为什么无效？**
我原以为 CPU 主要花在 YUYV→RGB 转换上，于是把转换限制到 80ms 一次。
对照实验（节流 68~71 vs 关闭节流 70~71 jiffies/秒）证明无收益，
说明摄像头交付帧率本就接近界面需要的 10fps。这条负结果的价值是：
**优化前先用数据验证假设，而不是先写代码**。

**Q7：中断风暴怎么发现的？**
① `top -b -n 1` 发现 `[irq/38-gt9147]` 常驻 22~28% CPU；
② `/proc/interrupts` 显示该中断 10 秒触发 14785 次且类型是 Level（应为 Edge）；
③ `devmem 0x0209C008` 读 GPIO1_PSR，发现 INT（GPIO1_IO09）常态为高，
说明它是低有效，而驱动按芯片配置寄存器里的"3=高电平触发"申请中断，电平条件恒成立 → 自激。
修复后空闲中断 0 次/10s、空闲 CPU 30%→9%、视频音画偏差 1.82s→0.000s、触摸回归正常。

**Q8：双网口那个 MDIO 问题具体是什么？**
两个 MAC 共用一对 MDIO/MDC（GPIO1_IO06/07）。设备树里我把 MDIO 总线挂在 ENET1 下，
而 ENET2 也要访问 PHY，结果 ENET2 拿不到总线。改成由 ENET2 持有 MDIO 节点、
ENET1 通过 phandle 引用，第二个网口才真正可用。

**Q9：91.7Mbps 怎么测的？为什么不是 100Mbps？**
iperf3 在板子与主机之间跑双向 TCP。91.7Mbps 是线速的 91.8%：以太网有效载荷要扣掉帧头、
IP/TCP 头与 ACK 等开销，100M 口跑 TCP 的实际上限通常在 94~95Mbps，这个数字已接近上限。

**Q10：采样间隔为什么放在驱动里而不是应用里？**
约束来自器件协议（DHT11 ≥1s、SR04 ≥60ms），任何应用都可能违规调用；
放驱动里对所有调用者统一生效，而且能把"驱动是否真实现了约束"变成可测指标——
我用自研 `drv_rate` 量修复前后每秒成功采样次数（DHT11 18→1.1 次/秒）。

**Q11：为什么自己写 settime 工具？**
板上 busybox 没编译 `date` applet，`hwclock` 也不支持 `--set`，既不能改时间也不能打印时间。
我写了静态编译的 `settime`（`--epoch` 用主机下发的 Unix 时间戳、`--show` 打印 UTC/本地/RTC），
并补了 `/etc/localtime` 与 `TZ=CST-8`；重启后内核日志能看到
`snvs_rtc ...: setting system clock to 2026-10-01 12:34:46 UTC`。
局限：板上没有 RTC 后备电池，完全断电后仍会丢时间。

**Q12：你怎么证明这些数字不是编的？**
每条都有可复现路径：`scripts/serial_console.py` 带时间戳抓日志；
`scripts/drv_rate.c` 量驱动采样率；`scripts/sensor_lat.c` 量单次 ioctl 阻塞；
`scripts/v4l2_enum.c` 枚举摄像头能力；应用内 `VS_METRICS=1` 每 2 秒输出一条
`METRIC page/rss/threads/cpu`，`VS_AUTOPILOT` 自动巡检 7 个页面；
`scripts/vs_metrics_run.sh` 一键部署+巡检+回收日志。对照组都是同板同场景。

**Q13：最有价值的一次排查是哪个？**
视频播放卡顿。表面是播放器问题，实际是触摸驱动中断触发方式配错：
`top` 看 irq 线程、`/proc/interrupts` 数中断、`devmem` 读引脚电平三步定位，
回收了 22~28% 的隐性 CPU 开销。这类"症状在 A、根因在 B"的问题更能体现调试方法。

**Q14：为什么不把没验证的东西写成已完成？**
因为踩过：CAN 和 UART3 都曾"设备树里有、看起来能用"，实际控制器没使能；
RS232/RS485/GPS 物理层至今需要跳线和回环插头验证，我在文档里标成
"控制器已验证、物理层待验证"。面试被追问反而加分。

## 写作红线（别踩）

1. **不写没有数据的形容词**：如"高帧率""非常流畅""零延迟"，要写就写 fps/ms/Mbps。
2. **不把已知缺陷写成成绩**：摄像头丢帧 20~28% 要写成"定位到根因 + 优化方向"。
3. **`/video/test.avi` 不能写"可播放"**：本板 mplayer 没编译 MP3 解码器，
   演示用 520×330/Baseline/AAC 的片源。
4. **CAN 实总线、RS232/RS485/GPS 物理层、4G 联网**都只做到控制器/驱动层，别写"已通信成功"。
5. **时间/RTC 要带限制条件**：无后备电池，断电后需重新校时（NTP 或串口下发）。
6. **帧率/CPU 必须带场景**：同一页面"空闲"和"播放中"能差一个数量级。
