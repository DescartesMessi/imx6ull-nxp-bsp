## Q1. 你了解 PHY 吗？有线网络是如何进行配合工作的？

### 1. PHY 是什么

PHY（Physical Layer transceiver，物理层收发器）是网卡里负责 OSI 第一层的那颗芯片，
和 MAC（本板是 SoC 内部的 FEC 控制器）一起构成一个完整的以太网口。
分工可以概括为：

- **MAC 管"帧"**：成帧/解帧、CRC、地址过滤、DMA 收发环、中断/NAPI，
  以及硬件校验和、VLAN offload 等。本板对应 `fec_main.c`（`imx6ul-fec`）。
- **PHY 管"线上的电平"**：把 MAC 的并行数字信号做线编码后驱动到双绞线上，
  再把收到的模拟信号恢复成数字信号。具体包括 4B/5B 编码、MLT-3、
  并串/串并转换、时钟恢复（CDR）、发送电平与驱动能力、以及
  经隔离变压器与 RJ45 对接。
- **PHY 还负责"链路管理"**：上电复位、自协商（速率 10/100、双工、
  流控）、链路状态与远端故障检测、以及通过管理接口向 MAC/内核汇报速率与双工。

### 2. MAC 与 PHY 之间的两类接口

一类是**数据接口**，决定数据怎么过：

| 接口 | 位宽/时钟 | 适用 |
|---|---|---|
| MII | 4bit / 25MHz(100M) | 10/100 |
| **RMII** | **2bit / 50MHz 参考时钟** | **10/100，本板用的就是它** |
| GMII / RGMII | 8bit / 4bit，125MHz | 千兆 |

本板 `&fec1`、`&fec2` 在设备树里都是 `phy-mode = "rmii"`，是引脚最省的 100M 方案，
代价是 MAC 侧需要 50MHz 参考时钟（本板由 `ENET1_REF_CLK1`，即 ALT4 复用提供）。

另一类是**管理接口 MDIO/MDC**，决定怎么"对话"：

- MDC 是时钟，MDIO 是双向数据，组成一条 802.3 clause 22 管理总线，
  一个 MDC/MDIO 上可挂最多 32 个 PHY，每个 PHY 有一个地址（0~31）。
- 内核通过它读写 PHY 标准寄存器：`BMCR(0x00)` 控制自协商/复位，
  `BMSR(0x01)` 链路状态，`PHYIDR1/2(0x02/0x03)` 芯片 ID，
  `ANAR/ANLPAR(0x04/0x05)` 自协商能力与对端能力等。
- 本板实测 PHY ID = `0x001cc816`，MDIO 地址 = 1
  （`cat /sys/bus/mdio_bus/devices/*/phy_id`）。

### 3. 上电到收发包的完整配合流程

1. **上电与复位**：设备树用 `phy-reset-gpios = <&gpio5 7 ...>`（ENET1，
   ENET2 是 gpio5 8）、`phy-reset-duration = <200>` 先给 PHY 一个可靠的硬复位。
2. **引脚复用**：`pinctrl` 把 RMII 数据线和 MDIO/MDC 配到 ENET 的 ALT 功能。
   这一步在排查时最容易被忽略——本板 MDIO/MDC（GPIO1_IO06/07）实际被
   ENET2 的 pinctrl 组占用，所以 MDIO 总线只注册了一条，两个 PHY 的
   描述都放在 `&fec2` 的 `mdio` 子节点下（见 dts 中的注释）。
3. **注册 MDIO 总线并扫描 PHY**：FEC 驱动注册 `mii_bus` 后，
   `libphy` 逐个地址读 ID 寄存器（"在线扫描"），确认哪些地址上有 PHY。
4. **驱动匹配与绑定**：内核用读到的 PHY ID 和 `phy_id`/`phy_id_mask`
   去匹配 `phy_driver`。匹配不上就退化成 `Generic PHY` 驱动——
   这本身能工作，但等于把芯片当"哑器件"用，拿不到任何厂商专属配置的挂载点。
5. **建立链路（自协商）**：`phy_connect` 后驱动打开自协商，
   双方交换能力并各自选出最高公共速率；本板 100M 链路上这一步约需 3.0s，
   是 100BASE-TX 自协商的固有时间，不是 BSP 的问题。
6. **状态机与状态上报**：`phy_state_machine` 持续跟踪链路。
   本板 PHY 的中断线没接（`irq=-1`），所以走**轮询**方式；
   链路 up 后把 `speed=100`、`duplex=full` 通知 MAC，
   MAC 据此配置 RMII 侧的速率/双工，netdev 进入 `carrier=1`。
7. **数据面工作**：之后 MAC 用 DMA 收发环收发，走 NAPI 收包中断合并，
   硬件校验和与 VLAN 卸载在 `fec_main.c` 中对 `imx6ul-fec` 已使能，
   不需要软件再补。PHY 只做"线上的第一层"。
8. **应用层落地**：本板 `eth0` 承载 NFS 根文件系统
   （`nfsroot=192.168.31.218:.../rootfs,v3,tcp,nolock`），
   所以网口一断，整机直接不可用——这也是我把有线网口作为重点外设单独排查的原因。

### 4. 我在这个项目里针对 PHY 做的事

排查发现四类问题，其中两类已修复：

- **P1** 原 defconfig 里 `# CONFIG_REALTEK_PHY is not set`，
  PHY 只能绑定通用驱动（日志 `PHY driver [Generic PHY]`）。
- **P2** 即使编上 realtek 驱动，`realtek.c` 里也**没有本板 PHY 的 ID**
  （原来只有 8201CP / 8211B / 8211E 三条），仍然匹配不到。

修复：

1. `arch/arm/configs/imx6ull_alientek_jjl_defconfig` 增加 `CONFIG_REALTEK_PHY=y`；
2. `drivers/net/phy/realtek.c` 的 `realtek_drvs[]` 与 `realtek_tbl[]` 中
   增加 RTL8201F 条目（`phy_id = 0x001cc816`，`phy_id_mask = 0x001fffff`），
   回调复用 `genphy_config_aneg` / `genphy_read_status`。

这里**有意**复用 genphy 回调：本板 PHY 中断线未接，基础速率/双工行为
与通用实现一致，这次改动的价值是"绑定到正确的 PHY 驱动、拿到后续做
RMII 时序与电源管理等芯片专属配置的挂载点"，而不是改变链路行为。

效果验证（同一块板、同一条网线，只换内核）：

```
优化前：FEC PHY driver [Generic PHY]
优化后：FEC PHY driver [RTL8201F 10/100 Ethernet]
```

吞吐实测：板端 `dd` 发 100MiB，主机 `nc` 接收，耗时 9.143s，
**吞吐 91.7Mbps，达 100M 线速的 91.8%**，已经贴近 100Base-TX 上
TCP 的实际上限（协议开销约 5~8%），说明 MAC+PHY 通路正常，
吞吐侧没有剩余优化空间。

剩余待产品决策项（我记录了但没擅自改）：`eth1` 无 PHY 不可用是否关闭 `&fec2`、
关闭后要把 ENET1 的 MDIO/MDC 补进 `enet1grp` 使配置自洽、
eth0/eth1 MAC 地址重复需分配唯一 MAC、以及 `phy-supply` 缺失
（当前走 dummy regulator）。eth1 关系到"板上到底有没有第二个可用网口"，
没有原理图确认前不动，避免误删仍需要的功能。

### 5. 一句话总结

PHY 是网口的物理层器件，负责线编码/时钟恢复/自协商与链路状态；
MAC（FEC）与 PHY 通过 RMII 走数据、通过 MDIO/MDC 走管理。
内核侧的配合链条是"复位 → 引脚复用 → MDIO 注册 → 扫描并读 PHY ID →
匹配并绑定驱动 → 自协商建立链路 → 上报速率双工 → MAC 收发帧"。
本项目在这条链上定位到"驱动缺失 + PHY ID 缺失"两处缺陷并修复，
绑定从 Generic PHY 变为 RTL8201F，实测 91.7Mbps，排查过程有寄存器级证据。

## Q2. 了解中断吗？你在项目中使用中断了吗？中断是怎么处理的？

### 1. 对中断的理解（概念层）

中断是外设主动打断 CPU 当前执行的机制，本质是"事件驱动"代替"轮询"：
有事件才来，CPU 不用空转等待。要区分三个层次：

- **硬件层**：外设拉高中断线 → 中断控制器（本板是 Cortex-A7 的 GIC，
  设备树里 `intc: interrupt-controller@00a01000`，`compatible = "arm,cortex-a7-gic"`，
  `#interrupt-cells = <3>`）按优先级和屏蔽位选出一路，通知 CPU 核。
- **内核层**：内核保存现场、跳到中断入口（ARM 的 IRQ 向量），
  由通用中断框架（`irq_desc`、`irq_chip`、`irq_domain`）完成 mask/ack，
  再调具体驱动注册的 handler。
- **驱动层**：驱动用 `request_irq` / `request_threaded_irq` 注册 handler，
  在 handler 里尽快处理掉硬件状态并返回 `IRQ_HANDLED`。

几个必须说清的边界：

- **中断上下文不能睡眠**：不能用 `mutex_lock`、`msleep`、
  `copy_to_user`、以及会睡眠的 I2C/SPI 传输。所以项目里凡是"中断里要读 I2C"
  的场景，一律用中断线程化。
- **上下半部划分**：上半部（hardirq）只做时间敏感、必须抢占的活
  —— 读寄存器清中断、抓时间戳、标记状态；能延后的一律下放：
  tasklet/软中断、workqueue，或者中断线程。
- **并发保护要区分场景**：中断和进程之间抢的共享数据用
  `spin_lock_irqsave`；可能休眠的临界区用 `mutex`；
  只做单值标志可以用 `READ_ONCE/WRITE_ONCE`。
- **触发类型必须和硬件一致**：边沿（rising/falling）还是电平（low/high）。
  配错会丢中断，或者电平触发没清状态导致中断风暴。

### 2. 项目里实际用了哪些中断（有代码、有 IRQ 号）

| 驱动 | 硬件 | 注册方式 | IRQ | 处理策略 |
|---|---|---|---|---|
| GT9147 触摸 | GPIO1_IO09，dts 里 `interrupts = <9 2>`（下降沿） | `devm_request_threaded_irq`，硬中断传 NULL，`IRQF_ONESHOT` | 39 | 线程化，因为要读 I2C |
| back 按键 | GPIO1_IO18，`GPIO_ACTIVE_LOW` | `devm_request_irq`，`RISING \| FALLING` | 48 | 上半部定时器消抖 + workqueue 上报 |
| SR04 超声波 | ECHO = GPIO4_IO20，双边沿 | `devm_request_irq`，双边沿 | 152 | 上半部抓时间戳 + completion 唤醒进程 |
| SR501 人体红外 | GPIO5_IO02 | `devm_request_irq` | 168 | 上半部延迟工作消抖 + waitqueue/poll 上报 |

- FEC 网卡走的是 NAPI（中断 + 软中断轮询），不是纯中断。
- PHY 是**反例**：本板 PHY 中断线没接（`irq=-1`），
  所以 `phy_state_machine` 用轮询跟踪链路，照样能正常工作 91.7Mbps。

顺便说明，中断号不是随便写的数字：GPIO 控制器本身是二级中断控制器
（`gpio1`~`gpio5` 都带 `interrupt-controller; #interrupt-cells = <2>`，
各 bank 用 `<GIC_SPI n IRQ_TYPE_LEVEL_HIGH>` 连到 GIC）；
驱动里 `gpiod_to_irq()` 拿到的是 gpiolib 通过 `irq_domain` 映射出来的
虚拟中断号（virq），这就是为什么按键打印出来是 48、
SR04 是 152、SR501 是 168。

### 3. 四种典型处理模型（对应项目里的四份代码）

**① GT9147：中断线程化，因为 handler 里必须做 I2C**

```c
irq_flags = gt9147_irq_flags[ts->irq_type] | IRQF_ONESHOT;
ret = devm_request_threaded_irq(&client->dev, ts->irq, NULL,
                gt9147_irq_thread, irq_flags, GT9147_DRIVER_NAME, ts);
```

硬中断 handler 传 NULL，内核用默认上半部"只唤醒线程并返回"；
真正的报点在 `gt9147_irq_thread` 里读触摸坐标，
而读坐标要走 I2C（会睡眠），所以必须在线程上下文做。
`IRQF_ONESHOT` 的作用是线程处理期间保持中断线屏蔽，
避免高电平/未清状态下反复触发。

**② back 按键：上半部只做定时器消抖，上报下放 workqueue**

```c
static irqreturn_t back_key_irq_handler(int irq, void *dev_id)
{
    struct back_key_device *key = dev_id;
    mod_timer(&key->debounce_timer, jiffies + msecs_to_jiffies(key->debounce_ms));
    return IRQ_HANDLED;
}

static void back_key_timer_function(unsigned long data)
{
    schedule_work(&((struct back_key_device *)data)->report_work);
}
```

机械按键一次动作会产生一串抖动沿。每次来沿就把 20ms 定时器往后推，
抖动期间定时器不断被推迟，只有真正稳定 20ms 才到期，
一次按压只上报一次。定时器回调也不能睡眠，
所以在 work 里才用 `gpiod_get_value_cansleep()` 读电平、
`input_report_key()` + `input_sync()` 上报，
`GPIO_ACTIVE_LOW` 的极性换算由 gpiod 自动完成。

**③ SR04 超声波：时间敏感，测量留在上半部，用 spinlock + completion**

```c
/* 上半部：双边沿触发，用高精度时间戳算回波宽度 */
now = ktime_get();
spin_lock_irqsave(&sr04->state_lock, flags);
if (level) {
    sr04->rise_time = now;  sr04->rise_seen = true;   /* 上升沿：起跑 */
} else if (sr04->rise_seen) {
    pulse_us = ktime_to_us(ktime_sub(now, sr04->rise_time)); /* 下降沿：到站 */
    sr04->waiting_echo = false;
    complete_measurement = true;
}
spin_unlock_irqrestore(&sr04->state_lock, flags);
if (complete_measurement)
    complete(&sr04->measurement_done);
```

这一路是**故意不放下半部的**：微秒级脉宽测量如果放 workqueue，
会被调度延迟污染。所以上半部只做三件事——读电平、取 `ktime_get()` 时间戳、
用自旋锁更新状态机，然后 `complete()` 唤醒等待的进程。
进程侧 `reinit_completion()` 先清历史状态（防上一次的过期中断"秒唤醒"），
再 `wait_for_completion_interruptible_timeout(..., 50ms)`，
50ms 超时对应 8 米量程，超时就返回测量失败而不是永久卡死。
进程和中断之间用 `spin_lock_irqsave` + completion，不用 mutex
（中断上下文拿不了 mutex），测距串行化交给进程侧的 mutex。

**④ SR501 人体红外：只做延迟工作，状态读取全下放**

```c
static irqreturn_t sr501_irq_handler(int irq, void *data)
{
    struct sr501_device *dev = data;
    mod_delayed_work(system_wq, &dev->work, msecs_to_jiffies(SR501_DEBOUNCE_MS));
    return IRQ_HANDLED;
}
```

上半部只重置一个 20ms 延迟工作，真正读 GPIO、判定有无人体、
递增 `event_seq`、唤醒 `wait_queue` 都在 work 里做。
用户态 `read` 用 `wait_event_interruptible` 等事件，
`poll` 也挂在同一个 `wait_queue_head_t` 上，两种方式都能及时拿到状态。

**⑤ 网卡的 NAPI：中断和轮询的混合（面试常被追问的点）**

FEC 收到第一个包时中断，上半部不直接处理协议栈，
而是 `napi_schedule()` 把该网卡挂到软中断（`NET_RX_SOFTIRQ`）的 poll 列表，
随后在软中断里批量收包，收完再重新开中断。
这本质上还是"上半部做不得已的事、批量工作下放"的思路，
好处是高流量下中断次数不会随包数线性增长。

### 4. 我实际遇到并处理过的问题

1. **中断号拿不到**：`gpiod_to_irq()` 可能返回负值（引脚没被配成
   中断功能、或该 bank 中断设备树没写好），项目里对返回值统一判错，
   不硬编码 IRQ 号。
2. **中断里睡眠**：这是我最警惕的一条。SR04 的上半部只用
   `gpiod_get_value()`（本地 GPIO，快且不睡眠），
   back_key/SR501 要读电平就移到 work 里用 `_cansleep` 版本；
   GT9147 要读 I2C 就直接用线程化中断。
3. **过期中断误唤醒**：SR04 用 `reinit_completion()` 清完成量，
   否则上一次测量的完成信号会让本次读操作立刻返回旧值。
4. **中断配错触发类型**：GT9147 的边沿/电平由芯片配置字决定，
   我把它映射成 `gt9147_irq_flags[]` 四档再拼 `IRQF_ONESHOT`，
   保证 dts 的 `interrupts` 与芯片实际输出一致。
5. **验证手段**：板端看 `/proc/interrupts` 观察各 IRQ 计数是否随事件增长、
   有没有只涨不停的异常中断；`dmesg` 看 probe 与 request_irq 结果；
   启动日志里四个驱动的 IRQ 号 39/48/152/168 都能对上，
   说明注册和硬件映射是通的。

### 5. 一句话总结

了解，而且在这个项目里是主力手段：8 个板级驱动中有 4 个走中断
（GT9147 线程化中断、back 按键定时器消抖 + workqueue、
SR04 硬中断抓时间戳 + completion、SR501 延迟工作 + waitqueue），
网卡用 NAPI 中断加轮询，PHY 因为没接中断线走纯轮询。
处理原则始终是：上半部只做必须立刻做的事并清中断、可延后或会睡眠的
工作交给线程/工作队列，共享状态按上下文选 spinlock 或 mutex，
触发类型与硬件一致，最后用 `/proc/interrupts` 和 dmesg 实测验证。

## Q3. 你了解 Linux 中断子系统吗？结合你的项目说一说整体链路

### 1. 子系统的基本分层与四个核心数据结构

这份内核是 `4.1.15`（`Makefile` 里 `VERSION=4 PATCHLEVEL=1 SUBLEVEL=15`），
中断子系统的落点很清晰：

| 层 | 文件 | 职责 |
|---|---|---|
| CPU 异常入口 | `arch/arm/kernel/entry-armv.S` | 保存现场，跳到已注册的顶层入口 |
| 中断控制器驱动 | `drivers/irqchip/irq-gic.c` | GIC 初始化、读写 IAR/EOIR、提供 `irq_chip` |
| 二级控制器驱动 | `drivers/gpio/gpio-mxc.c` | GPIO bank 的中断聚合，chained handler |
| 框架核心 | `kernel/irq/{irqdesc,manage,handle,chip}.c` | 描述符、注册/线程化、事件分发 |
| 域映射 | `kernel/irq/irqdomain.c` | hwirq ↔ virq 映射、设备树中断解析 |
| GPIO 抽象 | `drivers/gpio/gpiolib.c` | `gpiod_to_irq()` |

四个关键结构，各管一件事：

- `irq_chip`：**怎么操作硬件**——mask/unmask/ack/EOI/set_type。
  GIC 有 `gic_chip`，GPIO bank 有 `irq_alloc_generic_chip()` 生成的那套
  （`irq_gc_mask_clr_bit`、`irq_gc_ack_set_bit`、`gpio_set_irq_type`）。
- `irq_domain`：**hwirq 和 virq 怎么换算**。本板有两级：
  GIC 用 `irq_domain_add_linear()`（`GIC_SPI 66` 这种全局硬件号），
  GPIO 用 `irq_domain_add_legacy()`（bank 内 0~31 的偏移）。
- `irq_desc`：**每个 virq 一份的台账**，记录 chip、flow handler、
  action 链、状态位、深度。中断号在 `/proc/interrupts` 里一行对应一个 desc。
- `irqaction`：**驱动注册的处理函数节点**，`request_irq` 挂上去，
  同一 desc 上可挂多个（共享中断按链遍历，谁返回 `IRQ_HANDLED` 就认）。

再加一个控制流的抽象 `irq_flow_handler_t`：边沿用 `handle_edge_irq`、
电平用 `handle_level_irq`，负责 mask/ack/EOI 的时序与重入处理，
它是"硬件动作"和"驱动 handler"之间的粘合层。

### 2. 启动期：这套东西是怎么按顺序建立起来的

1. **顶层入口注册**：GIC 驱动用
   `IRQCHIP_DECLARE(cortex_a7_gic, "arm,cortex-a7-gic", gic_of_init)`
   匹配本板 dts 的 `intc@00a01000`（`compatible = "arm,cortex-a7-gic"`），
   `gic_of_init()` 里建 `irq_domain_add_linear()`，最后
   `set_handle_irq(gic_handle_irq)` 把顶层入口钉在 `gic_handle_irq`。
2. **GPIO bank 注册为二级控制器**：`gpio-mxc` probe 时
   `irq_base = irq_alloc_descs(-1, 0, 32, ...)` 动态申请 32 个 virq，
   再 `irq_domain_add_legacy(np, 32, irq_base, 0, &irq_domain_simple_ops)`，
   用 `irq_alloc_generic_chip("gpio-mxc", 1, irq_base, base, handle_level_irq)`
   建 chip，最后 `irq_set_chained_handler(port->irq, mx3_gpio_irq_handler)`
   把 bank 的 parent 中断（dts 里 `gpio1: interrupts = <GIC_SPI 66 ...>`）
   挂上 GPIO 的中断分发函数。
3. **设备驱动注册自己的中断**：以触摸为例，probe 里
   `devm_gpiod_get(..., "interrupt")` → `gpiod_to_irq()` →
   `gpiochip_to_irq()` → `irq_find_mapping(domain, 9)` 拿到 virq，
   再 `devm_request_threaded_irq()` 进 `__setup_irq()`：
   设触发类型（走 `irq_chip->irq_set_type` → `gpio_set_irq_type`
   写 GPIO 的 ICR 寄存器）、挂 `irqaction`、
   因为给了 `thread_fn`，还会创建内核线程 `irq/39-gt9147`。

这里有个能验证映射链的细节：`irq_base` 是**动态**申请的（不是硬编码），
本板这次启动里 gpio1 拿到 base=30，于是 GPIO1_IO09 → 30+9 = **39**、
GPIO1_IO18 → 30+18 = **48**，正好对上触摸和按键的启动日志。
这也是驱动里为什么要用 `gpiod_to_irq()` 而不是写死中断号。

### 3. 运行期：一次触摸从硬件到用户态的完整链路

```
手指触摸 GT9147
  │ INT 引脚（GPIO1_IO09，下降沿）
  ▼
GPIO1 控制器内部 ISR 置位 → 拉高 bank 中断线 → GIC SPI 66
  ▼
ARM IRQ 异常向量（保存现场）
  ▼
gic_handle_irq(regs)                      // set_handle_irq 注册的顶层入口
  │ 读 GIC IAR 得到 hwirq = 66
  ▼
handle_domain_irq(gic->domain, 66, regs)  // kernel/irq/irqdesc.c
  │ irq_find_mapping：hwirq 66 → virq（GPIO1 bank 的 desc）
  ▼
generic_handle_irq_desc() → desc->handle_irq = mx3_gpio_irq_handler
  │ chained_irq_enter：屏蔽/ack 父中断，进入 GPIO 控制器的级联处理
  │ 读 GPIO_ISR & GPIO_IMR，fls() 定位到 bit9
  ▼
generic_handle_irq(irq_find_mapping(gpio_domain, 9))   // → virq 39
  ▼
desc->handle_irq = handle_level_irq
  │ mask_ack（写 ISR 清标志、清 IMR 屏蔽位）
  ▼
handle_irq_event → 遍历 irqaction 链
  │ 本驱动 primary handler 传 NULL → irq_default_primary_handler
  │ 返回 IRQ_WAKE_THREAD
  ▼
irq_wake_thread() 唤醒内核线程 irq/39-gt9147
  │ IRQF_ONESHOT：中断线保持屏蔽，等线程收尾再解除
  ▼
gt9147_irq_thread()：I2C 读坐标（这里的睡眠是被允许的）
  │ input_report_abs / input_mt_sync / input_sync
  ▼
evdev 唤醒 /dev/input/event2 的等待者
  ▼
Qt（LinuxFB 后端）消费触摸事件
  ▼
irq_finalize_oneshot() 解除屏蔽，chained_irq_exit → GIC EOI
```

这条链里每一层都能对应到项目里的一份代码或一条日志，
而 `handle_level_irq` + `gpio_set_irq_type` 的组合也正是
"GPIO 内部是电平聚合、单根引脚可配边沿/电平"这两件事的落点。

### 4. 项目里五个分叉点（中断处理模型的对照）

同一条到 virq 的链路不变，**差异全在 `handle_irq_event` 之后怎么下放**：

| 场景 | 上半部做完什么 | 分叉到哪 | 项目里的具体实现 |
|---|---|---|---|
| GT9147 触摸 | 默认上半部只唤醒线程 | 内核线程 | `IRQF_ONESHOT` + `NULL` handler + I2C 读坐标 |
| back 按键 | 推 20ms 消抖定时器 | timer → system_wq | work 里 `gpiod_get_value_cansleep` + `input_report_key` |
| SR04 测距 | 读电平、`ktime_get()`、spinflock、`complete()` | 直接唤醒进程 | 进程侧 `wait_for_completion_interruptible_timeout(50ms)` |
| SR501 人体红外 | `mod_delayed_work(system_wq, 20ms)` | 延迟工作队列 | work 里递增 `event_seq`，唤醒 waitqueue/poll |
| FEC 网卡 | `napi_schedule()` | 软中断 `NET_RX_SOFTIRQ` | `net_rx_action` 里批量收包，收完重开中断 |

值得单独说明两点：

- **NAPI 是"中断 + 轮询"的混合**，但它走的是软中断而不是 workqueue，
  因为网络收包在软中断上下文就能完成，不需要睡眠，也不需要线程开销。
  这解释了为什么"下放"不只有 workqueue 一种答案，要看工作的性质。
- **SR04 是刻意不下放的例外**，微秒级脉宽测量放 workqueue 会被调度延迟污染，
  所以时间戳必须在上半部取，只把"通知进程"这一步通过 completion 交出去。
  同一个驱动里对"必须立刻做"和"可以延后"的划分，正是中断子系统的核心思想。

### 5. 观测与调试（本项目实际用到的）

- `/proc/interrupts`：每个 virq 一行，看计数是否随事件增长；
  某号只涨不停通常意味着电平触发没清或器件异常，边沿配错则表现为丢事件。
  本板启动日志里 GT9147=39、back key=48、SR04=152、SR501=168 都能对上。
- `dmesg`：看 probe 结果与 `request_irq` 返回值，确认注册成功。
- 注意本项目为压启动时间关掉了 `CONFIG_DEBUG_FS`，
  所以 `/sys/kernel/debug/irq` 这类调试节点不可用，靠 `/proc/interrupts` 和日志。
- 唤醒能力：back 按键在 dts 里标了 `wakeup-source`，
  驱动 `device_init_wakeup()` + `enable_irq_wake()`，
  让唤醒请求沿 GPIO → GIC 传递，可以从中断唤醒系统。
- i.MX6ULL 是单核 Cortex-A7，`smp_affinity` 没有实际意义；
  但代价是中断延迟直接吃在唯一的核上，所以上半部越短越好。

### 6. 一句话总结

Linux 中断子系统就是"**irq_domain 做号段换算、irq_chip 做硬件动作、
irq_desc 做台账、irqaction 挂驱动处理函数、flow handler 管时序、
线程/软中断/workqueue 做下放**"这样一套机制。
在本项目里完整链路是：
设备树两级 `interrupt-parent`（GPIO1 → GIC）→ 驱动 `gpiod_to_irq()`
拿到动态映射的 virq → `request_irq`/`request_threaded_irq` 注册 action →
硬件拉 GIC → `gic_handle_irq` → `handle_domain_irq` → GPIO chained handler →
具体 pin 的 virq → `handle_level_irq` → 驱动 handler →
再按场景下放到线程、timer+workqueue、completion 或软中断，
最后通过 input 子系统、waitqueue 或协议栈送达用户态。

## Q4. GT9147 向北是不是 Input 子系统？结合它详细说说 Input 子系统

### 1. 先摆清方向：GT9147 驱动在 Input 里站哪一侧

是的，GT9147 完全属于 Input 子系统，但要区分两个"方向"：

- **南向**：它是 I2C 设备驱动。probe 挂在 `i2c_client` 上，
  读复位、读产品 ID、读坐标，走 I2C 总线。
- **北向**：它把数据交给内核，**经由 Input 子系统再暴露给用户态**。
  准确说，驱动实现的是 Input 的**设备侧** `input_dev`；
  真正面向应用层的是 `evdev` 这个 **handler**，它注册出
  `/dev/input/event2` 字符设备。驱动自己并不创建 event 节点。

所以更严谨的表述是：GT9147 是 Input 子系统的设备端，
`/dev/input/event2` 是 Input 子系统向上暴露的接口。
内核启动日志能同时印证两侧：

```
gt9147 1-0014: product ID: 9147, ...  resolution: 800x480, points: 5, irq type: 3
input: gt9147-touchscreen as /devices/.../input/input2
GT9147 touchscreen registered on IRQ 39
```

### 2. Input 子系统的核心是"设备"和"处理器"两端匹配

这套框架只有三个角色，非常清晰：

| 角色 | 谁提供 | 本项目的对应 |
|---|---|---|
| `input_dev` | 设备驱动 | GT9147 驱动自己 allocate/register |
| `input_handler` | 消费者 | `evdev`、`mousedev`、`joydev`、键盘 LED 等 |
| `input_core` | `drivers/input/input.c` | 把两端匹配起来并转发事件 |

匹配过程在 `input.c` 里一看就明白：

```c
/* input_register_device() 尾部 */
list_for_each_entry(handler, &input_handler_list, node)
        input_attach_handler(dev, handler);
```

`input_attach_handler()` 用 `input_match_device()` 比对 `input_device_id`；
evdev 的 id 表是 `{ .driver_info = 1 }`，注释写着 *Matches all devices*，
所以**每个 input 设备都会自动多出一个 evdev 接口**。
匹配成功后调 `handler->connect = evdev_connect()`，
创建 `eventN` 字符设备，并用 `input_handle` 把 dev 和 handler 绑在一起。
反向也成立：handler 后注册时会遍历所有已有设备补匹配
（`input_register_handler()` 里的同名循环）。

数据通路的调用链是：

```
驱动 input_report_abs() / input_sync()
  ▼ input_event()
input_handle_event()          // 按 evbit/keybit/absbit 校验能力、算 disposition
  ▼
input_pass_values()           // 依次调用 input_handle->handler->events
  ▼
evdev_events() → evdev_pass_values()   // 按"包"写入 client 环形缓冲
  ▼
wake_up_interruptible(&client->wait)   // 唤醒阻塞在 read/poll 上的应用
  ▼
应用 read() 得到 struct input_event 流
```

注意最后一步的关键设计：`input_sync()` 产生的 `EV_SYN / SYN_REPORT`
不是"多余事件"，它是**包边界**。evdev 按包缓冲，
应用一次 `read()` 能拿到一整帧完整坐标，不会被拆成半帧。
缓冲区溢出时会插一个 `SYN_DROPPED` 通知应用丢弃残缺数据。

### 3. GT9147 是怎么把自己注册进 Input 的

对应 `gt9147_input_init()`：

```c
input = input_allocate_device();          /* 申请空的 input_dev */
input->name = "gt9147-touchscreen";
input->phys = "input/gt9147";
input->id.bustype = BUS_I2C;              /* 身份：I2C 设备 */
input->dev.parent = &ts->client->dev;     /* sysfs 挂在 I2C 节点下 */

__set_bit(EV_KEY, input->evbit);          /* 会发 KEY 事件 */
__set_bit(EV_ABS, input->evbit);          /* 会发绝对坐标事件 */
__set_bit(BTN_TOUCH, input->keybit);      /* 触摸按键 */
__set_bit(INPUT_PROP_DIRECT, input->propbit);  /* 直接接触式屏幕 */

/* 五个轴的能力与取值范围 */
input_set_abs_params(input, ABS_X, 0, ts->size_x - 1, 0, 0);
input_set_abs_params(input, ABS_Y, 0, ts->size_y - 1, 0, 0);
input_set_abs_params(input, ABS_MT_POSITION_X, 0, ts->size_x - 1, 0, 0);
input_set_abs_params(input, ABS_MT_POSITION_Y, 0, ts->size_y - 1, 0, 0);
input_set_abs_params(input, ABS_MT_TOUCH_MAJOR, 0, 255, 0, 0);

input_mt_init_slots(input, ts->max_touch_num, INPUT_MT_DIRECT);
input_register_device(input);             /* 注册后才出现 eventN */
```

`input_mt_init_slots()` 不只是分配 5 个 slot，它还会替驱动补三件事：
声明 `ABS_MT_SLOT`（0~4）和 `ABS_MT_TRACKING_ID`，
把 `ABS_X/ABS_Y` 从 `ABS_MT_POSITION_X/Y` 复制过来，
并因为 `INPUT_MT_DIRECT` 自动置 `INPUT_PROP_DIRECT`。
这也是驱动里写 `INPUT_MT_DIRECT` 的意义——告诉内核
"这是触摸屏而不是触摸板"。

### 4. 报点全过程：MT Type B 协议

`gt9147_irq_thread()` 就是按 Type B 协议逐条上报的，步骤值得拆开讲：

```c
/* 1. 读 0x814E：bit7 = 数据就绪，低 4 位 = 当前手指数 */
touch_num = status & GT9147_STATUS_TOUCH_MASK;

/* 2. 一次把 touch_num 个 8 字节坐标块读出来 */
gt9147_i2c_read(ts, GT9147_REG_POINTS, points, touch_num * GT9147_POINT_SIZE);

/* 3. 逐指上报 */
id    = point[0] & 0x0f;                  /* 硬件追踪 ID */
x     = point[1] | (point[2] << 8);
y     = point[3] | (point[4] << 8);
width = point[5] | (point[6] << 8);
gt9147_transform_position(ts, &x, &y);    /* 交换/镜像在驱动侧做完 */

set_bit(id, &active_slots);               /* 本帧这根手指还活着 */
input_mt_slot(ts->input, id);             /* 切到该手指的 slot */
input_mt_report_slot_state(ts->input, MT_TOOL_FINGER, true);  /* Down */
input_report_abs(ts->input, ABS_MT_POSITION_X, x);
input_report_abs(ts->input, ABS_MT_POSITION_Y, y);
input_report_abs(ts->input, ABS_MT_TOUCH_MAJOR, width);
input_report_abs(ts->input, ABS_MT_WIDTH_MAJOR, width);
```

这里有两个容易被追问的点：

**为什么要有 slot 和 tracking ID？** Type B 协议用 slot 表示"手指"
（`input_mt_slot()` 切通道，`report_slot_state(..., true)` 内部写
`ABS_MT_TRACKING_ID`），同一根手指在 slot 里连续更新坐标，
应用看到的是"移动"而不是"抬起再按下"。

**为什么还要第二遍循环？** GT9147 只在中断里报"当前还按着的手指"，
不会主动发抬起事件。所以驱动用 `active_slots` 位图记下本帧出现过的 ID，
再遍历全部 slot，没打勾的调
`input_mt_report_slot_state(..., MT_TOOL_FINGER, false)`
释放（tracking ID 置 -1）。漏掉这一步就会留下"幽灵手指"，
在 Qt 上表现为触点粘滞、拖不断。

最后两步收尾：

```c
input_mt_report_pointer_emulation(ts->input, true);  /* 补 BTN_TOUCH + ABS_X/Y */
input_sync(ts->input);                               /* EV_SYN：整帧封包 */
gt9147_i2c_write_u8(ts, GT9147_REG_STATUS, 0);       /* 清状态，否则不再中断 */
```

`report_pointer_emulation` 是兼容老程序的：它把主触点映射成
传统单点 `ABS_X/ABS_Y + BTN_TOUCH`，这样不认 MT 协议的程序也能用。

### 5. 北向的最终形态：event2 与 /proc/bus/input/devices

evdev 的设备号是这么来的：`EVDEV_MINOR_BASE = 64`，
`evdev_connect()` 调 `input_get_new_minor()` 拿 minor，
`legacy_minors = true` 时 `dev_no = minor - 64`，
再 `dev_set_name(&evdev->dev, "event%d", dev_no)`。
本板这块屏是第三个 evdev 设备，所以是 **event2**——
这个编号是动态分配的结果，不能当成固定契约，用户态要靠
`/proc/bus/input/devices` 或 `ID_INPUT_TOUCHSCREEN` udev 属性去认设备。

板端 `cat /proc/bus/input/devices` 关键三行：

```
H: Handlers=event2
B: PROP=2
B: ABS=... (ABS_MT_*, ABS_X/Y)
```

这里我要澄清一处容易看错的细节：文档里写的 "PROP=2 = INPUT_PROP_DIRECT"
表述不严谨。`/proc/bus/input/devices` 打印的是**位图**
（`input_seq_print_bitmap(seq, "PROP", dev->propbit, INPUT_PROP_MAX)`），
`PROP=2` 是 `0b10`，即 **bit1 置位**；
而枚举值 `INPUT_PROP_DIRECT` 是 `0x01`（bit0 是 `INPUT_PROP_POINTER`）。
所以"PROP=2"和"INPUT_PROP_DIRECT"说的是同一件事，
但一个是位图打印值、一个是枚举常量，回答时不能把两者混为一谈。

用户态这边，Qt（LinuxFB 后端 + evdev 输入插件）就是读
`/dev/input/event2` 的 `input_event` 流：`EV_ABS + ABS_MT_POSITION_*`
拿到原始多点数据，`EV_SYN/SYN_REPORT` 切分一帧。
`INPUT_PROP_DIRECT` 让上层把它识别为触摸屏（坐标即屏幕坐标），
而不是需要指针加速的触摸板。

### 6. 这部分踩过的坑（都和 Input 强相关）

1. **gpiod 极性改错，症状却爆在 Input 上**：复位脚是
   `GPIO_ACTIVE_LOW`，用 `gpiod_set_value()` 写逻辑电平时照抄旧代码导致复位反相，
   I2C 读产品 ID 报 `-EIO`，probe 失败，
   结果就是 `/dev/input/event2` 根本不出现。
   这说明"event 节点出没出现"是南向硬件是否正常的直接信号。
   编译、链接、符号全过，只有上板才暴露，教训是接口迁移必须做真机回归。
2. **I2C 必须在线程上下文**：报点要读寄存器，所以用
   `devm_request_threaded_irq` + `IRQF_ONESHOT`，
   上半部只唤醒 `irq/39-gt9147`，真正的报点在能睡眠的线程里做。
3. **没有 `input_sync()` 就没有帧**，应用会一直等不到完整数据；
   没有释放 slot 就会幽灵触点；这两条在 Qt 上表现为"没反应"和"粘屏"两种不同故障。
4. **越界保护**：`id >= ts->max_touch_num` 直接丢弃、
   `touch_num > max_touch_num` 走 `clear_status` 退出，
   避免非法硬件数据写坏 slot 数组。
5. **坐标语义统一在驱动侧**：`gt9147_transform_position()`
   把交换/镜像和边界钳位做完，北向拿到的就是屏幕坐标系，
   用户态和 Qt 不需要各自再修正一遍——这是"南向差异在驱动内消化、
   北向接口保持统一语义"的典型做法。

### 7. 一句话总结

GT9147 向北确实走 Input 子系统，但更准确的说法是：
**它是 Input 的设备端（input_dev），evdev 才是北向接口**。
完整链路是 `input_allocate_device` → 声明 EV_KEY/EV_ABS 能力与
`ABS_MT_*` 轴范围 → `input_mt_init_slots(5, INPUT_MT_DIRECT)` 建 slot →
`input_register_device` 触发 evdev 匹配并创建 `/dev/input/event2` →
中断线程按 MT Type B 协议用 `input_mt_slot` +
`input_report_abs` 报点、用 active_slots 补释放 →
`input_sync` 封帧 → evdev 唤醒并投递 `input_event` 流 →
Qt 在 LinuxFB 上消费，`INPUT_PROP_DIRECT` 让它按触摸屏而不是触摸板处理。

## Q5. 作为北向接口的 event，结合项目详细介绍；开发中还有哪些常见设备用它

### 1. event 接口的本质

`/dev/input/eventN` 不是一个"文件"，而是 `evdev` handler 为每个
input 设备注册出来的字符设备：`evdev_connect()` 里
`input_get_new_minor(EVDEV_MINOR_BASE=64, EVDEV_MINORS=32, true)` 拿号，
`legacy_minors = true` 时 `dev_no = minor - 64`，于是名字是 `event0..event31`；
底层用 `cdev_add` 挂到 `INPUT_MAJOR` 字符设备上，
同时 `device_add` 注册到 sysfs 的 input 类里。

所以它拿到的是**原始事件流**：不做协议解析、不做语义封装，
驱动往里塞什么，event 节点就往外吐什么。这也是 evdev 相比
mousedev/joydev 更受现代框架青睐的原因——信息无损失，
多点触控的 `ABS_MT_*`、按键的 `EV_KEY`、能力位图都能完整拿到。

### 2. 本板实际有四个 event 节点（有启动日志可对）

从 `/tmp/boot_phy.log` 里的 `input:` 行和板端 `/dev/input/event0..event3`
可以一一对上：

| 节点 | input 设备名 | 来源 | 能力 |
|---|---|---|---|
| event0 | `20cc000.snvs:snvs-powerkey` | SoC SNVS 电源键（platform） | `EV_KEY` / `KEY_POWER` |
| event1 | `smarthome-back-key` | 本项目自定义 back 按键驱动 | `EV_KEY` / `KEY_BACK`(158) |
| event2 | `gt9147-touchscreen` | GT9147 电容触摸屏（I2C） | `EV_KEY`+`EV_ABS`，MT Type B，`INPUT_PROP_DIRECT` |
| event3 | `Nozzle Alignment Camera` | UVC USB 摄像头（`uvcvideo`） | `EV_KEY` / `KEY_CAMERA`（机身上的快门键） |

其中 event3 最能说明"哪些设备会走 event"这件事：它不是键盘鼠标，
而是**一个 USB 摄像头的按键端点**。`drivers/media/usb/uvc/uvc_status.c`
里的 `uvc_input_init()` 会为支持按键的 UVC 摄像头注册 input 设备
（`input->name = dev->name`，能力位就 `EV_KEY + KEY_CAMERA`），
所以插上摄像头后系统就多了一个 event 节点。

顺带一个实证：既然 event3 是"插上摄像头才有"，那 eventN 的编号就会
随硬件枚举顺序变化。项目的 `test_back_key` 和 `gt9147_test` 两个测试程序
正是因此**不硬编码编号**——它们遍历 `/dev/input/eventN`，
用 `EVIOCGNAME` 读设备名，去匹配 `"smarthome-back-key"` /
`"gt9147-touchscreen"`（`strings` 里能看到这两个名字和
`/dev/input/event%d`）。这是"编号是动态的、要用名字或属性认设备"的现场证据。

### 3. 接口怎么用：读、写、ioctl、poll

**打开与读取**。典型流程是 `open("/dev/input/event2", O_RDONLY)`，
然后 `read()` 出一串 `struct input_event`：

```c
struct input_event {
        struct timeval time;   /* 事件时间戳 */
        __u16 type;            /* EV_KEY / EV_ABS / EV_SYN ... */
        __u16 code;            /* KEY_BACK / ABS_MT_POSITION_X ... */
        __s32 value;           /* 按下=1 / 抬起=0 / 坐标值 */
};
```

32 位 ARM 上 `timeval` 是 8 字节，所以一条事件 16 字节；
应用必须按 `sizeof(struct input_event)` 逐条读，
不能自己拼字节序（内核里还有 `input_event64` / compat 处理，
32 位程序读到的就是 16 字节版本）。

几个语义要点：

- `EV_SYN / SYN_REPORT` 是**帧边界**，一次 `read()` 通常拿到整帧；
  溢出时内核会插 `SYN_DROPPED`，应用的正确做法是丢弃到下一个
  `SYN_REPORT`，再用 ioctl 重新同步一次当前状态。
- `poll()`/`select()`/`epoll` 可等事件，`O_NONBLOCK` 下没数据返回 `EAGAIN`；
  还支持 `F_SETFL` 的异步通知（fasync）。
- `write()` 只对少数类型有意义，比如 `EV_LED`（键盘灯）、
  `EV_SND`（蜂鸣）、`EV_FF`（力反馈装载/擦除效果）。
  触摸屏和按键这类设备是**只读**的。

**常用 ioctl**（本项目测试程序就用了第一种）：

| ioctl | 作用 |
|---|---|
| `EVIOCGNAME(len)` | 读设备名，用来认设备（替代硬编码 eventN） |
| `EVIOCGID` / `EVIOCGPHYS` / `EVIOCGUNIQ` | 读总线 ID、物理路径、唯一 ID |
| `EVIOCGBIT(EV_KEY/EV_ABS, len)` | 读能力位图，判断设备支持哪些事件/按键/轴 |
| `EVIOCGKEY(len)` | 读当前按键状态（`SYN_DROPPED` 后重新同步用） |
| `EVIOCGABS(abs)` / `EVIOCSABS(abs)` | 读写轴的范围、分辨率、fuzz、flat |
| `EVIOCGMTSLOTS(len)` | 批量读各 slot 的多点触控原始值 |
| `EVIOCGRAB` | 独占抓取设备，其他客户端只收同步事件 |
| `EVIOCSCLOCKID` | 选时间戳时钟源（realtime / monotonic / boottime） |
| `EVIOCREVOKE` | 强制回收访问权（注销设备时用） |

**缓冲与多客户端**。evdev 每个客户端一份环形缓冲，
最小 64 条事件、最多 8 个包（`EVDEV_MIN_BUFFER_SIZE` / `EVDEV_BUF_PACKETS`）；
多个进程可以同时打开同一个 event 节点各读各的，
`EVIOCGRAB` 是唯一会互相影响的例外——比如强行 grab 触摸屏会让 Qt 收不到点，
这类 API 在生产环境要慎用。

### 4. 与同族 handler 的关系，以及为什么优先用 evdev

同一个输入设备可以同时被多个 handler 挂上。本工程 defconfig 里
`CONFIG_INPUT_EVDEV=y` 和 `CONFIG_INPUT_MOUSEDEV=y` 都开着，
所以 GT9147 触摸屏除了 `event2`，还会被 `mousedev` 消费出一路
`/dev/input/mouse0`（这正是 `input_mt_report_pointer_emulation()`
补 `ABS_X/Y + BTN_TOUCH` 的另一个作用面）。

| handler | 节点 | 特点 |
|---|---|---|
| evdev | `/dev/input/eventN` | 原始、完整、含多点与能力位图，现代首选 |
| mousedev | `/dev/input/mouseN` | 只给单点鼠标语义，多点信息丢失 |
| joydev | `/dev/input/jsN` | 摇杆/手柄的轴+按键语义 |

所以开发触摸屏、多点手势、按键这类功能，都读 event；
mousedev/joydev 只在对接老程序时才用。

### 5. 开发中还有哪些常见设备会用 event

凡是"内核里有 `input_dev` 的设备"，都会自动多出一个 event 节点：

| 类别 | 典型设备 | 事件类型 |
|---|---|---|
| 按键/开关 | gpio-keys（电源、音量、复位、lid 盖开关）、SNVS 电源键、矩阵键盘、USB/PS2 键盘 | `EV_KEY` |
| 指点设备 | USB/蓝牙鼠标、触摸板、TrackPoint、轨迹球 | `EV_REL` / `EV_ABS` / `EV_KEY` |
| 触摸屏/手写笔 | 电容/电阻触摸屏（I2C/SPI/USB）、电磁笔 digitizer | `EV_ABS` + MT `ABS_MT_*` |
| 游戏输入 | USB 手柄、摇杆、方向盘、力反馈设备 | `EV_KEY` + `EV_ABS` + `EV_FF` |
| 遥控器 | 红外/蓝牙遥控（rc-core 转成 input） | `EV_KEY` / `EV_MSC` |
| 传感与姿态 | 加速度计/陀螺仪（部分走 input，如 mma8450）、旋转编码器、霍尔 | `EV_ABS` / `EV_KEY` |
| USB HID 复合设备 | 键鼠一体接收器、多媒体键、条码枪 | `EV_KEY` / `EV_REL` |
| 多媒体外设 | UVC 摄像头机身按键（本项目 event3）、HDMI CEC | `EV_KEY` |
| 虚拟设备 | `uinput` 注入的虚拟键鼠（自动化测试常用） | 全类型 |

消费这些 event 的上层也很统一：X11 的 libinput/evdev 驱动、
Wayland 的 libinput、Qt 的 evdev 插件、SDL、Android 的 EventHub，
本质上都在读同一份 `input_event` 流。调试工具也一样——
`evtest`、`libinput debug-events`、`/proc/bus/input/devices`
都是围绕这个接口转的。本工程里还能用 `CONFIG_INPUT_EVBUG=m`
把事件打到 dmesg，做快速验证。

### 6. 结合项目的开发经验

1. **先按名字找设备，再打开**：`test_back_key` 遍历 eventN 用
   `EVIOCGNAME` 匹配 `smarthome-back-key`，`gt9147_test` 匹配
   `gt9147-touchscreen`，避免摄像头插拔导致编号漂移。
2. **按帧解析**：两个测试程序都以 `EV_SYN/SYN_REPORT` 为一帧，
   触摸按 `ABS_MT_POSITION_X/Y` 取坐标、`BTN_TOUCH` 判按下。
3. **权限**：`/dev/input/event*` 默认是 `root:input 0660`，
   要么以 root 跑（本工程 BusyBox rootfs 就是），要么用 udev 规则、
   `input` 组或 `uaccess` 授权给桌面用户。
4. **不要 grab**：Qt 正读着 event2，测试程序再 `EVIOCGRAB` 会把 Qt 饿死；
   验证时只读不锁。
5. **SYN_DROPPED 要处理**：触摸高频采样下缓冲溢出是正常现象，
   正确做法是丢到下一个 `SYN_REPORT`，再用 `EVIOCGABS`/`EVIOCGKEY`
   重新同步，而不是把残留的半帧当有效数据用。

### 7. 一句话总结

`/dev/input/eventN` 是 evdev 为每个 input 设备登记的北向字符设备接口，
输出统一的 `struct input_event` 流（type/code/value + 时间戳，
`SYN_REPORT` 切帧），配套 `EVIOCGNAME`/`EVIOCGBIT`/`EVIOCGABS`/
`EVIOCGRAB` 等 ioctl 和 poll 唤醒；本板四个节点分别是
SNVS 电源键(event0)、自定义 back 键(event1)、GT9147 触摸屏(event2)、
UVC 摄像头按键(event3)，测试程序按设备名而不按编号去找它们。
开发中几乎所有人在用的输入设备都走这个接口——键盘、鼠标、
触摸板、触摸屏、手柄、遥控器、传感器、条码枪、UVC 摄像头按键、
以及 uinput 虚拟设备；上层框架（Qt/libinput/Android EventHub）
读的也都是同一份事件流。

## Q6. 用的是什么架构的主控芯片？芯片里有哪些寄存器？哪些特殊寄存器重要？举例说明配合工作

### 1. 主控芯片与架构（有启动日志为证）

```
CPU:   Freescale i.MX6ULL rev1.1 69 MHz (running at 396 MHz)
CPU:   Industrial temperature grade (-40C to 105C) at 50C
Reset cause: POR
Board: MX6ULL ALIENTEK JJL
DRAM:  512 MiB
CPU: ARMv7 Processor [410fc075] revision 5 (ARMv7), cr=10c5387d
Machine model: Freescale i.MX6 ULL ALIENTEK JJL Board
```

- **芯片**：NXP（原 Freescale）**i.MX6ULL**，rev1.1，工业级温度档。
- **架构**：**ARMv7-A**，**单核 Cortex-A7**。
  `MIDR = 0x410fc075` 可以逐字段拆：implementer `0x41` = ARM，
  architecture `0xf` = ARMv7，part number `0xc07` = Cortex-A7，
  revision `5` = r0p5；`cr=10c5387d` 是 `SCTLR` 的当前值。
- **位宽/扩展**：32 位，带 VFPv4 + NEON，有 MMU 和 L1/L2 Cache。
- **频率**：本板 U-Boot 报 396 MHz（i.MX6ULL 有 528/792 MHz 等档位，
  实际由芯片型号和 CCM 配置决定，运行时有 DVFS）。
- **内存**：512 MiB DDR3L，DDR 基址 `0x8000_0000`（所以内核物理地址
  都在 0x8xxxxxxx，per-cpu 数据也在这一段里）。
- **总线结构**：ARM 核 + AXI/AHB 互联 + 多级 AIPS 桥
  （启动日志里的 `2000000.aips-bus` / `2100000.aips-bus`），
  所有外设寄存器都是**通过 AIPS 桥映射到同一个物理地址空间**的 MMIO。

### 2. 寄存器分两大类

**第一类：ARM 核内部系统寄存器（CP15）**。不在内存地址空间里，
要用 `MRC/MCR` 访问（Linux 里通过 `read_cpuid()` 等宏）。
关键的有：

| 寄存器 | 作用 |
|---|---|
| `MIDR` | 芯片/核识别（0x410fc075） |
| `SCTLR` | MMU、Cache、对齐检查、分支预测总开关（cr=10c5387d） |
| `VBAR` | 异常向量表基址（中断入口挂在这） |
| `TTBR0/TTBR1`、`TTBCR` | 一级页表基址与地址空间划分 |
| `DACR`、`CPACR` | 域访问权限、NEON/浮点协处理器使能 |
| `MPIDR`、`CCSIDR`、`CLIDR` | 多核 ID、Cache 层级信息 |

操作系统启动早期就必须配好这一类，否则连中断和虚拟内存都跑不起来。

**第二类：SoC 外设寄存器（MMIO，地址取自本工程 dtsi 与启动日志）**：

| 类别 | 模块与基址 | 说明 |
|---|---|---|
| 时钟/复位/电源 | CCM `0x020C_4000`、SRC `0x020D_8000`、GPC `0x020D_C000`、SNVS `0x020C_C000` | 时钟树、复位原因、低功耗 |
| 看门狗 | WDOG1 `0x020B_C000`、WDOG2 `0x020C_0000` | 超时复位 |
| 熔丝/OTP | OCOTP `0x021B_C000` | MAC、唯一 ID、校准值 |
| 引脚复用 | IOMUXC `0x020E_0000`、IOMUXC_GPR `0x020E_4000` | 功能选择、电气特性、全局杂项 |
| 中断 | GIC `0x00A0_1000`(分发器)/`0x00A0_2000`(CPU 接口)、GPIO1~5 `0x0209_C000`~`0x020A_C000` | 中断聚合与分发 |
| 定时器 | GPT1 `0x0209_8000`、EPIT1 `0x020D_0000` | 通用/周期定时 |
| 存储 | MMDC `0x021B_0000`、USDHC1 `0x0219_0000`、USDHC2 `0x0219_4000` | DDR 控制器、SD/eMMC |
| 通信 | UART1 `0x0202_0000`、I2C1 `0x021A_0000`、I2C2 `0x021A_4000`、eCSPI1 `0x0200_8000`、FEC1 `0x020B_4000`、FEC2 `0x0218_8000`、USB OTG1/2 `0x0218_4000`/`0x0218_4200` | 串口、触摸屏 I2C、SPI 传感器、双网口、USB 摄像头 |
| 显示/采集 | LCDIF `0x021C_8000`、CSI `0x021C_4000`、ADC1 `0x0219_8000` | 屏幕、摄像头接口、ADC |

### 3. 最重要的"特殊寄存器"清单

按"配错就出硬故障、且往往没有报错"来排序：

1. **`IOMUXC_SW_MUX_CTL_PAD_x` 与 `IOMUXC_SW_PAD_CTL_PAD_x`**：
   前者选 ALT 功能，后者管上拉/下拉、驱动强度、速率、开漏、迟滞。
   本项目 PHY 排查的核心就是这两个：ENET1 的 MDIO/MDC 引脚实际被
   ENET2 的 pinctrl 组占着，读寄存器才看出来。
2. **`IOMUXC_GPR1`**：全局杂项控制，ENET1/ENET2 的 REF_CLK 来源选择、
   SAI/ASRC 时钟、以及各种 IP 的旁路开关。U-Boot 里直接改它。
3. **`CCM_CCGRx` / `CCM_CBCDR` / `CCM_CSCMR` / `CCM_ANALOG PLL`**：
   外设时钟门控、分频、时钟源。门控没开时读外设寄存器会得到 0
   甚至总线挂死，"代码看着没错但硬件不动"经常是这里。
4. **`SRC_SRSR` / `SRC_SBMR1/2`**：复位原因
   （本板启动打印 `Reset cause: POR`）和启动介质
   （eMMC/SD/NAND/USB 由 BOOT_MODE 与 GPIO 拨码经 `SBMR` 反映）。
5. **`SNVS_LPCR`(0x38) / `SNVS_HPSR`(0x14) / `SNVS_LPSR`(0x4C)**：
   低功耗与开关机。本项目的 SNVS 电源键驱动就是
   读 `HPSR bit6` 判断按下、读 `LPSR bit18` 识别"关机事件"并写回清除，
   再使能 `LPCR bit5 (DEP_EN)`。
6. **`WDOG_WCR` / `WDOG_WSR` / `WDOG_WRSR`**：看门狗使能与喂狗，
   以及 `WDZST/WDBG`（休眠/调试时是否停表）。
7. **GPIO 的 `ICR` / `IMR` / `ISR` / `EDGE_SEL`**：中断触发类型、
   屏蔽、状态清除；配合 `GDIR/DR/PSR` 做输入输出。
8. **GIC 的 `GICD_ISENABLER` / `ICFGR` / `IPRIORITYR` / `GICC_IAR` / `GICC_EOIR`**：
   中断使能、触发类型、优先级、应答与结束。
9. **FEC 的 `ECR` / `RCR` / `MII_SPEED` / `MII_DATA` / `IMASK` / `IEVENT`**：
   网络开关、RMII/速率/双工、MDIO 时序与帧、中断。
10. **`MMDC_MDCTL` / `MDCFG` / `MDMISC` / `MDSCR`**：DDR 初始化与训练，
    写错直接起不来，所以都在 SPL/U-Boot 阶段完成。
11. **CP15 的 `SCTLR` / `VBAR` / `TTBRx` / `DACR` / `CPACR`**：
    OS 级基础，配合第 1 类属于"芯片内"的另一半。

### 4. 典型场景里的寄存器配合

**场景 A：网络口从引脚到链路的全链路（本项目最实的一个）**

这一串正好把 U-Boot、pinctrl、CCM、FEC、PHY 五层串起来：

```
IOMUXC_GPR1        选 ENET1/2 的 50M REF_CLK 来源
  │  U-Boot 代码：clear gpr1[13], set gpr1[17]（ENET1）
  │              clear gpr1[14], set gpr1[18]（ENET2）
  ▼
IOMUXC_SW_MUX_CTL_PAD_x  把引脚切到 ENET 的 ALT 功能
  │  devmem 0x020E0074 = 0x1  → GPIO1_IO06 = ALT1 = ENET2_MDIO
  │  devmem 0x020E00DC = 0x14 → ENET1_TX_CLK = ALT4 = ENET1_REF_CLK1
  ▼
IOMUXC_SW_PAD_CTL_PAD_x  电气特性（驱动强度/上拉/速率）
  ▼
CCM_CCGRx / CCM_ANALOG   给 FEC 与 PHY 提供时钟
  ▼
FEC_ECR / FEC_RCR        使能 MAC、选 RMII、定速率双工
  │  imx6ul-fec 带 FEC_QUIRK_ENET_MAC：
  │  RCR bit8=1 → RMII；bit9=0 → 100M、bit9=1 → 10M
  ▼
FEC_MII_SPEED            算 MDC 分频（由 IPG 时钟推出）
FEC_MII_DATA             发 clause22 管理帧
  │  拼 ST|OP|PA|RA|TA 写入 MII_DATA，读回 PHY 寄存器
  ▼
PHY 侧 BMCR/BMSR/PHYIDR  自协商、链路状态、芯片 ID
  │  本项目读到 phy_id = 0x001cc816 → RTL8201F
  ▼
链路 up，ecr/rcr 按 100M-Full 重配 → 实测 91.7Mbps
```

**场景 B：中断从引脚到 CPU**

```
IOMUXC_SW_MUX_CTL_PAD_x   引脚切为 GPIO
GPIOx_ICR                 选边沿/电平（e.g. GPIO1_IO09 下降沿）
GPIOx_IMR                 解除该 bit 屏蔽
GPIOx_ISR                 事件置位 → 聚合拉高 bank 中断线
GICD_ISENABLER/ICFGR      在 GIC 侧使能并配类型
GICC_IAR / GICC_EOIR      应答与结束
CP15 VBAR                 指向异常向量，CPU 才能跳进来
```

对应本板 IRQ 39/48/152/168 四个节点，以及 `gpio-mxc` 里
`irq_gc_ack_set_bit`（写 ISR 清标志）、`irq_gc_mask_clr_bit`（写 IMR 屏蔽）。

**场景 C：上电启动到内核**

```
SRC_SBMR1/2     BOOT_MODE/GPIO 拨码决定从 eMMC 还是 SD 启动
  ▼ Boot ROM
MMDC_MDCTL/MDCFG/MDSCR   DDR 初始化与训练（U-Boot SPL 里做）
CCM PLL/CBCDR           把核、DDR、外设时钟配到目标频率
IOMUXC                  配 UART、eMMC、DDR 引脚
UART_UCR1..4/UFCR/UBIR   配控制台波特率（ttymxc0, 115200）
CP15 SCTLR/VBAR/TTBR     MMU、Cache、异常向量就绪
  ▼
跳转内核；内核启动日志 "Reset cause: POR" 就是 SRC_SRSR 的解读
```

**场景 D：低功耗与唤醒、看门狗兜底**

```
运行态：WDOG_WCR 使能看门狗，WDOG_WSR 定时写 0x5555/0xAAAA 喂狗
        （本项目 &wdog1 带 fsl,wdog_b，WDOG1_WDOG_ANY 引脚
         经 LCD_RESET 焊盘 ALT 复用输出，可复位外部电路）
  ▼
进入挂起：SNVS_LPCR 配低功耗、back 键 dts 标 wakeup-source
          → enable_irq_wake() → GPIO ICR/IMR 与 GIC 保持唤醒能力
  ▼
按键唤醒：SNVS 电源键驱动读 HPSR bit6 判断"是谁按的"，
          读 LPSR bit18（SPO）识别关机事件，写 LPSR 清除
  ▼
关机：syscon-poweroff 写 SNVS_LPCR(0x38) 的 mask 0x61 拉低电，
      同时 WDOG 停止喂狗作为兜底复位
```

**场景 E：定时器与时钟源**

```
CCM 选 osc_per / ipg 作为时钟源
  ▼
GPT_CR（EN/CLKSRC/PRESCALER 使能与分频）
GPT_SR / GPT_IR（状态与中断）
GPT_OCR + GPT_CNT（比较匹配，产生周期性中断）
  ▼
内核 tick / 定时任务；设备树里 gpt1 的 clock-names 就是
"ipg" 与 "osc_per"，正好对应这两个时钟输入
```

### 5. 这些寄存器在项目里怎么访问

三种方式，我在排查里都用过：

- **板端 `devmem`**：`devmem 0x020E0074 32` 读 IOMUXC，
  这是当时定位 MDIO 引脚被 ENET2 占用的关键手段；
  `devmem 0x020E0074 32 0x1` 也能写（但引脚寄存器一般不这么改）。
- **驱动里 `ioremap` + `readl/writel`**：`fec_main.c`、
  `gpio-mxc.c`、`snvs_pwrkey.c` 都是这样按偏移操作。
- **设备树 + syscon/regmap**：SNVS、IOMUXC_GPR 是 `syscon`，
  多个驱动共享（电源键、poweroff、RTC、音频的 gpr 属性都是同一块寄存器）。

一条纪律：改寄存器必须用**读-改-写**（对应 `clrsetbits_le32` /
`regmap_update_bits`），别整字覆写；CCM/SNVS/WDOG/MMDC 这几处写错
要么立刻复位、要么再也起不来。

### 6. 一句话总结

主控是 ARMv7-A 架构的单核 **Cortex-A7** —— NXP **i.MX6ULL**
（rev1.1，本板 396MHz，512MiB DDR3L，`MIDR=0x410fc075`）。
寄存器分两类：一类是核内 CP15 系统寄存器（SCTLR、VBAR、TTBR、CPACR…），
一类是通过 AIPS 桥映射的 SoC 外设 MMIO 寄存器
（IOMUXC/IOMUXC_GPR、CCM、SRC、GPC、SNVS、WDOG、GPIO、GIC、FEC、MMDC、
USDHC、UART、I2C、eCSPI、LCDIF、ADC…）。
最关键的几张"命门寄存器"是引脚复用的 `SW_MUX_CTL_PAD`/`SW_PAD_CTL_PAD`、
管 ENET 参考时钟的 `IOMUXC_GPR1`、管外设时钟的 `CCM_CCGRx`、
管复位与启动的 `SRC_SRSR/SBMR`、管开关机唤醒的 `SNVS_LPCR/HPSR/LPSR`、
管看门狗的 `WDOG_WCR/WSR`，以及中断三件套
`GPIOx_ICR/IMR/ISR` + `GICD/GICC`。
本项目里最完整的一次协作链是：
`GPR1` 选 REF_CLK → `MUX/PAD` 复用 MDIO/MDC 与 RMII 引脚 →
`CCM` 给时钟 → `FEC_ECR/RCR` 选 RMII 与速率 →
`FEC_MII_SPEED/MII_DATA` 走 MDIO → PHY 的 `BMCR/BMSR/PHYIDR`
完成自协商与识别，最后 100M-Full 链路跑到 91.7Mbps。

## Q7. ARMv7 的寄存器

### 1. ARMv7 的"寄存器"分三层，不能混着说

| 层次 | 内容 | 访问方式 |
|---|---|---|
| 通用/状态寄存器 | R0~R15、CPSR、SPSR_<mode> | 普通指令 + `MRS/MSR` |
| CP15 系统控制寄存器 | CRn c0~c15（体系结构定义） | `MRC/MCR` |
| 扩展寄存器 | VFP/NEON 的 D0~D31/Q0~Q15、FPSCR、FPEXC | VFP/NEON 指令 |

### 2. 通用寄存器与程序状态寄存器

- **R0~R12**：通用数据/地址寄存器。ARM 只有 16 个可直接寻址的寄存器，
  所以函数调用要靠压栈保存现场。
- **R13 = SP**，**R14 = LR**，**R15 = PC**。
  有一点和 x86 很不一样：**读 PC 得到的不是当前指令地址**，
  ARM 状态下是"当前指令 + 8"，Thumb 状态是"当前指令 + 4"，
  因为流水线已经把 PC 提前取了；手写汇编时这里最容易踩坑。
- **CPSR**（Current Program Status Register）不能当普通寄存器用，
  只能用 `MRS`/`MSR` 读写，字段包括：

| 字段 | 含义 |
|---|---|
| N/Z/C/V | 条件标志（负/零/进位/溢出） |
| Q、GE | 饱和标志、SIMD 比较结果 |
| IT[7:2] | Thumb-2 条件执行块状态 |
| J、E、A | Jazelle、数据端序、异步中止屏蔽 |
| **I、F** | **IRQ 屏蔽、FIQ 屏蔽**（异常入口硬件自动置位） |
| **T** | ARM/Thumb 状态 |
| **M[4:0]** | **处理器模式** |

- **SPSR_<mode>**：异常发生时硬件把异常前的 CPSR 存进对应模式的 SPSR，
  由 `RFE`/`SUBS PC, LR` 在返回时恢复，所以中断屏蔽位和条件标志
  都能自动还原，不需要软件手工记。

### 3. 处理器模式与"分组寄存器"

ARMv7-A 的模式：`USR`、`FIQ`、`IRQ`、`SVC`（Supervisor）、
`MON`（Monitor，TrustZone）、`ABT`、`HYP`（虚拟化扩展）、`UND`、`SYS`。

关键在"分组（banked）"：

- 每种异常模式有**自己独立的 SP、LR、SPSR**，
  所以 IRQ 来的时候不用先保存用户栈指针就能切到自己的栈，响应才快。
- **FIQ 额外分组 R8~R12**，这就是"快速中断"的由来：
  高优先级加独立通用寄存器，几乎不用保存现场。

本板的证据是启动日志里的 `CPU: All CPU(s) started in SVC mode.`：
内核跑在 SVC 模式，用户程序跑在 USR，每来一次中断硬件自动切到 IRQ 模式，
用 IRQ 的 SP/LR，把原 CPSR 存进 SPSR_irq。

### 4. CP15：体系结构定义的 16 组系统寄存器

用 `MRC/MCR p15, op1, Rt, CRn, CRm, op2` 访问，`CRn` 是主编号：

| CRn | 寄存器 | 作用 |
|---|---|---|
| c0 | MIDR、CTR、CCSIDR、CLIDR、CSSELR、MPIDR、REVIDR | 芯片/核识别、Cache 层级与行大小 |
| c1 | **SCTLR**、ACTLR、**CPACR** | MMU/Cache 总开关、NEON 使能 |
| c2 | **TTBR0、TTBR1、TTBCR** | 一级页表基址与地址空间划分 |
| c3 | **DACR** | 域访问控制（权限） |
| c4 | 实现定义 | 各核不同 |
| c5 | DFSR、IFSR | 数据/取指异常状态 |
| c6 | DFAR、IFAR | 出错地址（内核 oops 里的 fault address） |
| c7 | 缓存维护 | ICIALLU、DCCMVAC、DCIMVAC 等 |
| c8 | TLB 维护 | TLBIALL、TLBIMVA 等 |
| c9 | PMU、Cache lockdown | PMCR、PMCCNTR、PMCNTENSET |
| c10 | PRRR、NMRR、TLB lockdown | 内存区属性（VMSA） |
| c12 | **VBAR**、MVBAR | 异常向量表基址 |
| c13 | **CONTEXTIDR**、TPIDRURW/TPIDRURO/TPIDRPRW | ASID、TLS、per-CPU 指针 |
| c14 | 调试寄存器 | 断点/观察点 |
| c15 | CBAR 等 | 外设基址、实现定义 |

### 5. 把 SCTLR 拆到每一位（本工程可验证的深度点）

内核里 v7 两级页表的模板写在 `arch/arm/mm/proc-v7-2level.S`：

```asm
v7_crval:
        crval   clear=0x2120c302, mmuset=0x10c03c7d, ucset=0x00c01c7c
```

而本板启动日志打印的是 `cr=10c5387d`。差在哪，两处都能解释清楚：

1. 本工程 `CONFIG_SWP_EMULATE=y`（`build/kernel/.config` 里明确开着），
   `proc-v7.S` 里有 `bic r6, r6, #(1 << 10)`，把模板里的
   bit10（F，SWP/SW 使能）清掉——内核用异常模拟 SWP，不让硬件直接执行。
2. `0x10c5387d - 0x10c0387d = 0x0005_0000`，正好是 **bit16 和 bit18**，
   这两位在 Cortex-A7 上属于实现定义/只读为 1 的位，写不进去、
   读出来固定是 1。

拆开看关键位：

| 位 | 名称 | 值 | 含义 |
|---|---|---|---|
| 0 | M | 1 | **MMU 已开** |
| 1 | A | 0 | 对齐异常关闭（允许非对齐访问） |
| 2 | C | 1 | **D-Cache 已开** |
| 3 | W | 1 | 写缓冲使能 |
| 12 | I | 1 | **I-Cache 已开** |
| 13 | V | 1 | **向量表在 0xFFFF_0000** |
| 22 | U | 1 | 非对齐访问允许 |
| 23 | XP | 1 | 扩展页表（ARMv7 二级页表格式） |
| 28 | TRE | 1 | TEX 重映射使能 |

### 6. 典型场景里寄存器怎么配合

**场景 A：建立虚拟内存（启动早期）**

```
c0/MIDR 读出 0x410fc075
  → proc-v7.S 用 .long 0x410fc070 + mask 0xff0ffff0 匹配 Cortex-A7
    （掩码故意忽略 revision 字段，所以 r0p5 也能匹配上）
  → 取 v7_crval 模板
c2/TTBR0、TTBR1、TTBCR   建好内核/用户一级页表
c3/DACR                  设域权限：traps.c 的 early_trap_init() 末尾
                         就调用 modify_domain(DOMAIN_USER, DOMAIN_CLIENT)，
                         底层是 mcr p15,0,r,c3,c0
c1/SCTLR                 M/C/I 置 1 → 虚拟内存与 Cache 正式生效
c12/VBAR 与 V 位         把异常向量固定到 0xFFFF_0000
                         early_trap_init() 里 memcpy((void *)vectors,
                         __vectors_start, ...)，注释写明 mapped at 0xffff0000
```

**场景 B：异常与中断**

```
entry-armv.S 的向量表（8 项，顺序固定）：
  reset / undefined / SVC(软中断) / prefetch abort /
  data abort / address exception(保留) / IRQ / FIQ
  ▼ 硬件动作
CPSR 的 I 位自动置 1（关 IRQ），T/E 位按异常要求设好
原 CPSR 存入 SPSR_irq，返回地址存入 LR_irq，切到 IRQ 模式用 IRQ 自己的 SP
  ▼ 软件
按 VBAR 跳到 vector_irq → 把 R0-R12、LR 存到栈
→ 调 set_handle_irq 注册的 gic_handle_irq（Q3 那条链）
  ▼ 返回
恢复 R0-R12，把 SPSR_irq 写回 CPSR（恢复 I 位与原模式），PC = LR
```

本板 IRQ 39/48/152/168 就落在这条链上，`/proc/interrupts` 的计数
本质就是这条软硬件路径每走一次加一。

**场景 C：进程切换与"每线程 / 每 CPU"数据**

- 切换进程要保存/恢复 R0~R15 与 CPSR（内核 `cpu_switch_to`）。
- `c2/TTBR0` 换用户页表，`c13/CONTEXTIDR` 换 ASID；
  ASID 让 TLB 不必每次全刷，而是按地址空间打标签。
- TLS：用户线程指针放在 `TPIDRURW/TPIDRURO`
  （`arch/arm/include/asm/tls.h`），这是 glibc `pthread_self()` 快的来源。
- 每 CPU 数据：`arch/arm/include/asm/percpu.h` 明确写着
  "we store the per cpu offset in the TPIDRPRW"，
  代码就是 `mcr p15, 0, r, c13, c0, 4`，`__my_cpu_offset()` 再读回来。

**场景 D：用户态浮点与 NEON 加速**

```
c1/CPACR 使能 CP10/CP11（内核 vfp 初始化时做）
VFP/NEON 用 D0~D31 / Q0~Q15 运算，FPSCR 记状态与舍入模式
本工程 .config: CONFIG_VFP=y、CONFIG_VFPv3=y、CONFIG_NEON=y
用户态落地：libjpeg-turbo（turbojpeg ARM 运行时）、Qt 的图形合成
```

**场景 E：Cache/TLB 维护**

DMA 收发（本项目 FEC 网卡）、模块加载、`mmap` 改属性时，
内核用 `c7`（如 `DCCMVAC` 清到 PoC）、`c8`（如 `TLBIMVA`）做一致性操作。
ARM 的 I/D Cache 不做硬件一致，DMA 缓冲必须显式 clean/invalidate，
这是 ARM 板级驱动比 x86 更容易出错的地方。

### 7. 一句话总结

ARMv7 的寄存器分三层。第一层是程序可见的 R0~R15 与 CPSR/SPSR：
R13/R14/R15 是 SP/LR/PC，读 PC 会拿到"当前指令 +8/+4"，
CPSR 的 M[4:0] 选模式、I/F 控制中断屏蔽，各异常模式有独立的
SP/LR/SPSR，FIQ 还额外分组 R8~R12。第二层是 CP15 的 c0~c15：
识别用 c0/MIDR（本板 0x410fc075），总开关用 c1/SCTLR
（本板 0x10c5387d，可用 CONFIG_SWP_EMULATE 与 A7 只读位完整解释），
页表 c2、域权限 c3、异常状态与地址 c5/c6、Cache/TLB 维护 c7/c8、
向量基址 c12/VBAR、ASID 与线程及每 CPU 指针 c13。
第三层是 VFP/NEON 的 D/Q 寄存器。三层配合起来，才构成
"启动建页表开 MMU → 异常/中断进出 → 进程切换 → 用户态 NEON 加速"
这条完整链路。

## Q8. 结合项目，说明启动链路的完整流程

### 1. 先给全貌

本板的启动是**三级接力**（没有 SPL，这点和很多人默认的不一样）：

```
上电复位
  ▼
Boot ROM（芯片内固化）
  │ 读 BOOT_MODE/拨码 → 决定从 SD 还是 eMMC 启动
  │ 从启动介质读 u-boot.imx，执行 IVT + DCD
  │ DCD 里就把 CCM 时钟开好、DDR3 初始化并训练好
  ▼
U-Boot proper（deploy/tftp/u-boot.imx，310272 字节）
  │ 串口 banner → 板级初始化 → bootdelay
  │ bootcmd: 从 eMMC FAT 读 zImage 和 dtb
  ▼
Linux zImage（deploy/tftp/zImage）+ dtb（imx6ull-alientek-jjl.dtb）
  │ 自解压 → head.S 建页表开 MMU → start_kernel
  │ 设备树解析 → 各驱动 probe（FEC/PHY、LCD、I2C 触摸、SD、USB…）
  ▼
挂根文件系统：root=/dev/nfs，nfsroot=192.168.31.218:.../deploy/nfs/rootfs
  ▼
init=/linuxrc → BusyBox init → /etc/inittab → rcS → getty
  ▼
应用：Qt5(LinuxFB)、mjpg-streamer+libjpeg-turbo、mplayer/ALSA、VehicleSystem
```

### 2. 阶段 0：上电与 Boot ROM

- 复位类型由 `SRC_SRSR` 记录，本板日志是 `Reset cause: POR`。
- 引脚拨码/`BOOT_MODE` 经 `SRC_SBMR` 反映，决定从
  **SD 卡还是 eMMC** 启动；eMMC 上 U-Boot 写在 boot0 与用户区**起始扇区 2**。
- Boot ROM 是芯片内固化的（不是我们编译的），它只认
  **IVT（Image Vector Table）+ DCD（Device Configuration Data）**这个头。

### 3. 阶段 1：IVT + DCD —— 本板启动最容易忽略的一环

`deploy/tftp/u-boot.imx` 是 **310272 字节**，`u-boot.bin` 是 **303464 字节**，
差的 6808 字节就是 IVT/DCD 头。这个头在
`sources/uboot-imx/board/freescale/mx6ull_alientek_jjl/imximage.cfg` 里定义，
里面 `IMAGE_VERSION 2`、`BOOT_FROM sd`，后面是 **60 条 `DATA` 写寄存器**：

```
/* Enable all clocks */
DATA 4 0x020c4068 0xffffffff   /* CCM_CCGR0 */
...
DATA 4 0x020c4080 0xffffffff   /* CCM_CCGR6，7 个 CCGR 全开 */

DATA 4 0x020E04B4 0x000C0000   /* IOMUXC：DDR 相关 PAD 复用 */
DATA 4 0x020E0250 0x00000030   /* DDR PAD 电气参数（驱动/ODT/SDQS…） */
...

DATA 4 0x021B0004 0x0002002D   /* MMDC_MDCFG0：DDR3 时序 */
DATA 4 0x021B000C 0x676B52F3   /* MMDC_MDCFG2 */
DATA 4 0x021B0018 0x00201740   /* MMDC_MDMISC */
DATA 4 0x021B0800 0xA1390003   /* MMDC_MPWLDECTRL0：写均衡 */
DATA 4 0x021B083C 0x41640158   /* 读 DQS 门控/延迟 */
DATA 4 0x021B082C 0xf3333333   /* DQS 延迟 */
DATA 4 0x021B001C 0x02008032   /* MMDC_MDSCR：MPZDL/MPRDDL 校准序列 */
...
DATA 4 0x021B0000 0x84180000   /* MMDC_MDCTL：最后使能控制器 */
```

也就是说：**Boot ROM 在跳进 U-Boot 之前，已经把时钟和 512MiB DDR3
配好并做完训练了**。这就是为什么本板不需要 SPL
（`build/uboot` 下没有 SPL 产物，defconfig 也没开 SPL），
DDR 初始化由 DCD 而不是 SPL 承担——这一层比"U-Boot 做了 DDR 初始化"的说法准确得多。

### 4. 阶段 2：U-Boot proper

从启动日志（带时间戳）看得很清楚：

```
[   5.589] U-Boot 2016.03-00003-g9f8ef6d-dirty (Sep 29 2026 - 20:30:17 +0800)
[   5.594] CPU:   Freescale i.MX6ULL rev1.1 69 MHz (running at 396 MHz)
[   5.609] CPU:   Industrial temperature grade (-40C to 105C) at 50C
[   5.612] Board: MX6ULL ALIENTEK JJL
[   5.616] DRAM:  512 MiB
[   5.683] MMC:   FSL_SDHC: 0, FSL_SDHC: 1
[   5.944] mmc1(part 0) is current device
[   7.271] reading zImage
[   7.412] reading imx6ull-alientek-jjl.dtb
[   7.451] Starting kernel ...
```

做的事按顺序是：

1. **串口控制台**：`ttymxc0` 115200，打 banner。
2. **CPU/DRAM/MMC 识别**：确认 DDR 已由 DCD 配好（512 MiB），
   两个 SDHC 控制器在线（FSL_SDHC 0/1）。
3. **板级 IOMUX 与时钟**：`mx6ull_alientek_jjl.c` 里
   `setup_iomux_uart` / `usdhc*_pads` / `setup_iomux_fec`；
   FEC 那段还用 `clrsetbits_le32(&iomuxc_regs->gpr[1], ...)`
   选 ENET 的 50M REF_CLK 来源，并 `enable_fec_anatop_clock()`。

## Q9. 详解内核自解压、head.S 匹配 Cortex-A7、建页表开 MMU（SCTLR=0x10c5387d）

### 1. 起点：bootz 交接到 zImage 时的约定

U-Boot `bootz` 跳转时保证：

- `r0 = 0`
- `r1 = machine type`
- `r2 = dtb 物理地址`（本板是 0x83000000）
- **MMU 关、D-cache 关**，I-cache 无所谓
- CPU 在 SVC 模式

这时 PC 指向 zImage 的**解压桩**（不是真正的内核）。

### 2. 第一阶段：zImage 自解压（arch/arm/boot/compressed/head.S）

**① 为什么是两段式**：zImage = 一小段位置无关的"解压程序"
+ "压缩过的内核" + 末尾 4 字节记录解压后大小。
真正的内核（含 `head.S`）是解压出来的。

**② 入口处的前 8 条 `mov r0, r0`**：这是历史包袱——早期 ARM
用 `mov r0,r0` 造 NOP 填充，后面 4 个字是
`_magic_sig / _magic_start / _magic_end / 0x04030201` 魔数，
供 bootloader 识别 zImage 身份与端序。

**③ 保存参数、确保 SVC 模式**：

```asm
mov  r7, r1                  @ 保存 machine id
mov  r8, r2                  @ 保存 dtb 指针
safe_svcmode_maskall r0      @ 确保 SVC 模式、屏蔽 IRQ/FIQ
msr  spsr_cxsf, r9           @ 把原始启动模式存进 SPSR（HYP 回跳用）
```

**④ 计算"内核最终要放到哪里"——本板关键的一步**：

```asm
#ifdef CONFIG_AUTO_ZRELADDR      @ 本工程 =y
        mov  r4, pc
        and  r4, r4, #0xf8000000 @ 取当前物理地址的 128MB 对齐高位
        add  r4, r4, #TEXT_OFFSET
#else
        ldr  r4, =zreladdr
#endif
```

本板 `TEXT_OFFSET = 0x00008000`（`arch/arm/Makefile` 里
`textofs-y := 0x00008000`），DDR 从 0x8000_0000 起，
所以 **r4 = 0x8000_8000**，这就是内核的解压目标地址，
对应日志里的 `.init : 0x808cb000 - 0x8092c000` 与
`Freeing unused kernel memory: 388K (808cb000 - 8092c000)`。

**⑤ 判断是否需要"自己搬自己"**：如果解压目标和当前位置重叠
（比如 zImage 恰好被 load 在 0x8000_8000），就必须先把自己挪走再解压；
`head.S` 里 `restart:` 之后那段重定位代码（含 GOT 表修正）就是干这个的。
本板 zImage 载在 0x8080_0000，与目标 0x8000_8000 不重叠，
所以走 `cache_on`：**临时建一张 1MB 段的页表把 cache 打开**，
让解压过程快得多。

**⑥ 解压**：

```c
/* arch/arm/boot/compressed/misc.c */
decompress_kernel(output_start, free_mem_ptr, free_mem_end, arch_id)
{
        output_data = (unsigned char *)output_start;   /* 0x80008000 */
        ...
        putstr("Uncompressing Linux...");
        ret = do_decompress(input_data, input_data_end - input_data,
                            output_data, error);        /* gzip 解压 */
}
```

**⑦ 交棒前把 cache 关掉**：

```asm
bl  decompress_kernel
bl  cache_clean_flush
bl  cache_off                 @ 内核入口约定 MMU/D-cache 必须是关的
mov r1, r7                    @ 恢复 machine id
mov r2, r8                    @ 恢复 dtb
__enter_kernel:
        mov r0, #0            @ must be 0
        mov pc, r4            @ 跳到 0x80008000，ARM 状态
```

本板日志证据：`Starting kernel ...`（7.451s）到
`Booting Linux on physical CPU 0x0`（8.264s）相隔 **0.81s**，
这就是"自解压 + 早期初始化"的耗时。日志里看不到
`Uncompressing Linux...`，是因为这份配置没把解压阶段的
串口输出（`DEBUG_LL` 相关 putc）编进去。

### 3. 第二阶段：head.S 入口与 Cortex-A7 匹配

解压出来的内核入口是 `arch/arm/kernel/head.S` 的 `ENTRY(stext)`，
虚拟地址 = `PAGE_OFFSET + TEXT_OFFSET`。

```asm
ENTRY(stext)
        safe_svcmode_maskall r9      @ 确认 SVC 模式 + 屏蔽 IRQ/FIQ
        mrc     p15, 0, r9, c0, c0   @ 读 MIDR = 0x410fc075
        bl      __lookup_processor_type
        movs    r10, r5              @ r5 = 命中的 procinfo 指针
        beq     __error_p            @ 不认识就打印 'p' 挂掉
```

`__lookup_processor_type`（head-common.S）的逻辑：

```asm
__lookup_processor_type:
        adr     r3, __lookup_processor_type_data
        ldmia   r3, {r4 - r6}        @ r5=__proc_info_begin r6=__proc_info_end
        sub     r3, r3, r4           @ virt→phys 偏移（此时 MMU 还没开）
        add     r5, r5, r3
        add     r6, r6, r3
1:      ldmia   r5, {r3, r4}         @ r3=value, r4=mask
        and     r4, r4, r9           @ mask & MIDR
        teq     r3, r4
        beq     2f                   @ 命中
        add     r5, r5, #PROC_INFO_SZ
        cmp     r5, r6
        blo     1b
        mov     r5, #0               @ unknown processor
2:      ret     lr
```

`proc-v7.S` 里 Cortex-A7 的表项：

```asm
__v7_ca7mp_proc_info:
        .long   0x410fc070           @ value
        .long   0xff0ffff0           @ mask
        __v7_proc __v7_ca7mp_proc_info, __v7_ca7mp_setup
```

`0x410fc075 & 0xff0ffff0 = 0x410fc070`——**掩码故意抹掉 revision 字段，
所以 r0p5 也能匹配**。命中后 `r10` 指向 `__v7_ca7mp_proc_info`，
里面有 MMU flags、processor functions 和
`PROCINFO_INITFUNC`（即 `__v7_ca7mp_setup`）。
匹配不上会走到 `__error_p` 打印一个 `p`，
这就是很多人见过的"内核只打个 p 就死"的来源。

紧接着算 PHYS_OFFSET：

```asm
        adr     r3, 2f
        ldmia   r3, {r4, r8}
        sub     r4, r3, r4           @ (PHYS_OFFSET - PAGE_OFFSET)
        add     r8, r8, r4           @ PHYS_OFFSET
2:      .long   .
        .long   PAGE_OFFSET
```

本工程 `CONFIG_VMSPLIT_2G=y`、`CONFIG_PAGE_OFFSET=0x80000000`，
DDR 也从 0x80000000 起，所以
**PAGE_OFFSET == PHYS_OFFSET == 0x80000000，内核 RAM 的虚拟地址等于物理地址**。
这解释了为什么日志里的 `808cb000` 这类地址既是虚拟也是物理——
2G/2G 分割加 `CONFIG_ARM_PATCH_PHYS_VIRT=y` 的结果，不是打印错误。

之后还有两个补丁动作：`__vet_atags` 校验 `r2` 指向的 dtb
（magic `0xd00dfeed` 或 ATAGS）；`__fixup_smp`
（`CONFIG_SMP_ON_UP=y`）和 `__fixup_pv_table`
（`CONFIG_ARM_PATCH_PHYS_VIRT=y`）在运行时改写指令，
把编译期假设的物理/虚拟偏移修正成实际值。

### 4. 第三阶段：__create_page_tables 建临时粗糙页表

**① 页表放在哪**：

```asm
#define KERNEL_RAM_VADDR  (PAGE_OFFSET + TEXT_OFFSET)   /* 0x80008000 */
        .equ swapper_pg_dir, KERNEL_RAM_VADDR - PG_DIR_SIZE
        .macro pgtbl, rd, phys
        add  \rd, \phys, #TEXT_OFFSET
        sub  \rd, \rd, #PG_DIR_SIZE
        .endm
```

非 LPAE 时 `PG_DIR_SIZE = 0x4000`（16KB = 4096 项 × 4 字节），
所以**初始一级页表在 0x80004000**，正好卡在内核镜像
（0x80008000）下面 16KB。head.S 里还有
`#error KERNEL_RAM_VADDR must start at 0xXXXX8000` 保证这个布局成立。

**② 表里写了什么**：先把 16KB 清零，然后建三类映射，
全部用 **1MB 段映射（section）**，因为此时只求"能跑起来"：

| 映射 | 目的 | 对应代码 |
|---|---|---|
| identity mapping（虚拟==物理） | 覆盖 `__turn_mmu_on`（放在 `.idmap.text`） | `adr r0, __turn_mmu_on_loc; ...; str r3, [r4, r5, lsl #PMD_ORDER]` |
| RAM 映射 | 从 0x80000000 映射到 `_end`（.bss 末），内核代码/数据才能访问 | `orr r3, r8, r7; str r3, [r0], #1 << PMD_ORDER` 逐段 +1MB |
| boot params 映射 | 把 dtb/ATAGS 所在的两个 section 也映射进来 | 注释 "We map 2 sections in case the ATAGS/DTB crosses a section boundary" |

其中 `r7 = PROCINFO_MM_MMUFLAGS`，内容是
`PMD_TYPE_SECT | PMD_SECT_AP_WRITE | PMD_SECT_AP_READ | PMD_SECT_AF`
（段的读写权限 + Access Flag）。L1 表项下标由
`PAGE_OFFSET >> SECTION_SHIFT = 0x80000000 >> 20 = 0x800` 得到，
即 RAM 映射落在第 0x800 项，正好是 4GB 地址空间里 2GB 之后那一段。

**③ 为什么必须有 identity mapping**：接下来要写 SCTLR 打开 MMU，
而**写 SCTLR 之后，流水线里已在取的下一条指令仍然按物理地址计算**。
所以必须保证"这段代码的虚拟地址等于物理地址"，
`__turn_mmu_on` 才被单独放进 `.idmap.text` 段。
这张 identity map 是临时的，后面 `paging_init()` 会把它删掉。

### 5. 第四阶段：CPU setup 决定"要写进 SCTLR 的值"

head.S 用一条位置无关的间接调用进入处理器专属代码：

```asm
        ldr  r13, =__mmap_switched      @ 打开 MMU 后要跳去的虚拟地址
        adr  lr, BSYM(1f)
        mov  r8, r4                     @ TTBR1 = swapper_pg_dir
        ldr  r12, [r10, #PROCINFO_INITFUNC]   @ = __v7_ca7mp_setup
        add  r12, r12, r10
        ret  r12
1:      b    __enable_mmu
```

`__v7_ca7mp_setup` → `__v7_setup`（proc-v7.S）做这些事：

```asm
        mcr p15, 0, r10, c7, c5, 0      @ 清 I-cache + BTB
        mcr p15, 0, r10, c8, c7, 0      @ 清 I/D TLB
        v7_ttb_setup r10, r4, r8, r5    @ 配 TTBCR / TTBR0 / TTBR1
        mcr p15, 0, r5, c10, c2, 0      @ 写 PRRR（内存区域属性）
        mcr p15, 0, r6, c10, c2, 1      @ 写 NMRR
        adr r5, v7_crval
        ldmia r5, {r5, r6}              @ r5=clear, r6=mmuset
#ifdef CONFIG_SWP_EMULATE
        orr r5, r5, #(1 << 10)          @ clear 掩码加上 bit10
        bic r6, r6, #(1 << 10)          @ mmuset 里去掉 bit10
#endif
        mrc p15, 0, r0, c1, c0, 0       @ 读当前 SCTLR
        bic r0, r0, r5                  @ 清掉 clear 掩码中的位
        orr r0, r0, r6                  @ 置上 mmuset 中的位
        ret lr                          @ r0 = 待写入 SCTLR 的值
```

`v7_crval` 来自 `proc-v7-2level.S`：
`clear=0x2120c302, mmuset=0x10c03c7d`。
`CONFIG_SWP_EMULATE=y` 让 bit10 从 mmuset 里被清掉 →
实际"要置的位"是 `0x10c0387d`。
这一步**还没有真正开 MMU**，只是把要写入的值算好放在 r0 里。

### 6. 第五阶段：__enable_mmu 与 __turn_mmu_on

```asm
__enable_mmu:
        bic  r0, r0, #CR_A              @ A=0，允许非对齐访问
        mov  r5, #(domain_val(DOMAIN_USER, DOMAIN_MANAGER) | \
                   domain_val(DOMAIN_KERNEL, DOMAIN_MANAGER) | \
                   domain_val(DOMAIN_TABLE, DOMAIN_MANAGER) | \
                   domain_val(DOMAIN_IO, DOMAIN_CLIENT))
        mcr  p15, 0, r5, c3, c0, 0      @ 写 DACR（域权限）
        mcr  p15, 0, r4, c2, c0, 0      @ 写 TTBR0（页表物理地址）
        b    __turn_mmu_on

        .pushsection .idmap.text, "ax"
__turn_mmu_on:
        mcr  p15, 0, r0, c1, c0, 0      @ ★ 写 SCTLR：这条之后 MMU 生效
        mrc  p15, 0, r3, c0, c0, 0
        instr_sync
        mov  r3, r13                    @ r13 = __mmap_switched 的虚拟地址
        ret  r3
```

细节：

- **DACR 必须在开 MMU 前写好**，否则取指/取数会被域权限拦住。
- `__turn_mmu_on` 靠前面那张 identity map 活着；一写 SCTLR，
  MMU 立刻生效，随后跳到 `__mmap_switched` 的**虚拟地址**，
  完成"物理世界 → 虚拟世界"的切换。
- 此刻读出的 SCTLR = **0x10c5387d**：比"要置的位" 0x10c0387d
  多了 `0x0005_0000`，正是 Cortex-A7 上只读为 1 的
  bit16（DT）与 bit18（IT）。日志里的 `cr=10c5387d` 就是
  `__mmap_switched` 把它存进 `cr_alignment` 后打印出来的。

### 7. 第六阶段：__mmap_switched → start_kernel

```asm
__mmap_switched:
        adr r3, __mmap_switched_data
        ldmia r3!, {r4, r5, r6, r7}
        /* 拷贝 data 段（加载地址与链接地址不同时） */
1:      cmpne r5, r6
        ldrne fp, [r4], #4
        strne fp, [r5], #4
        bne 1b
        /* 清 BSS */
        mov fp, #0
1:      cmp r6, r7
        strcc fp, [r6], #4
        bcc 1b
        ldmia r3, {r4, r5, r6, r7, sp}   @ 取全局变量地址和栈顶
        str r9, [r4]                     @ processor_id
        str r1, [r5]                     @ __machine_arch_type
        str r2, [r6]                     @ __atags_pointer（dtb）
        strne r0, [r7]                   @ cr_alignment = SCTLR 值
        b   start_kernel
```

到这一步，异常向量还没搬、正式页表也还没建：
`start_kernel()` → `setup_arch()` → `paging_init()` →
`devicemaps_init()` 会用 **4KB 页 + 二级页表**重建完整映射
（外设 0x020E0000 IOMUXC、0x021B0000 MMDC 就是在这步映射进内核空间的），
并撤掉临时 identity map；`early_trap_init()` 把向量表装到 0xFFFF0000。
之后 GIC、定时器、各驱动才按 Q8 的顺序跑起来。

### 8. 本板这一段的关键数字（可直接背）

| 项目 | 值 | 来源 |
|---|---|---|
| MIDR | 0x410fc075 | 日志 `CPU: ARMv7 Processor [410fc075]` |
| 匹配 value / mask | 0x410fc070 / 0xff0ffff0 | `proc-v7.S` 的 `__v7_ca7mp_proc_info` |
| PAGE_OFFSET | 0x80000000 | `CONFIG_VMSPLIT_2G=y`、`CONFIG_PAGE_OFFSET=0x80000000` |
| PHYS_OFFSET | 0x80000000 | DDR 起始地址，PATCH_PHYS_VIRT 运行时修正 |
| TEXT_OFFSET | 0x00008000 | `arch/arm/Makefile` 的 `textofs-y` |
| KERNEL_RAM_VADDR | 0x80008000 | PAGE_OFFSET + TEXT_OFFSET |
| 初始页表 swapper_pg_dir | 0x80004000 | KERNEL_RAM_VADDR - 0x4000 |
| 解压目标（AUTO_ZRELADDR） | 0x80008000 | `(pc & 0xf8000000) + TEXT_OFFSET` |
| v7_crval | clear=0x2120c302, mmuset=0x10c03c7d | `proc-v7-2level.S` |
| 实际写入 SCTLR | **0x10c5387d** | 日志 `cr=10c5387d` |
| 自解压 + 早期初始化耗时 | 0.81s | `Starting kernel` 7.451s → `Booting Linux` 8.264s |

### 9. 一句话总结

zImage 是"解压桩 + 压缩内核"，桩在 MMU 关闭状态下用
`AUTO_ZRELADDR` 算出目标 0x80008000、必要时自搬、临时开 cache 解压，
解压后再关 cache 跳入内核入口；`head.S` 的 `stext` 先确保 SVC 模式
并屏蔽中断，用 MIDR 0x410fc075 以 mask 0xff0ffff0 匹配 0x410fc070
（Cortex-A7），算出 PHYS_OFFSET 与 PAGE_OFFSET 都是 0x80000000，
在 0x80004000 建一张 16KB 一级页表（只做 identity map、
内核 RAM 到 `_end`、dtb 三块 1MB 段映射），再调 `__v7_setup` 按
`v7_crval` 算出要写进 SCTLR 的位（`CONFIG_SWP_EMULATE` 清掉 bit10），
由 `__enable_mmu` 写 DACR/TTBR0 后在 `.idmap.text` 的
`__turn_mmu_on` 里真正写 SCTLR——读出 0x10c5387d
（多出的 bit16/bit18 是 A7 只读位），随后跳到 `__mmap_switched`
拷贝 data、清 BSS、设栈、记录 processor_id/machine/dtb/SCTLR，
最后进 `start_kernel()`；正式页表和异常向量要等之后的
`paging_init()` / `early_trap_init()` 才建立。

## Q10. 网络结构是怎样配合工作的

### 1. "网络结构"要分两层看

这个项目里的"网络"其实是两套东西叠在一起：

| 层 | 内容 | 参与方 |
|---|---|---|
| 部署/系统层 | IP 规划、NFS 根文件系统、TFTP、吞吐测试、视频流 | 开发板 + 主机 Ubuntu |
| 协议栈层 | socket → TCP/IP → netdev → FEC 驱动 → MAC → RMII → PHY → RJ45 | 内核 + 硬件 |

而且链路层往上还有**两套彼此独立的网络实现**：
U-Boot 自己的 `drivers/net/fec_mxc.c` + `net/tftp.c`（用于 TFTP 下载），
和 Linux 内核的 `drivers/net/ethernet/freescale/fec_main.c` + `net/`。
两者只在硬件（FEC + PHY）这一层共享，代码和协议栈各写各的——
所以 U-Boot 里能 TFTP，不代表内核里 NFS 一定能通，反之亦然。

### 2. 底层硬件链路（从下往上）

```
RJ45 ─ 隔离变压器 ─ RTL8201F(PHY) ─ RMII(2bit/50MHz) ─ FEC(ENET1) ─ AXI/AIPS ─ ARM 核
                        │                                  │
                   MDIO/MDC 管理总线                   DMA 描述符环
```

| 环节 | 本项目实际情况 |
|---|---|
| PHY | RTL8201F，MDIO 地址 1，PHY ID `0x001cc816`（Q1 排查过） |
| 参考时钟 | 50MHz REF_CLK，由 `IOMUXC_GPR1` 选源（U-Boot 里 `clrsetbits gpr[1]`） |
| 接口模式 | RMII，`RCR` bit8=1；速率 100M 时 bit9=0 |
| MAC | FEC/ENET1，基址 `0x020B_4000`，Linux 侧设备名 `20b4000.ethernet` |
| 中断 | FEC 中断 → GIC；PHY 自己的中断线没接（`irq=-1`），链路靠轮询 |
| 收发环 | **TX 512 个、RX 512 个描述符**（`TX_RING_SIZE=512`，`RX_RING_SIZE = 4096/2048 × 256 = 512`） |
| 链路状态 | 100Mbps / Full / MTU 1500 / 实测 91.7Mbps（线速 91.8%） |

FEC 寄存器在这一层怎么配合，Q6 场景 A 已经串过一遍：
`ECR` 使能、`RCR` 选 RMII 与速率、`MII_SPEED` 算 MDC 分频、
`MII_DATA` 收发 clause22 管理帧、`IMASK/IEVENT` 管中断、
`R_DES_START/X_DES_START` 放描述符环、`RDAR/TDAR` 通知硬件有新描述符。

### 3. Linux 网络子系统的分层与数据结构

```
应用: socket API / sendmsg / recvmsg / read / write
  ▼
协议族: AF_INET/AF_INET6 → TCP/UDP/ICMP/ARP (net/ipv4/*, net/core/*)
  ▼
netdev 抽象层: struct net_device, dev_queue_xmit(), netif_receive_skb()
  ▼
驱动: fec_main.c 的 net_device_ops
  ▼
硬件: DMA 描述符环 + FEC + PHY
```

几个必须点名的结构：

| 结构 | 作用 |
|---|---|
| `sk_buff` | 网络包的载体，数据缓冲 + 各层协议头指针 + 校验和/GSO 标记 |
| `net_device` | 一个网络接口的抽象，`eth0` 就是它的一个实例 |
| `net_device_ops` | 驱动能力表，本工程：`ndo_open/ndo_stop/ndo_start_xmit/ndo_set_rx_mode/ndo_do_ioctl/ndo_tx_timeout` |
| `napi_struct` | 中断与轮询的结合体，`netif_napi_add(..., fec_enet_rx_napi, NAPI_POLL_WEIGHT)` |
| `phy_device` / `mii_bus` | PHY 抽象与管理总线，`libphy` 负责匹配和状态机 |
| `qdisc` | 发送侧排队/调度层，默认 `pfifo_fast` |

### 4. 发送路径（以本项目的 100MiB nc 吞吐测试为例）

板端执行 `dd if=/dev/zero bs=1M count=100 | nc 192.168.31.218 9000`：

```
dd/nc 写出数据
  ▼ write() → sendmsg() → tcp_sendmsg()
TCP 组 sk_buff、填 TCP 头、算校验和（或标记交给硬件）
  ▼ ip_queue_xmit() → ip_output()
IP 层填 IP 头、选出口 eth0、查路由
  ▼ dev_queue_xmit() → qdisc（pfifo_fast）
  ▼ ndo_start_xmit = fec_enet_start_xmit()
  │  fep->txq 取空闲描述符，dma_map_single，填 cbd_bufaddr/cbd_datlen
  │  返回 NETDEV_TX_OK
  ▼ 写 TDAR 通知 FEC 发数据
FEC 从 DDR 读描述符 + 数据 → RMII → PHY → 网线
  ▼ 发完置 IEVENT 的 TX 位 → fec_enet_interrupt
fec_enet_tx() 回收描述符、dma_unmap、dev_kfree_skb()，唤醒队列
```

实测 100MiB / 9.143s = **91.7Mbps**，占 100M 线速的 91.8%，
已接近 100Base-TX 上 TCP 的实际上限（协议开销约 5~8%）。

### 5. 接收路径

```
FEC DMA 把包写进 RX 描述符指向的缓冲，置 IEVENT，拉中断
  ▼ fec_enet_interrupt()
  │  readl(FEC_IEVENT) 读事件 + 写回清标志
  │  napi_schedule_prep() → write FEC_IMASK 只留 MII（关 NAPI 中断）
  │  __napi_schedule() 挂到软中断 NET_RX_SOFTIRQ
  ▼ 软中断 net_rx_action → napi_poll = fec_enet_rx_napi()
  │  fec_enet_rx(ndev, budget) 批量收（budget = NAPI_POLL_WEIGHT = 64）
  │  取 skb、dma_unmap、校验和出错就丢弃，否则置 CHECKSUM_UNNECESSARY
  │  VLAN 包走 __vlan_hwaccel_put_tag()
  │  napi_gro_receive() 做 GRO 合并后交给协议栈
  │  顺便 fec_enet_tx() 回收发送环
  ▼ 若本轮到 64 个包还没收完：返回 budget，等下一次 poll
    若收完了：napi_complete() + 恢复 FEC_DEFAULT_IMASK（重新开中断）
  ▼ 协议栈：ip_rcv → tcp_v4_rcv → 找到 socket → 唤醒应用
```

这条"**中断只负责叫醒，收包在软中断里批量做**"就是 Q2/Q3 讲过
的 NAPI 模型；它和 PHY 的轮询状态机是两回事——
PHY 轮询管的是"链路 up 没 up"，NAPI 管的是"包收得够不够快"。

### 6. 硬件卸载能力（本板已启用）

`fec_enet_init()` 里，因为 `imx6ul-fec` 带
`FEC_QUIRK_HAS_CSUM | FEC_QUIRK_HAS_VLAN`：

```c
ndev->features |= (NETIF_F_IP_CSUM | NETIF_F_IPV6_CSUM
                   | NETIF_F_RXCSUM | NETIF_F_SG | NETIF_F_TSO);
ndev->features |= NETIF_F_HW_VLAN_CTAG_RX;
ndev->hw_features = ndev->features;
```

意味着收发校验和、分段（TSO/SG）、VLAN 接收都由 FEC 硬件做，
CPU 不用逐包算 checksum。这也是 91.7Mbps 这个数值能接近线速的原因之一。

### 7. PHY 与 MAC 的"分工协作"（这张表最关键）

| 关注点 | 谁负责 | 本项目落点 |
|---|---|---|
| 帧的成/解、CRC、地址过滤、DMA | MAC(FEC) | `fec_main.c` |
| 线编码、时钟恢复、自协商、链路状态 | PHY(RTL8201F) | `libphy` + `realtek.c` |
| 速率/双工变化怎么通知 MAC | PHY 状态机 → `fec_enet_adjust_link` | 回调里改 `ECR/RCR` |
| 加载 PHY 驱动 | `PHY ID` 匹配 `phy_driver` | 补了 `0x001cc816` 才绑到 RTL8201F |
| 管理通道 | MDIO/MDC（FEC 侧 `MII_SPEED/MII_DATA`） | 读 `BMCR/BMSR/PHYIDR` |
| 中断 | MAC 中断给 GIC；PHY 中断本板没接 | `irq=-1` → 轮询 `phy_state_machine` |

所以一旦 PHY 侧没起来，症状不是"网卡报错"，而是
`carrier=1` 之前链路一直不 up，NFS 挂不上，整机卡在启动。

### 8. 部署层：本项目的 IP 规划与服务

| 项目 | 值 | 说明 |
|---|---|---|
| 开发板 eth0 | `192.168.31.50` | 静态 IP，`ip=...:off` 关闭 DHCP |
| 主机（Ubuntu） | `192.168.31.218` | TFTP + NFS 服务器 |
| 网关/掩码 | `192.168.31.1` / `255.255.255.0` | — |
| NFS 根 | `192.168.31.218:/home/pointer/.../deploy/nfs/rootfs` | `v3,tcp,nolock` |
| 接口清单 | eth0、eth1、lo、sit0 | eth1 无 PHY 不可用；`ipv6.disable=1` |
| 吞吐测试 | 主机 `nc -l -p 9000`，板端 `dd 100MiB \| nc` | 91.7Mbps |

bootargs 里这一段就是网络结构的"配置声明"：

```
root=/dev/nfs rw init=/linuxrc
nfsroot=192.168.31.218:/home/pointer/.../deploy/nfs/rootfs,v3,tcp,nolock
ip=192.168.31.50:192.168.31.218:192.168.31.1:255.255.255.0::eth0:off
ipv6.disable=1
```

`ip=` 的字段顺序是：本机 IP : 服务器 IP : 网关 : 掩码 : 主机名 : 设备 : 自动配置。
最后那个 `off` 表示不做 DHCP，直接静态配置，起步更快；
内核里也确实关掉了 `CONFIG_IP_PNP_DHCP`。

### 9. 四个真实业务场景怎么串起这套结构

**① NFS 根文件系统（最关键）**

```
应用 open("/usr/local/bin/VehicleSystem")
  ▼ VFS → NFS client（RPC over TCP）→ TCP → IP → dev_queue_xmit
  ▼ FEC + PHY → 网线 → 主机 nfsd → 读磁盘 → 回包
  ▼ 中断 → NAPI → ip_rcv → tcp_v4_rcv → 唤醒应用
```

这就是为什么"网络通不通"等于"板子能不能起来"，
也是我在 Q1 里花大力气排查 PHY 的原因。

**② TFTP 下载内核（U-Boot 阶段，另一套栈）**

`tftp 80800000 zImage` 走 U-Boot 的 `net/tftp.c` + `drivers/net/fec_mxc.c`，
UDP 69 端口，需要 U-Boot 自己完成 PHY 自协商
（`CONFIG_FEC_MXC_PHYADDR 0x1`，与 Linux 侧同一颗 PHY）。

**③ 吞吐验证**：主机 `nc -l -p 9000`，板端 `dd | nc`，
用来验证 MAC+PHY 通路是否在正常水平（91.7Mbps）。

**④ 视频流**：`mjpg-streamer` 从 UVC 摄像头取 JPEG
（event3 那个设备的同一台摄像头），通过 HTTP 推到主机用 VLC 看；
这是 TCP 大流量场景，正好也用 FEC 的 TSO/SG。

### 10. 排障用的网络相关接口

| 手段 | 看什么 |
|---|---|
| `dmesg \| grep "FEC PHY driver"` | 绑定的是 Generic PHY 还是 RTL8201F |
| `cat /sys/bus/mdio_bus/devices/*/phy_id` | PHY ID 是否 `0x001cc816` |
| `cat /sys/class/net/eth0/{speed,duplex,carrier,mtu}` | 100/full/carrier=1/1500 |
| `/proc/interrupts` | FEC 中断计数是否随流量增长 |
| `devmem 0x020E0074 32` | MDIO/MDC 引脚是否被 ENET2 组占着 |
| `ip link set eth1 up` | 报 `SIOCSIFFLAGS: No such device`，确认 eth1 无 PHY |
| 主机 `nc` + 板端 `dd` | 吞吐 91.7Mbps，验证通路 |

### 11. 一句话总结

本项目的网络是"**硬件链路 + 两套软件栈 + 一套部署规划**"三部分配合：
硬件上是 FEC(MAC) 通过 RMII 接 RTL8201F(PHY)，
靠 MDIO/MDC 读 `BMCR/BMSR/PHYIDR` 完成自协商，靠 TX/RX 各 512 个
描述符环做 DMA 收发；软件上 Linux 侧走
socket → TCP/IP → `dev_queue_xmit`/`netif_receive_skb` →
`fec_enet_start_xmit`/`fec_enet_interrupt` + NAPI + `napi_gro_receive`，
并启用硬件校验和、TSO/SG、VLAN 卸载；U-Boot 侧另有一套
`fec_mxc.c` + `net/tftp.c` 负责 TFTP；部署上开发板静态
`192.168.31.50`、主机 `192.168.31.218` 提供 NFS 根与 TFTP，
根文件系统走 `v3,tcp` NFS，实测 100M 链路 91.7Mbps（线速 91.8%）。
其中 **NFS 根决定整机可用性**，所以 PHY 绑定、自协商、MDIO 引脚
这几处一旦有问题，表现就是"启动卡死"而不是"网卡报错"。

## Q11. 主控 SoC 与 MAC、PHY 芯片的配合

### 1. 先分清三者分别是谁、在哪

| 角色 | 在哪 | 本项目对应 | 职责 |
|---|---|---|---|
| SoC | 芯片本体 | i.MX6ULL（Cortex-A7） | 提供总线、时钟、引脚复用、中断、DMA |
| MAC | **集成在 SoC 内部** | FEC / ENET1 `0x020B_4000`、ENET2 `0x0218_8000` | 成帧解帧、CRC、地址过滤、DMA 描述符环、硬件卸载 |
| PHY | **板上的独立芯片** | RTL8201F（MDIO 地址 1，ID `0x001cc816`） | 线编码、时钟恢复、自协商、链路状态、模拟驱动 |

关键认知：**MAC 不是外接芯片，而是 SoC 的一个外设 IP**，
挂在 AIPS 总线上，靠 MMIO 寄存器操作、靠中断和 DMA 工作；
PHY 才是外置器件，必须由 SoC 提供时钟/复位，并通过
MDIO 被"管理"、通过 RMII 传数据。

### 2. 它们之间的五类连接（合作通道）

| 通道 | SoC 侧 | PHY 侧 | 本项目配置 |
|---|---|---|---|
| **数据（RMII）** | ENETx_TX_DATA0/1、TX_EN、RX_DATA0/1、CRS_DV、RX_ER | 对应引脚 | dts 里 `phy-mode = "rmii"`，2bit / 50MHz |
| **管理（MDIO/MDC）** | FEC 的 `MII_SPEED`(0x044) / `MII_DATA`(0x040) | MDIO/MDC | clause 22，PHY 地址 1 |
| **复位** | GPIO5_IO7(ENET1) / GPIO5_IO8(ENET2) | RESET# | `phy-reset-gpios` + `phy-reset-duration = <200>` |
| **参考时钟** | `IOMUXC_GPR1` 选 ENETx_REF_CLK | XI/REF_CLK 输入 | U-Boot 里 `clrsetbits gpr[1]`（ENET1 清 bit13 置 bit17） |
| **中断（可选）** | 某个 GPIO | INT# | **本板没接** → `irq = -1`，退化为轮询 |

注意这里有个顺序关系：**数据通道（RMII）只传以太网帧，
管理通道（MDIO）才是 SoC 去读 PHY 寄存器、下配置的路径**。
所以"MAC 怎么知道 PHY 是 100M 还是 10M"这件事，
必须靠 MDIO 读回来，而不是靠 RMII。

### 3. 配合的完整时序（从 probe 到链路 up，含代码）

**① SoC 侧准备：时钟、引脚、参考时钟**

`IOMUXC_SW_MUX_CTL_PAD_x` 把引脚切到 ENET 功能、
`SW_PAD_CTL_PAD_x` 配上拉/驱动强度/速率，
`IOMUXC_GPR1` 选 50MHz REF_CLK 来源，
`CCM_CCGRx` 打开 FEC 时钟。
这一步在 U-Boot（`setup_iomux_fec()`）和内核 pinctrl 里各做一轮。

**② SoC 用 GPIO 复位 PHY**（`fec_main.c: fec_reset_phy()`）

```c
msleep(msec);                       /* 保持 RESET# 有效，本板 200ms */
gpio_set_value(phy_reset, 1);       /* 释放复位 */
msleep(200);  /* 复位结束后至少再延时 150ms 才能继续操作 SR8201F */
```

这段注释直接点名了"SR8201F"——说明驱动作者知道板上是
RTL8201F/SR8201F 这颗国产兼容型号。**复位是 SoC→PHY 的第一个配合动作**，
PHY 要在复位释放后内部 PLL 锁定、从 REF_CLK 恢复时钟，
没等够时间就去读寄存器就会失败。

调用位置在 `fec_probe()` 里：

```
pm_runtime_enable → fec_enet_clk_enable(ndev, true)   /* 开 FEC 时钟 */
devm_regulator_get(dev, "phy") → regulator_enable()   /* 本板无 phy-supply，
                                                         走 dummy regulator */
fec_reset_phy(pdev)                                   /* 复位 PHY */
fec_enet_init(ndev)                                   /* 建 DMA 环、NAPI、
                                                         features 卸载位 */
request_irq(...)                                      /* FEC 中断 */
init_completion(&fep->mdio_done)
fec_enet_mii_init(pdev)                               /* 建 MDIO 总线 */
register_netdev(ndev)
```

**③ 建 MDIO 总线（SoC 的 MAC 主动去"认"PHY）**

`fec_enet_mii_init()` 先算 MDC 频率，因为 MDC 是从 IPG 时钟分频出来的：

```c
holdtime = DIV_ROUND_UP(clk_get_rate(fep->clk_ipg), 100000000) - 1;
fep->phy_speed = mii_speed << 1 | holdtime << 8;
writel(fep->phy_speed, fep->hwp + FEC_MII_SPEED);   /* 0x044 */
```

然后注册 mii_bus：

```c
fep->mii_bus->name = "fec_enet_mii_bus";
fep->mii_bus->read  = fec_enet_mdio_read;
fep->mii_bus->write = fec_enet_mdio_write;
for (i = 0; i < PHY_MAX_ADDR; i++)
        fep->mii_bus->irq[i] = PHY_POLL;   /* 全走轮询 —— 对应 irq=-1 */
mdiobus_register(fep->mii_bus);
```

每次读写 PHY 寄存器都是"拼一个 clause 22 帧丢进 `MII_DATA`"：

```c
writel(FEC_MMFR_ST | FEC_MMFR_OP_READ | FEC_MMFR_PA(mii_id) |
       FEC_MMFR_RA(regnum) | FEC_MMFR_TA, fep->hwp + FEC_MII_DATA);
wait_for_completion_timeout(&fep->mdio_done, usecs_to_jiffies(FEC_MII_TIMEOUT));
data = FEC_MMFR_DATA(readl(fep->hwp + FEC_MII_DATA)) & 0xffff;
```

那个 `mdio_done` 是靠 FEC 中断里的 `FEC_ENET_MII` 事件
`complete()` 唤醒的——**SoC 内部的中断、完成量、MAC 寄存器、
PHY 寄存器在这一刻串成一条链**。

总线注册后 `libphy` 扫 0~31 地址读 `PHYIDR1/2`，
本板在地址 1 读到 `0x001cc816`，匹配到 `realtek.c` 的
RTL8201F 条目 → 日志 `FEC PHY driver [RTL8201F 10/100 Ethernet]`。

**④ 自协商（PHY 与对端握手，MAC 只是旁观者）**

`eth0` up 时 `fec_enet_mii_probe()` 调 `phy_connect()`，
之后 `phy_start()` 启动 `phy_state_machine`：

- 驱动（本板复用 genphy 回调）往 `BMCR(0x00)` 写自协商使能 + 重启自协商；
- PHY 与对端交换 FLP，能力放在 `ANAR(0x04)` / 对端 `ANLPAR(0x05)`；
- 读 `BMSR(0x01)` 的 link status / auto-neg complete，
  从 `LPA` 解析出速率和双工，得到 **100Mbps / Full**，
  本板这个过程约 3s（100BASE-TX 自协商的固有时延）。

**⑤ 结果回传给 MAC：`fec_enet_adjust_link()`**

PHY 状态机发现链路变化后回调驱动：

```c
phy_dev = of_phy_connect(ndev, fep->phy_node,
                         &fec_enet_adjust_link, 0, fep->phy_interface);
```

`fec_enet_adjust_link()` → `fec_restart()` 按解析出的速率/双工写
`FEC_ECR` / `FEC_RCR`（`imx6ul-fec` 带 `FEC_QUIRK_ENET_MAC`：
`RCR` bit8=1 选 RMII，bit9=0 表示 100M、bit9=1 表示 10M），
使能 MAC 收发并打开中断，然后 `netif_carrier_on()`。

**这就是三者配合的闭环**：
SoC 复位并管理 PHY → PHY 自协商决定速率 → 结果通过 MDIO 读回 →
MAC 按这个结果配置自己的 RMII 时序和收发器 → 数据面才开始工作。

### 4. 寄存器层面的"谁配谁"对照表

| 环节 | SoC 侧寄存器 | PHY 侧寄存器 |
|---|---|---|
| FEC 时钟 | `CCM_CCGRx` | — |
| 引脚复用/电气 | `IOMUXC_SW_MUX_CTL_PAD` / `SW_PAD_CTL_PAD` | — |
| 参考时钟来源 | `IOMUXC_GPR1` | REF_CLK/XI 输入 |
| 硬复位 | `GPIO5_GDIR/DR` | RESET# 引脚 |
| MDC 频率 | `FEC_MII_SPEED`(0x044) | — |
| MDIO 帧 | `FEC_MII_DATA`(0x040) | `BMCR`(0x00)、`BMSR`(0x01)、`PHYIDR1/2`(0x02/0x03)、`ANAR`(0x04)、`ANLPAR`(0x05) |
| MAC 使能/速率/双工 | `FEC_ECR`(0x024)、`FEC_RCR`(0x084) | — |
| MAC 中断 | `FEC_IMASK`(0x008)、`FEC_IEVENT`(0x004) | INT#（本板未接） |
| DMA 收发环 | `FEC_R_DES_START`/`X_DES_START`、`RDAR`/`TDAR` | — |
| 数据面 | RMII 引脚（2bit/50MHz） | 4B/5B、MLT-3、CDR、驱动 |

### 5. 实测证据与故障对照（三层定位法）

本板实测：PHY ID `0x001cc816`、MDIO 地址 1、100Mbps/Full、
MTU 1500、`irq = -1`（轮询）、`phy-supply` 缺失走 dummy regulator、
吞吐 91.7Mbps。

排查时的顺序是"MAC → 总线 → PHY → 链路"四步：

| 观察点 | 正常表现 | 出问题说明什么 |
|---|---|---|
| `dmesg \| grep "fec 20b4000"` | `eth0: registered PHC device` | MAC 自身没 probe，看时钟/引脚/regulator |
| `libphy: fec_enet_mii_bus: probed` | 有 | 没有说明 MDIO 引脚或 MDIO 时钟有问题 |
| `FEC PHY driver [RTL8201F...]` | 绑定成功 | 显示 `Generic PHY` 说明内核没编 realtek 驱动或 PHY ID 不在表里 |
| `/sys/class/net/eth0/{speed,duplex,carrier}` | 100/Full/1 | 一直 `carrier=0` 说明自协商或 REF_CLK 有问题 |

对应的典型故障：

- **引脚复用错**：本项目 ENET1 的 MDIO/MDC 实际被 ENET2 的 pinctrl 组占着
  （`devmem 0x020E0074` 读到 `0x1` = GPIO1_IO06 是 ENET2_MDIO），
  结果是 MDIO 扫不到 PHY。
- **复位极性/时序错**：和 GT9147 那次 gpiod 极性事故同源——
  复位没真正释放，读 PHY ID 会得到 0x0000/0xFFFF。
- **PHY 驱动缺失/ID 不在表里**：能通但绑到 Generic PHY，
  拿不到芯片专属配置的挂载点（这是我补 `0x001cc816` 的原因）。
- **REF_CLK 选错或没输出**：PHY 没时钟，自协商永远不完成。
- **PHY 中断未接**：功能正常（`irq=-1` 走 `PHY_POLL`），
  但链路变化的响应变慢。

### 6. 一句话总结

配合关系是"**SoC 管资源、MAC 管帧、PHY 管线**"：
i.MX6ULL 把 MAC 集成在芯片内部（FEC，寄存器 `0x020B4000`），
SoC 通过 `CCM_CCGRx` 供时钟、`IOMUXC` 配 RMII 与 MDIO 引脚、
`IOMUXC_GPR1` 选 50MHz REF_CLK、`GPIO5` 硬复位 PHY；
MAC 通过 `MII_SPEED/MII_DATA` 走 clause 22 读 PHY 的
`PHYIDR1/2`（本板 `0x001cc816`，地址 1）完成驱动绑定，
通过 `BMCR/BMSR/ANAR/ANLPAR` 完成 100M/Full 自协商（约 3s），
再把结果经 `fec_enet_adjust_link` 回写到 `FEC_ECR/FEC_RCR`
（RMII bit8、100M bit9=0）；之后 MAC 用 DMA 环收发，
经 RMII 与 PHY 交换以太网帧，PHY 负责 4B/5B、MLT-3、
时钟恢复和线驱动。实测 100M 链路 91.7Mbps（线速 91.8%），
而 PHY 中断线本板没接，链路状态靠轮询。
